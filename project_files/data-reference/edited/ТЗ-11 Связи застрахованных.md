# ТЗ-11. Поток связей застрахованных

Редакция 1 от 15.11.2026.

Описание потока 1С:УСК → Дата-референс, по которому 1С передаёт, кто из застрахованных чей родственник. Отдельного ТЗ
1С на поток нет: документ составлен стороной Дата-референса по сообщениям тестового контура и ответам 1С:УСК
(15.11.2026) и описывает, как сервис принимает поток. Общие правила потоков — «Потоки данных, общие положения»
контракта 1С:УСК; здесь — только то, что относится к связям.

## Назначение

Связь — запись регистра сведений 1С: полис застрахованного, полис связанного с ним застрахованного (например,
родственника), тип связи и срок. Сервису Заявок связи нужны для индивидуальной заявки: участники — застрахованный и
связанные с ним застрахованные. Читает связи сервис Заявок через REST Дата-референса; ручка описывается отдельно.

Застрахованный в контуре — это полис (отдельной сущности «застрахованное лицо» нет), поэтому обе стороны связи — GUID
полисов: те же, что `id` в потоке полисов (ТЗ-01) и `policies.external_id` в базе сервиса. Полис застрахованного
(`idInsured`) — не обязательно полис сотрудника: 1С может связать полисы любых застрахованных.

## Очереди и конверт

| Очередь | `metadata.topic` | Что приходит |
|---|---|---|
| `1c-usk_to_rvl-online_insured-association-changes` | `insured-association-changes` | сообщения со строками регистра |
| `1c-usk_to_rvl-online_insured-association-changes-final` | `insured-association-changes-final` | финальное сообщение передачи со счётчиками |

Имена очередей — настройки сервиса (`ONEC_QUEUE_INSURED_ASSOCIATIONS`, `ONEC_QUEUE_INSURED_ASSOCIATIONS_FINAL`), в
таблице — значения тестового контура. Очереди заводит 1С:УСК, сервис их не объявляет.

Конверт общий для всех потоков: `{"data": {…}, "metadata": {"message-id": …, "topic": …, "producer": …,
"creation-timestamp": …}}`. Ключ дедупликации — `metadata.message-id`; повторная доставка с тем же `message-id` второй
раз не принимается. Подтверждение брокеру — после записи сообщения в базу сервиса.

## Сообщение со строками

`data` сообщения очереди `…-changes`:

| Поле | Тип | Обяз. | Что значит |
|---|---|---|---|
| `cid` | GUID | да | идентификатор передачи; общий у всех её сообщений |
| `mode` | строка | — | режим записи регистра; приходит `Замещение` (ниже) |
| `filter` | массив | да | отбор набора записей (ниже) |
| `recordSet` | массив | да | строки регистра; бывает пустым массивом — тогда это сообщение без строк. Поля нет, `null` или не массив — ошибка контракта (раздел «Ошибки»), а не сообщение без строк |

Строка `recordSet`:

| Поле | Тип | Обяз. | Колонка `insured_associations` | Что значит |
|---|---|---|---|---|
| `rowNumber` | целое | да | — | номер строки в передаче; задаёт порядок строк из разных сообщений, не хранится |
| `idInsured` | GUID | да | `insured_policy_external_id` | полис застрахованного, к которому относится связь |
| `otherSide.value` | GUID | да | `related_policy_external_id` | полис связанного застрахованного |
| `otherSide.type` | строка | — | — | вид ссылки 1С, `CatalogRef.ПолисаЗастрахованных`; не используется |
| `otherSide.representation` | строка | — | — | ФИО связанного застрахованного; **не хранится** (раздел «Персональные данные») |
| `relationType` | GUID | да | `relation_type_external_id` | тип связи; справочника типов у сервиса нет, хранится и отдаётся GUID |
| `period` | дата | да | `valid_from` | начало действия записи |
| `periodTo` | дата | — | `valid_to` | окончание действия записи; `3000-01-01` — без окончания (NULL) |

Значения — по общим правилам контракта 1С:УСК: GUID только в канонической записи (8-4-4-4-12), нулевой GUID —
«значения нет»; дата берётся календарным днём как написана, в любом из трёх видов (со смещением, без смещения, голая
дата), смещение не переводится в UTC.

Тип связи сервис отдаёт GUID'ом; наименование типа сервис Заявок узнаёт в 1С:УСК (решение владельца 15.11.2026).
Встречавшиеся типы связи: `4b4e0f45-2c50-11e8-8123-005056b43f21`, `5e0c951b-2c51-11e8-8123-005056b43f21`,
`797093be-2c51-11e8-8123-005056b43f21`, `6a424bfd-2c51-11e8-8123-005056b43f21`.

## Финальное сообщение

`data` сообщения очереди `…-changes-final`:

| Поле | Тип | Обяз. | Что значит |
|---|---|---|---|
| `cid` | GUID | да | идентификатор передачи |
| `countMessages` | целое ≥ 0 | да | сколько сообщений со строками в передаче |
| `countRows` | целое ≥ 0 | да | сколько строк во всех сообщениях передачи |
| `filter` | массив | да | отбор передачи — тот же, что в её сообщениях со строками |
| `mode` | строка | — | `Замещение` |

Финальное сообщение в передаче одно. Признак финального — наличие счётчиков.

## Отбор и режим «Замещение»

Элемент `filter`: `{"fieldName": …, "value": …, "isActive": true|false}`. Измерения регистра — четыре:

| `fieldName` | `value` | Колонка |
|---|---|---|
| `period` | дата | `valid_from` |
| `idInsured` | GUID | `insured_policy_external_id` |
| `otherSide` | ссылка `{type, representation, value}`; берётся `value` | `related_policy_external_id` |
| `relationType` | GUID | `relation_type_external_id` |

Отбор задают действующие элементы (`isActive = true`); недействующие не учитываются. `isActive` обязан быть
логическим значением JSON: элемент без него или с другим значением отклоняет передачу, иначе отбор молча расширился бы. Запись подходит под отбор, если
по каждому действующему элементу её значение совпадает со значением элемента.

Режим «Замещение»: записи сервиса, подходящие под отбор передачи, заменяются строками передачи целиком. Пустая
передача (`countMessages = 0` или строк нет) удаляет записи по отбору — так 1С сообщает об окончании связи. Записи вне
отбора не меняются.

Каждая запись регистра хранится отдельно. Записи одной пары полисов с одним типом и разным началом — разные записи.
**Связь действует на дату D, если есть её запись с `period` ≤ D ≤ `periodTo`** — по всем записям, день окончания
включительно, без среза последних (решение владельца 15.11.2026). Чтение связей на дату — задача ручки REST.

## Сборка передачи

- Передача — финальное сообщение и сообщения со строками с одним `cid`. Сообщения со строками по одному не
  применяются: сервис копит их, пока передача не соберётся.
- Порядок двух очередей не гарантирован: финальное сообщение может прийти раньше строк. Собранность проверяется на
  каждом сообщении передачи.
- Передача собрана, когда пришло финальное сообщение и сообщений со строками — `countMessages`. Тогда сверяются
  счётчики: строк во всех сообщениях должно быть `countRows`.
- Счётчики не сошлись (сообщений со строками больше `countMessages`, строк больше или меньше `countRows`) — передача
  не применяется, все её сообщения отклоняются, прежние связи не меняются.
- Повторная доставка того же сообщения (тот же `message-id`) не учитывается дважды. То же содержимое под другим
  `message-id` — ещё одно сообщение передачи.

## Применение

Собранная передача применяется одной транзакцией:

1. Отбор — из финального сообщения. Отбор сообщения со строками, отличный от отбора финального, отклоняет передачу.
2. Строки всех сообщений берутся в порядке `rowNumber`. Строка вне отбора своей передачи отклоняет передачу; две
   строки с одинаковыми четырьмя измерениями — тоже.
3. Если уже применена передача, финальное сообщение которой принято позже, а отбор пересекается с отбором этой
   передачи, эта передача пропускается: применяется та, что финализирована последней. Отборы пересекаются, если по
   каждому измерению, заданному в обоих, значения совпадают; незаданное измерение пересекается с любым. Пропускается
   передача целиком, даже если пересечение частичное: например, более старая передача по одному застрахованному не
   применяется и к его связям, которых более новая передача (по одной паре полисов) не касалась (подтверждено
   владельцем 15.11.2026). Если 1С задаёт отбор всегда одним набором полей, частичных пересечений не бывает
   (открытый вопрос 2).
4. Если полиса застрахованного или связанного ещё нет — передача ждёт полис (раздел «Ожидание полиса»).
5. Записи, подходящие под отбор, удаляются; строки передачи записываются.

## Ожидание полиса

Связь может прийти раньше полиса — и связанного застрахованного, и самого застрахованного. Тогда все сообщения
передачи ждут полис со статусом «ждёт родителя» и причиной `ждёт родителя: полис <GUID>`; ждут первый недостающий
полис по порядку строк, сначала полис застрахованного. Поток ожидающая передача не держит. Пришёл полис — передача
применяется на следующем проходе разбора.

Не дождалась полиса за `projectx.import.parent-wait-timeout` (24 часа от начала ожидания) — все сообщения передачи
отклоняются с причиной `срок ожидания родителя истёк: полис <GUID>`; полис, пришедший позже, отказ не отменяет.
Если после прихода одного полиса передача ждёт второй, срок отсчитывается заново. Передача без строк полисов не ждёт.
Полис не признаётся «не нашим»: поток полисов приходит без отбора.

## Ошибки

Ошибка в сообщении отклоняет всю передачу без повторов. У сообщения с ошибкой — сама ошибка, у остальных сообщений
передачи — `передача <cid> отклонена: ошибка в сообщении <message-id>: <причина>`. Причины называют поле, но не его
значение:

| Случай | Причина |
|---|---|
| GUID не в канонической записи | `поле idInsured не является GUID`, `поле otherSide.value не является GUID`, `поле relationType не является GUID` |
| GUID нет или нулевой | `нет обязательного GUID в поле <поле>` |
| нет даты начала | `нет обязательной даты в поле period` |
| в сообщении со строками нет поля `recordSet` или оно `null` | `нет обязательного поля recordSet` |
| `recordSet` не массив (объект, строка, число, логическое) | `поле recordSet не является массивом` |
| нет номера строки | `нет обязательного поля rowNumber` |
| в отборе нет действующих элементов | `в отборе передачи нет ни одного действующего элемента` |
| в отборе неизвестное поле | `в отборе передачи неизвестное поле` (имя поля не называется: это значение из сообщения) |
| у элемента отбора нет логического `isActive` | `в отборе передачи у элемента нет признака isActive` |
| поле отбора задано дважды | `в отборе передачи одно поле задано дважды` |
| значение отбора не читается | `поле filter.<поле> не является GUID` / `не является датой` |
| счётчики не сошлись | `счётчики передачи <cid> не сошлись: ожидалось N сообщений / K строк, получено n / k` |
| лишнее сообщение после применения | `лишний пакет: передача <cid> уже применена` |
| сообщение пришло к уже отклонённой передаче | `передача <cid> уже отклонена` |
| второе финальное сообщение | `второе финальное сообщение передачи <cid>` |
| разные отборы у сообщений передачи | `части передачи <cid> называют разные отборы` |
| строка вне отбора | `строка связи вне отбора передачи` |
| повтор измерений | `в передаче две строки связи с одинаковыми измерениями` |

Отбор без действующих элементов отклоняется, а не применяется: иначе пустая передача удалила бы все связи сервиса.
По той же причине сообщение со строками без массива `recordSet` отклоняет передачу: считай его сервис сообщением без
строк, передача «1 сообщение, 0 строк» удалила бы связи по отбору. Сообщение, пришедшее к уже закрытой передаче,
получает исход передачи («уже отклонена» или «уже пропущена»), к применённой — свою причину, как прочие ошибки.

## Персональные данные

`otherSide.representation` — ФИО связанного застрахованного — есть в строках и в отборе. Сервис его не хранит (ФИО
есть в полисе) и не пишет в журнал. Тело сообщения в журнале входящих (`inbound_message.payload`) стирается через
`projectx.import.payload-ttl` (30 суток) после приёма при любом исходе разбора, как тела полисов. Передача, которая не
собралась за этот срок, после стирания собрана быть не может: её присылают заново.

## Наблюдение

- Передачу, которая ждёт частей дольше `projectx.import.stuck-transfer-threshold` (1 час), называет предупреждение
  проверки зависших передач (раз в 15 минут) и считает показатель `onec_insured_association_transfers_stuck`; правило
  оповещения — `max(onec_insured_association_transfers_stuck) > 0`.
- Истёкшее ожидание полиса — запись ERROR с `cid` передачи и рост `onec_inbound_parent_wait_expired_total{stream="INSURED_ASSOCIATIONS"}`.

## Пример

Данные вымышлены (ФИО и GUID полисов); строение и типы связи — как в сообщениях тестового контура. Сообщение со
строками:

```json
{"data":{"recordSet":[{"periodTo":"3000-01-01T00:00:00+03:00",
  "relationType":"797093be-2c51-11e8-8123-005056b43f21",
  "otherSide":{"type":"CatalogRef.ПолисаЗастрахованных","representation":"Тестов Пётр Иванович",
               "value":"11111111-2222-4333-8444-555555555502"},
  "idInsured":"11111111-2222-4333-8444-555555555501","period":"2026-11-13T00:00:00+03:00","rowNumber":1}],
 "filter":[{"value":"2026-11-13T00:00:00+03:00","isActive":true,"fieldName":"period"},
           {"value":"11111111-2222-4333-8444-555555555501","isActive":true,"fieldName":"idInsured"},
           {"value":{"type":"CatalogRef.ПолисаЗастрахованных","representation":"Тестов Пётр Иванович",
                     "value":"11111111-2222-4333-8444-555555555502"},"isActive":true,"fieldName":"otherSide"},
           {"value":"797093be-2c51-11e8-8123-005056b43f21","isActive":true,"fieldName":"relationType"}],
 "mode":"Замещение","cid":"aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeee01"},
 "metadata":{"producer":"Srvr=\"1c-test\";Ref=\"usk_test\";","schema-version":"",
             "creation-timestamp":63930160142030,"topic":"insured-association-changes",
             "message-id":"aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeee11"}}
```

Финальное сообщение той же передачи:

```json
{"data":{"countMessages":1,"countRows":1,"filter":[…тот же отбор…],"mode":"Замещение",
         "cid":"aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeee01"},
 "metadata":{"producer":"Srvr=\"1c-test\";Ref=\"usk_test\";","schema-version":"",
             "creation-timestamp":63930160142216,"topic":"insured-association-changes-final",
             "message-id":"aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeee12"}}
```

Результат — одна запись `insured_associations`: полис `…501` связан с полисом `…502` типом `797093be-…`, начало
13.11.2026, без окончания.
