# ТЗ: API сервиса Дата-референс

Редакция 2 от 22.10.2026. Заменяет версию от 21.09.2026.

Сервис Дата-референс отдаёт справочные данные 1С:УСК только на чтение: каталог санаториев (ЛПУ) по договору страхования,
карточку и услуги ЛПУ с ценами, стоимость услуги за период, полисы, МКБ-10, договор страхования со страхователем и
страховую программу. Документ описывает действующий контракт сервиса.

**Статус документа.** Редакция 2 соответствует тому, как сервис работает. Правила ведёт команда сервиса в журнале
решений REST, ТЗ правится вслед за ним; номера В-4…В-15 в тексте — пункты журнала. Машиночитаемое описание тех же ручек —

## Назначение, границы и допущения

Все ручки — `GET`, ничего не записывают и не меняют состояние. Заявки, резервы, персональные данные участников заявок,
договоры КМ и печатные формы живут в сервисах Заявок и Договоров и в этот документ не входят. В 1С:УСК сервис ничего не
пишет: данные приходят из очередей 1С, их приём описан документами контракта 1С:УСК (ТЗ-01…ТЗ-10) и описанием потока
связей застрахованных (ТЗ-11).

Потребители:

| Потребитель | Ручки |
|---|---|
| Сервис Заявок (ЛК HR и кабинет застрахованного) | R-01…R-07, R-08 по GUID страхователя, R-10 |
| Сервис Договоров (ЛК застрахованного) | R-05д, R-08 по `id` и по `external_id`, R-09 |
| Кабинет застрахованного (insured-bff) | R-05 по номеру без договора (В-16), далее R-05 по `id` |

Допущения, на которых построены контракты:

- `external_id` договора страхования — входной ключ для R-01 и R-04. Вызывающий знает его заранее или получает по GUID
  страхователя: после входа кадровика через B2B-портал у сервиса Заявок есть `companyId` — GUID страхователя в 1С:УСК, и
  R-08 по `insurer_external_id` отдаёт действующий договор этого страхователя (В-13).
- Схема данных — та, что задают миграции сервиса; «Структура БД v.0.1» с изменениями v.0.2 описывает её с расхождениями.
  Поля `lpu_contracts.main_price_dog` нет: прайсовый договор выбирается при чтении по `main_contract_external_id` и
  `use_prices_main_contract` (базовая логика B).
- Признак «программа РВЛ» — наличие строки в `programs`: справочник наполняется только программами РВЛ, отдельного флага
  нет. Ссылки полиса на программу хранятся GUID'ом 1С без внешнего ключа: строка полиса по программе не РВЛ сохраняется
  и просто не находит пары в `programs`.
- Виды обращения РВЛ определяются по наименованию в `appeal_types`: «РВЛ и СКЛ» и «РВЛ в России» (В-9).
- При неоднозначности данных (два кандидата на прайсовый договор, две строки прайса на одни сутки, два действующих
  договора страхователя, два полиса с одним номером в договоре) сервис отвечает ошибкой, а не выбирает наугад: лучше
  заметный отказ, чем тихо неверная цена или не тот договор.
- Поля, для которых в потоках 1С нет источника, в ответы не входят (В-8): нечем заполнить — потребитель получал бы `null`
  всегда. Появится источник — поле добавляется отдельным изменением контракта.

## Общие соглашения

**Транспорт.** Синхронный REST, JSON в UTF-8, имена полей в `snake_case`, префикс пути `/internal/v1`. Ручки под
`/internal` — внутренние, за пределы сети контура не публикуются; префикс общий с сервисом Договоров.

**Аутентификация.** Межсервисной аутентификации и сервисного токена нет. Ручки защищает сетевая политика контура.

**Значения.**

- Даты — `yyyy-mm-dd`, без времени и часового пояса. Открытая дата окончания 1С (`3000-01-01`) хранится и отдаётся как
  `null` и читается как «бессрочно».
- Денежные суммы и проценты — JSON-числа, валюта — рубли.
- Идентификаторы — UUID. В каждом объекте ответа есть оба ключа: внутренний `id` сервиса и `external_id` — GUID записи в
  1С:УСК. Первый нужен для следующих вызовов, второй — для обмена с 1С:УСК.
- Параметр пути `{id}` во всех ручках — внутренний `id`, не GUID 1С; у каждой ручки сказано, из какого ответа его взять.
  GUID 1С принимается только параметрами запроса `external_id`, `contract_external_id` и `insurer_external_id`.
- Признак архива `is_archive` (пометка на удаление в 1С) отдаётся в ответах о договоре, полисе, программе и коде МКБ-10:
  без него потребитель не заметит договор, выпущенный по удалённой программе.

**Действующая запись (В-4)** — одно правило для полисов, договоров ЛПУ и договоров страхования везде, где ручка отбирает
действующие записи:

```
is_archive = false
AND begin_date <= :today
AND (end_date IS NULL OR end_date >= :today)
```

Ещё не начавшийся полис или договор ЛПУ действующим не считается: полис следующего периода не даёт права на лечение, а
договор ЛПУ следующего года, загруженный заранее, без проверки `begin_date` сделал бы прайсовый договор неоднозначным на
весь остаток текущего года. Будущие периоды прайса в R-03 отдаются: вызывающему бывает нужен заезд следующего сезона.

Остальное отбирается так: строка условий обслуживания полиса — по базовой логике A (доступна, день в её сроке); ЛПУ,
программы, услуги и виды обращения — только `is_archive = false`. Ручки, которые отдают запись по ключу (R-05, R-05д,
R-08 по `id` и `external_id`, R-09, R-07 по кодам), действующие не отбирают и отдают и архивные записи.

Текущая дата берётся в зоне Europe/Moscow и передаётся в запрос параметром `:today`, а не вычисляется через
`CURRENT_DATE` внутри запроса: на сервере в UTC `CURRENT_DATE` три часа в сутки отстаёт от московской даты, а кроме того
дата нужна для ключа кэша.

**Параметры запроса.**

- Параметр считается переданным, если его имя есть в строке запроса, даже с пустым значением: `external_id=` вместе с
  другим ключом — это два ключа и 400, а не «пустой ключ не считается».
- Взаимоисключающие ключи одной ручки вместе — 400 `VALIDATION_ERROR` с именем поля: сервис не угадывает, какой ключ
  имелся в виду.
- Неизвестные параметры не проверяются и на ответ не влияют; исключение — прежний ключ договора `contract_id` в поиске
  полиса R-05 по ключу, он отклоняется явно.
- Постраничной выдачи нет. R-04 и R-07 ограничивают выдачу параметром `limit`, остальные списки отдаются целиком: объём в
  рамках одного договора, одного ЛПУ или одной программы небольшой.

**Пределы входа.** Выход за предел — 400 `VALIDATION_ERROR` с именем поля, до обращения к базе.

| Ручка | Параметр | Предел |
|---|---|---|
| R-04 | `query` | не больше 100 символов в строке, как она пришла (до обрезки пробелов); не меньше 2 после обрезки краевых пробелов и схлопывания внутренних |
| R-04 | `limit` | от 1 до 50, по умолчанию 10 |
| R-07 | `query` | не больше 100 символов до обрезки пробелов; не меньше 2 после обрезки краевых |
| R-07 | `limit` | от 1 до 100, по умолчанию 20; действует только с `query`, с `codes` не учитывается |
| R-07 | `codes` | не больше 100 элементов в перечне, как он пришёл (пустые элементы и повторы тоже считаются) |
| R-06 | `date_to` | позже `date_from`; не больше 366 ночей после `date_from` |

Символы считаются по Unicode. Предел R-06 и пределы строк — настройки сервиса; уменьшение предела сужает контракт и
делается только с уведомлением потребителей.

**`X-Request-Id`.** Заголовок принимается, если совпадает с `[A-Za-z0-9._-]{1,64}`; иначе сервис выдаёт свой UUID, запрос
при этом не отклоняется. Значение возвращается в заголовке ответа и в `error.request_id`, по нему запрос находится в
журнале сервиса. Вызывающий передаёт свой `X-Request-Id` сквозняком.

**Время ответа и отказ базы.** Чтение из базы ограничено 3 с. База недоступна или не ответила вовремя — 503
`SERVICE_UNAVAILABLE` в едином формате, без `Retry-After`. При недоступной базе 503 приходит через 2 с (ожидание
соединения), при зависшей базе или занятом пуле соединений — до 5 с, поэтому таймаут чтения у клиента — не меньше 7 с. На 503 вызывающий повторяет тот же запрос
ограниченное число раз с паузой; это не отказ его процесса. Если ответ есть в кэше, он отдаётся и при недоступной базе.

**Перегрузка.** Сервис обрабатывает одновременно не больше заданного числа запросов ко всем ручкам `/internal/v1`
(настройка сервиса, по умолчанию 100 на экземпляр). Запрос сверх предела не ждёт свободного места: он сразу получает тот же
503 `SERVICE_UNAVAILABLE` в едином формате, с `X-Request-Id` и без `Retry-After`; уже принятые запросы обслуживаются.
Для вызывающего это тот же случай, что отказ базы: повторить тот же запрос ограниченное число раз **с паузой**, а не
сразу — немедленный повтор усиливает перегрузку. Поле `message` не разбирать: по нему причины 503 не различаются,
различает их только журнал и метрики сервиса. Пробы `/livez`, `/readyz` и порт управления под предел не попадают.

**Отказы до ручки.**

- Нет такого пути — 404 `NOT_FOUND` в едином формате, `application/json` при любом `Accept`.
- Метод, кроме `GET`, `HEAD` и `OPTIONS`, — 405 `METHOD_NOT_ALLOWED` с заголовком `Allow: GET, HEAD, OPTIONS`. `HEAD`
  отвечает как `GET`, без тела; `OPTIONS` — 200 с тем же `Allow`.
- `Accept` не допускает JSON — 406 `NOT_ACCEPTABLE`, раньше ручки.
- Запрос длиннее 8 КБ (строка запроса вместе с заголовками) отбивает встроенный веб-сервер: 400 в HTML, без
  `X-Request-Id`. Это ответ веб-сервера, а не сервиса; при пределах входа выше до него не доходит.

## Коды ошибок

Тело любой ошибки — формат, общий с сервисом Договоров:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "нарушен формат запроса",
    "details": [{"field": "id", "reason": "ожидается UUID"}],
    "request_id": "3f1c2a9e-5b7d-4c11-9a2e-7d0f6b8e1a42"
  }
}
```

`details` — всегда массив объектов, состав элемента зависит от кода; поле с плавающим типом ломает генерацию клиентов.
`message` — для журнала, не для показа пользователю.

| HTTP | code | Когда | `details` |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | параметр не того формата, обязательного нет, недопустимое сочетание, выход за предел | `{field, reason}` |
| 404 | `NOT_FOUND` | нет такого пути | пусто |
| 404 | `INSURANCE_CONTRACT_NOT_FOUND` | договора страхования нет; в R-01 и R-04 — ещё и не действует сегодня; по GUID страхователя — нет действующего договора | пусто |
| 404 | `LPU_NOT_FOUND` | ЛПУ нет либо оно в архиве | пусто |
| 404 | `POLICY_NOT_FOUND` | полиса нет (в том числе ещё не пришёл из 1С) | пусто |
| 404 | `SERVICE_NOT_FOUND` | услуги нет, она в архиве или ЛПУ не отдаёт её в перечне R-03 | пусто |
| 404 | `PROGRAM_NOT_FOUND` | программы нет | пусто |
| 405 | `METHOD_NOT_ALLOWED` | метод не `GET` | пусто |
| 406 | `NOT_ACCEPTABLE` | `Accept` не допускает JSON | пусто |
| 409 | `AMBIGUOUS_PRICE_CONTRACT` | у ЛПУ два и более кандидата на прайсовый договор | `{lpu_contract_id}` по кандидату |
| 409 | `AMBIGUOUS_POLICY` | по номеру больше одного полиса | `{policy_id}` по кандидату; в R-05 по номеру без договора — `{policy_id, contract_external_id}`, порядок не задан |
| 409 | `AMBIGUOUS_INSURANCE_CONTRACT` | у страхователя два и более действующих договора страхования | `{insurance_contract_id}` по кандидату, порядок не задан |
| 409 | `AMBIGUOUS_PRICE` | на одни сутки периода действует больше одной строки прайса | `{valid_from, valid_to}` строк |
| 422 | `NO_ACTIVE_PRICE_CONTRACT` | у ЛПУ нет ни одного действующего договора, по которому брать цены, или услуга к нему не относится | пусто |
| 422 | `PRICE_NOT_COVERED` | в периоде есть сутки без строки прайса | `{date_from, date_to}` непокрытых интервалов |
| 500 | `INTERNAL_ERROR` | необработанная ошибка сервиса | пусто |
| 503 | `SERVICE_UNAVAILABLE` | база недоступна или не ответила за 3 с, либо сервис перегружен: запрос пришёл сверх предела одновременно обрабатываемых | пусто |

Код 404 договора страхования называет справочник: `CONTRACT_NOT_FOUND` у сервиса Договоров — это договор КМ, и коды
контура не должны путаться.

Ошибки 409 и 422 — всегда проблема данных в 1С, а не ошибка вызывающего, поэтому в `details` есть всё для разбора:
идентификаторы конфликтующих записей или непокрытые интервалы. Такие ответы дополнительно пишутся в журнал сервиса на
уровне WARN — по ним собирается очередь на исправление на стороне 1С.

## Базовая логика A: программы РВЛ по договору

Общий шаг для R-01 и R-04: по `external_id` договора получить набор действующих полисов и программ РВЛ, которые они дают.

1. Договор страхования с этим `external_id` есть и действует сегодня по общему правилу. Нет или не действует — 404
   `INSURANCE_CONTRACT_NOT_FOUND`: истёкший и ещё не начавшийся договор отвечают так же, как архивный.
2. Действующие полисы договора — по общему правилу. Признак доступности самого полиса (`policies.availability`) в отбор
   не входит.
3. Программы РВЛ — те, у которых есть хотя бы одна действующая строка условий обслуживания полиса (`policy_services`):
   строка доступна (`availability = true`), сегодняшний день попадает в её срок (пустая дата срок с этой стороны не
   ограничивает), программа есть в `programs` и не в архиве.

```sql
WITH active_policies AS (                       -- шаг 2 (шаг 1 — отдельное чтение договора)
    SELECT p.id
    FROM policies p
    WHERE p.external_contract_id = :contract_external_id
      AND p.is_archive = false
      AND p.begin_date <= :today
      AND (p.end_date IS NULL OR p.end_date >= :today)
),
rvl_programs AS (                               -- шаг 3
    SELECT DISTINCT pr.id, pr.external_id
    FROM policy_services ps
    JOIN active_policies ap ON ap.id = ps.policy_id
    JOIN programs pr ON pr.external_id = ps.external_program_id
                    AND pr.is_archive = false
    WHERE ps.availability = true
      AND (ps.begin_date IS NULL OR ps.begin_date <= :today)
      AND (ps.end_date IS NULL OR ps.end_date >= :today)
)
```

Что здесь важно:

- `JOIN programs` — это и есть фильтр «только программы РВЛ».
- Полис ссылается на договор и на программу GUID'ом 1С (`external_contract_id`, `external_program_id`) без внешнего
  ключа: 1С не гарантирует порядок потоков, и полис может прийти раньше договора или программы. Связь появляется, как
  только придёт вторая сторона, повторной выгрузки не нужно.
- Договор проверяется отдельно и раньше полисов, поэтому «договора нет» и «у договора нет полисов» различимы: первое — 404,
  второе — пустой ответ.
- Результат одинаков для всех пользователей договора и меняется только после сообщения 1С — он входит в кэш R-01
  (раздел о кэшировании).

## Базовая логика B: прайсовый договор ЛПУ

Прайсовый договор — договор ЛПУ, по которому берутся услуги и цены. Определяется при каждом чтении и используется в
R-01, R-02, R-03 и R-06. Главный договор ЛПУ и его допсоглашения действуют одновременно — это норма источника (В-5).

1. Кандидаты — действующие сегодня договоры ЛПУ по общему правилу: `is_archive = false`, `begin_date <= :today`,
   `end_date IS NULL OR end_date >= :today`.
2. Среди них ищем допсоглашения со своими ценами: `main_contract_external_id` заполнен и
   `use_prices_main_contract = false`. Ровно одно — оно и есть прайсовый договор (`kind = DOPS`); два и более — 409
   `AMBIGUOUS_PRICE_CONTRACT`.
3. Таких допсоглашений нет — берём главный договор (`main_contract_external_id` пуст). Ровно один — он прайсовый
   (`kind = MAIN`); два и более — 409 `AMBIGUOUS_PRICE_CONTRACT`; ни одного — 422 `NO_ACTIVE_PRICE_CONTRACT`.

Допсоглашение с `use_prices_main_contract = true` своих цен не имеет и в отборе не участвует — цены берутся с главного
договора. Признак выгрузки в СОБ (`uploaded_to_sob`) в отборе не участвует и отдаётся как есть.

```sql
WITH active AS (
    SELECT *
    FROM lpu_contracts
    WHERE lpu_id = :lpu_id
      AND is_archive = false
      AND begin_date <= :today
      AND (end_date IS NULL OR end_date >= :today)
),
dops AS (SELECT * FROM active
          WHERE main_contract_external_id IS NOT NULL
            AND use_prices_main_contract = false),
main AS (SELECT * FROM active
          WHERE main_contract_external_id IS NULL)
SELECT * FROM dops
UNION ALL
SELECT * FROM main WHERE NOT EXISTS (SELECT 1 FROM dops);
```

Одна строка — прайсовый договор. Больше одной — 409 `AMBIGUOUS_PRICE_CONTRACT` с `id` кандидатов в `details`. Ни одной —
422 `NO_ACTIVE_PRICE_CONTRACT`. В каталоге R-01 договоры читаются одним запросом на все отобранные ЛПУ, а выбор кандидата
делается по тем же шагам для каждого ЛПУ: N+1 запросов нет.

**Разное поведение в списке и в точечных ручках (В-6б).** В R-02, R-03 и R-06 спрашивают про конкретное ЛПУ, и ошибка —
единственный честный ответ: 409 или 422. В R-01 одна неверная строка в 1С положила бы весь каталог сразу для всех
пользователей договора, поэтому ЛПУ с неоднозначным прайсовым договором исключается из `items` и попадает в `skipped` с
причиной `AMBIGUOUS_PRICE_CONTRACT` и в журнал (WARN), а ЛПУ без действующего договора в каталог просто не попадает.

## R-01. Каталог ЛПУ по договору

```
GET /internal/v1/lpu?contract_external_id={uuid}
```

| Параметр | Обяз. | Описание |
|---|---|---|
| `contract_external_id` | да | GUID договора страхования в 1С:УСК |

Ответ — действующие ЛПУ, доступные застрахованным этого договора, по наименованию.

```json
{
  "items": [
    {"id": "…", "external_id": "…", "name": "Санаторий «Пример»",
     "region": "Московская область", "inn": "5000000000", "kpp": "500001001"}
  ],
  "skipped": [
    {"lpu_id": "…", "reason": "AMBIGUOUS_PRICE_CONTRACT"}
  ]
}
```

`region`, `inn`, `kpp` могут быть `null`. `skipped` — всегда массив, обычно пустой.

Порядок отбора:

1. Базовая логика A — договор действует, программы РВЛ его действующих полисов.
2. Строки перечня этих программ (`program_lpu`) по видам обращения РВЛ («РВЛ и СКЛ», «РВЛ в России», не в архиве) —
   различные ЛПУ.
   Сроки строки перечня в отбор не входят (В-6а).
3. Само ЛПУ не в архиве.
4. Базовая логика B — у ЛПУ однозначно определяется прайсовый договор. Нет действующего договора — ЛПУ в выдачу не
   попадает; неоднозначность — в `skipped`.

```sql
-- CTE базовой логики A
, rvl_appeal_types AS (
    SELECT external_id
    FROM appeal_types
    WHERE is_archive = false
      AND lower(trim(name)) IN (:rvl_appeal_type_names)   -- «рвл и скл», «рвл в россии»
)
SELECT DISTINCT l.id, l.external_id, l.name, l.region, l.inn, l.kpp
FROM program_lpu pl
JOIN rvl_programs rp ON rp.id = pl.program_id
JOIN rvl_appeal_types at ON at.external_id = pl.external_appeal_type_id
JOIN lpu l ON l.id = pl.lpu_id
WHERE l.is_archive = false
ORDER BY l.name;
```

Отбор по виду обращения нужен, чтобы в каталог РВЛ не попали учреждения, где по той же программе есть только
амбулаторная помощь или стационар. Вид обращения строки перечня хранится GUID'ом 1С без внешнего ключа: пока вид
обращения не пришёл из 1С, строка хранится, но в отбор не попадает.

Ошибки: 400 `VALIDATION_ERROR` — нет параметра или он не UUID; 404 `INSURANCE_CONTRACT_NOT_FOUND` — договора нет, он в
архиве, истёк или ещё не начался. Пустой `items` — не ошибка: у договора может не быть действующих полисов с программами
РВЛ.

## R-02. Карточка ЛПУ

```
GET /internal/v1/lpu/{id}
```

`{id}` — внутренний `id` ЛПУ: `items[].id` каталога R-01 или `services[].lpu_id` программы R-09 (программа отдаёт и
учреждения в архиве — для них R-02 отвечает 404 `LPU_NOT_FOUND`).

```json
{
  "id": "…", "external_id": "…",
  "name": "Санаторий «Пример»", "region": "…", "inn": "…", "kpp": "…",
  "address": "…",
  "price_contract": {
    "id": "…", "external_id": "…", "number": "0000RB000",
    "begin_date": "2026-01-01", "end_date": "2026-12-31",
    "uploaded_to_sob": true,
    "kind": "MAIN"
  }
}
```

`kind` — `MAIN` (главный договор) или `DOPS` (допсоглашение со своими ценами): вызывающему полезно видеть, что цены взяты
с допсоглашения; в разборе расхождений по суммам это первый вопрос. `region`, `inn`, `kpp`, `address`,
`price_contract.number` и `price_contract.end_date` могут быть `null`.

Краткого описания учреждения и предельного срока бронирования в ответе нет (В-8): в потоках 1С у них нет источника, а
«минимум 90 / 60 дней до заезда» — правило процесса сервиса Заявок, а не атрибут учреждения.

Ошибки: 400 — `id` не UUID; 404 `LPU_NOT_FOUND` — нет записи либо ЛПУ в архиве; 409 `AMBIGUOUS_PRICE_CONTRACT`; 422
`NO_ACTIVE_PRICE_CONTRACT`.

Ручка не проверяет, доступно ли ЛПУ по договору вызывающего: параметр один — `id` ЛПУ. Ограничение рамками договора —
отдельное изменение контракта, если понадобится.

## R-03. Услуги ЛПУ и цены

```
GET /internal/v1/lpu/{id}/services?need_prices=true
```

| Параметр | Обяз. | Описание |
|---|---|---|
| `id` (путь) | да | внутренний `id` ЛПУ, как в R-02 |
| `need_prices` | нет | `true` — отдать строки прайса; по умолчанию `false` |

Услуги берутся только по прайсовому договору (базовая логика B) и только по видам обращения РВЛ — без этого фильтра в
выдачу попадут процедуры и анализы, а нужны позиции размещения.

```json
{
  "lpu": {"id": "…", "external_id": "…", "name": "Санаторий «Пример»"},
  "price_contract": {"id": "…", "external_id": "…", "number": "…",
                     "begin_date": "…", "end_date": "…", "uploaded_to_sob": true, "kind": "MAIN"},
  "services": [
    {
      "id": "…", "external_id": "…",
      "code": "41.178.178", "name": "Размещение в 2-местном номере",
      "appeal_type": {"id": "…", "external_id": "…", "name": "РВЛ и СКЛ"},
      "prices": [
        {"price": 12000.00, "price_with_discount": 11400.00,
         "service_name": "…", "service_code": "26.23.006/82",
         "valid_from": "2026-01-01", "valid_to": "2026-05-31"}
      ]
    }
  ]
}
```

Правила:

- услуги — `contragent_services` прайсового договора, не в архиве, с видом обращения РВЛ (вид обращения не в архиве);
  по наименованию;
- `need_prices=false` — поля `prices` в ответе нет вовсе (не пустой массив, а отсутствующее поле), чтобы его нельзя было
  спутать с «цен нет»;
- `need_prices=true` — у каждой услуги строки прайса, которые действуют сегодня или начнутся позже (`valid_to` пуста или
  `>= :today`), по возрастанию `valid_from`; прошедшие периоды не отдаются;
- услуга без актуальных цен остаётся в списке с пустым `prices`: это диагностически важно — такая услуга даст 422 в R-06;
- услуги без вида обращения в выдачу не попадают — под фильтр по видам обращения они не подходят;
- строки прайса отдаются как есть, `price` и `price_with_discount`; какая сумма основная, решает R-06 (В-6в);
- могут быть `null`: `code` услуги, `price_with_discount`, `service_name`, `service_code` и `valid_to` строки прайса;
- `price_contract.external_id` — GUID договора ЛПУ в 1С, к которому относятся все услуги ответа. Его же ждёт 1С:УСК в
  сообщении о заявке как договор услуги (`owner_id`): вызывающий сохраняет его рядом с выбранной услугой, потому что
  прайсовый договор ЛПУ может смениться.

```sql
SELECT cs.id, cs.external_id, cs.code, cs.name, at.id, at.external_id, at.name
FROM contragent_services cs
JOIN appeal_types at ON at.external_id = cs.external_appeal_type_id
WHERE cs.lpu_contract_id = :price_contract_id
  AND cs.is_archive = false
  AND at.is_archive = false
  AND lower(trim(at.name)) IN (:rvl_appeal_type_names)
ORDER BY cs.name;
```

**Виды обращения по наименованию (В-9).** Отбор по строковому наименованию хрупок: переименование или лишний пробел в 1С
молча обнулят выдачу. Поэтому сравнение идёт без учёта регистра и краевых пробелов, список наименований — в настройке
сервиса, а не в коде, и при старте сервис пишет WARN, если хотя бы одно наименование в `appeal_types` не нашлось. Когда
1С назовёт GUID этих видов обращения, сравнение переводится на GUID той же настройкой.

Ошибки: 400 — `id` не UUID или `need_prices` не читается как логическое значение; 404 `LPU_NOT_FOUND`; 409 `AMBIGUOUS_PRICE_CONTRACT`; 422
`NO_ACTIVE_PRICE_CONTRACT`.

## R-04. Поиск полисов в договоре

```
GET /internal/v1/policies/search?contract_external_id={uuid}&query={text}&limit=10
```

Подсказка для поля «найти сотрудника»: кадровик набирает часть ФИО или номера полиса и выбирает из короткого списка.
Ищется среди действующих полисов договора с программами РВЛ (базовая логика A).

| Параметр | Обяз. | Описание |
|---|---|---|
| `contract_external_id` | да | GUID договора страхования в 1С:УСК — граница выдачи |
| `query` | да | часть ФИО или номера; пределы — в «Общих соглашениях» |
| `limit` | нет | от 1 до 50, по умолчанию 10 |

Правила поиска:

1. Нормализация строки: обрезка краевых пробелов, схлопывание внутренних, нижний регистр, `ё` → `е`.
2. В строке есть цифра — поиск по номеру полиса без учёта регистра: сначала точное совпадение, затем начало номера, затем
   вхождение.
3. Иначе строка режется на слова: каждое слово должно совпасть с началом фамилии, имени или отчества — так «иван петр»
   находит и «Петров Иван», и «Иванов Пётр».
4. Ранжирование по словам: сначала полисы, где совпали и фамилия, и имя, затем — где совпала фамилия, затем остальные.
   Внутри группы (и внутри групп поиска по номеру) — по фамилии и имени.
5. Предел и ранжирование применяются в базе, выдача обрезается по `limit`.

```json
{
  "items": [
    {"id": "…", "external_id": "…", "number": "26LM0000/000001",
     "last_name": "Тестов", "first_name": "Тест", "middle_name": "Тестович"}
  ]
}
```

`middle_name` может быть `null`.

Ошибки: 400 — нет параметра, `contract_external_id` не UUID, выход за пределы `query` или `limit`; 404
`INSURANCE_CONTRACT_NOT_FOUND` — договора нет, он в архиве, истёк или ещё не начался.

Дата рождения в выдачу не входит: в постановке было «ФИО + номер». Тёзки с одинаковым ФИО различаются номером полиса;
дата рождения добавляется только по требованию ИБ.

Родственники по работнику в выдаче поиска не группируются. Связь «чей это родственник» сервис с 15.11.2026 принимает
из 1С (поток связей застрахованных, ТЗ-11), но в эту ручку она не входит: застрахованных родственников отдаёт R-10.

Полисы, у которых персональные данные стёрты по сроку хранения, поиск не находит: он ищет только действующие полисы.

## R-05. Полис; R-05д. Полис без персональных данных

R-05 — полис целиком, с персональными данными, для сервиса Заявок и кабинета застрахованного:

```
GET /internal/v1/policies/{id}
GET /internal/v1/policies?external_id={uuid}
GET /internal/v1/policies?number={number}&contract_external_id={uuid}
GET /internal/v1/policies?number={number}
```

- По внутреннему `id` (`items[].id` подсказки R-04) или по `external_id` — однозначно.
- По номеру с договором: номер уникален в пределах договора, а не глобально. Полис ищется по паре «номер + GUID
  договора» без чтения самого договора: полис может прийти из 1С раньше договора, а неизвестный договор — тот же 404
  `POLICY_NOT_FOUND`. Нашлось два и более полиса — 409 `AMBIGUOUS_POLICY` со списком `id` в `details`.
- По номеру без договора (В-16) — для кабинета застрахованного, который знает номер полиса из токена, а договор не
  знает. Полис ищется среди полисов всех договоров. Один — 200, ответ тот же, что с договором; ни одного — 404
  `POLICY_NOT_FOUND`; несколько — 409 `AMBIGUOUS_POLICY`, ни один полис не отдаётся, чтобы застрахованный не увидел
  чужие данные; в `details` у каждого кандидата `policy_id` и `contract_external_id` — GUID договора 1С из самого полиса
  (договора в справочнике может не быть), порядок не задан. Дальше кабинет работает с полисом по его `id`.
- Номер сравнивается точно в обоих режимах: не нормализуется, регистр и пробелы значимы. Архивные, закончившиеся, ещё не
  начавшиеся и обезличенные полисы находятся так же, как с договором; пускать ли во вход, решает вызывающий по полям
  ответа. Номера полиса нет ни в тексте ошибки, ни в журнале сервиса.
- Ключ — ровно один: `external_id`, либо `number` — с `contract_external_id` или без него. `external_id` рядом с номером
  или договором — 400 по полю `external_id`, в том числе пустой `external_id=`; договор без номера или пустой номер (в
  том числе из пробелов) — 400 по недостающей части. Без договора ищется, только если параметра `contract_external_id`
  в запросе нет вовсе: номер вместе с пустым или пробельным `contract_external_id` — 400 по полю
  `contract_external_id`. Без ключа — 400 по полю `external_id` с причиной «нужен external_id либо number». Параметр
  `contract_id` (прежний ключ договора) в запросе по номеру или без ключа — 400 по полю `contract_id`, вместе с
  `external_id` — 400 по полю `external_id`: договор передаётся GUID'ом 1С. В адресе `/policies/{id}` лишние параметры не
  учитываются.

Пример 409 по номеру без договора:

```json
{
  "error": {
    "code": "AMBIGUOUS_POLICY",
    "message": "по номеру полиса найдено больше одной записи",
    "details": [
      {"policy_id": "…", "contract_external_id": "…"},
      {"policy_id": "…", "contract_external_id": "…"}
    ],
    "request_id": "…"
  }
}
```

```json
{
  "id": "…", "external_id": "…", "number": "26LM0000/000001",
  "last_name": "Тестов", "first_name": "Тест", "middle_name": "Тестович",
  "date_of_birth": "1990-01-01", "gender": "М",
  "email": "insured@example.com",
  "begin_date": "2026-01-01", "end_date": "2026-12-31",
  "availability": true,
  "is_archive": false,
  "personal_data_erased": false,
  "contract": {"id": "…", "external_id": "…", "number": "26 LM 0000"},
  "programs": [
    {
      "program": {"id": "…", "external_id": "…", "name": "Восстановительное лечение"},
      "limit_amount": 150000.00,
      "begin_date": "2026-01-01", "end_date": "2026-12-31",
      "availability": true,
      "services": [
        {"layer_number": 1, "copayment": 20.00,
         "begin_date": "2026-01-01", "end_date": "2026-12-31",
         "availability": true}
      ]
    }
  ]
}
```

Правила состава ответа:

- полис отдаётся и архивный, и закончившийся;
- `contract` — `null`, если договора страхования ещё нет в справочнике;
- `programs` — только программы РВЛ, которые есть в `programs` и не в архиве; условия обслуживания (`policy_services`)
  вложены в свою программу;
- лимит (`limit_amount`) и процент сооплаты (`copayment`) отдаются как есть: стоимость за период считает R-06, сооплату
  по лимиту и проценту — сервис Заявок;
- программы и условия отдаются со своими сроками и `availability`, без фильтра по дате: вызывающему бывает нужен и
  будущий период;
- паспортных данных нет: потока паспортных данных в 1С нет. Понадобятся ДУЛ — это отдельная ручка и отдельное
  согласование с ИБ, а не тихое расширение ответа;
- отношения к предприятию («работник / родственник») нет: в потоке полисов 1С (ТЗ-01) этого поля нет; связи
  застрахованных (ТЗ-11) в ответ полиса не входят — родственников застрахованного отдаёт R-10;
- могут быть `null`: `middle_name`, `gender`, `email`, `end_date` полиса и программы, `begin_date` и `end_date` строки
  условий обслуживания; ФИО и дата рождения — только у обезличенного полиса (ниже).

**Обезличенный полис (В-11).** ФИО, дата рождения и e-mail хранятся, пока полис действует, и ещё 30 суток после
окончания или перевода в архив; потом стираются. Такой полис отвечает 200: `last_name`, `first_name`, `middle_name`,
`date_of_birth`, `email` — `null`, `personal_data_erased: true`; номер, пол, даты, договор и программы — как были. 404
здесь не подходит: его не отличить от «полис ещё не пришёл из 1С». Поле `personal_data_erased` есть у каждого полиса и
отличает «стёрто» от «не было в 1С».

**Полис, который ещё не пришёл из 1С,** отвечает 404 `POLICY_NOT_FOUND`: сервис не знает, существует ли полис в 1С, и
честнее «не найден», чем выдуманный статус «в пути». Вызывающий, который ищет только что выпущенный полис, повторяет
запрос ограниченное число раз с паузой.

R-05д — проекция полиса без персональных данных, для сервиса Договоров:

```
GET /internal/v1/policies/{id}/contract-view
GET /internal/v1/policies/contract-view?external_id={uuid}
```

```json
{"id": "…", "external_id": "…", "number": "26LM0000/000001",
 "begin_date": "2026-01-01", "end_date": "2026-12-31", "is_archive": false}
```

Сервису Договоров нужны номер, GUID 1С и период; персональные данные ему не отдаются и из базы для этой ручки не
читаются. `end_date` может быть `null`. Вторым адресом Договоры находят наш `id` по GUID 1С после регистрации полиса; без `external_id` — 400.

Ошибки R-05 и R-05д: 400 — `id` или GUID не UUID, неверное сочетание ключей; 404 `POLICY_NOT_FOUND`; 409
`AMBIGUOUS_POLICY` (только по номеру). Ответы не кэшируются.

## R-06. Стоимость услуги за период

```
GET /internal/v1/services/{id}/price?date_from=2026-04-24&date_to=2026-05-05
```

| Параметр | Обяз. | Описание |
|---|---|---|
| `id` (путь) | да | внутренний `id` услуги — `services[].id` ответа R-03, не GUID 1С |
| `date_from` | да | дата заезда |
| `date_to` | да | дата выезда, не входит в период |

Считаем по периодам действия строк прайса и возвращаем разбивку плюс итог.

Алгоритм:

1. `date_to` позже `date_from`, иначе 400 по полю `date_to`. Ночей = `date_to − date_from`; день выезда не оплачивается.
   Ночей не больше 366, иначе 400 по полю `date_to` с причиной «не больше 366 ночей после date_from». Порядок дат
   проверяется раньше предела; обе проверки — до обращения к базе.
2. Услуга есть (иначе 404 `SERVICE_NOT_FOUND`); её ЛПУ не в архиве (иначе 404 `LPU_NOT_FOUND`); у ЛПУ однозначно
   определяется прайсовый договор (базовая логика B: 409 или 422); услуга не в архиве (иначе 404 `SERVICE_NOT_FOUND`);
   услуга относится к прайсовому договору (иначе 422 `NO_ACTIVE_PRICE_CONTRACT`: считать по ценам неактуального договора
   нельзя); ЛПУ отдаёт её в перечне R-03 (иначе 404 `SERVICE_NOT_FOUND`).
3. Для каждых суток периода ищем строку прайса, у которой `valid_from <= сутки` и (`valid_to` пуста или `>= сутки`). Нет
   ни одной — сутки идут в непокрытые; больше одной — 409 `AMBIGUOUS_PRICE` со сроками строк, и этот отказ важнее 422.
4. Подряд идущие сутки с одной и той же строкой прайса схлопываются в отрезок.
5. Есть хотя бы одни непокрытые сутки — 422 `PRICE_NOT_COVERED`, в `details` — непокрытые интервалы `{date_from,
   date_to}`. Частичный расчёт не отдаём: половина суммы хуже честного отказа.

```json
{
  "service": {"id": "…", "external_id": "…", "name": "Размещение в 2-местном номере"},
  "date_from": "2026-04-24", "date_to": "2026-05-05",
  "segments": [
    {"date_from": "2026-04-24", "date_to": "2026-05-01", "nights": 7,
     "price": 12000.00, "price_with_discount": 11400.00,
     "amount": 84000.00, "amount_with_discount": 79800.00},
    {"date_from": "2026-05-01", "date_to": "2026-05-05", "nights": 4,
     "price": 12600.00, "price_with_discount": null,
     "amount": 50400.00, "amount_with_discount": null}
  ],
  "total": {"nights": 11, "amount": 134400.00, "amount_with_discount": null, "basis": "BASE"}
}
```

**Две цены и основная сумма (В-6в).** У каждого отрезка и у итога две суммы: `amount` по `price` и
`amount_with_discount` по `price_with_discount`. Если хотя бы у одного отрезка скидочной цены нет, итоговый
`amount_with_discount` — `null`: складывать скидочные цены с обычными в одном итоге нельзя. Какая сумма основная для
сооплаты, говорит `total.basis`: `DISCOUNT`, когда скидочная цена есть у всех отрезков (тогда основная —
`amount_with_discount`), иначе `BASE` (основная — `amount`). ЛК HR не выводит это правило у себя.

Признак выгрузки договора в СОБ (`uploaded_to_sob`) для расчёта не требуется.

Возрастные цены (ребёнок на дополнительном месте дешевле взрослого) в данных 1С — отдельные позиции прейскуранта, а не
правило внутри одной, поэтому возраст в эту ручку не передаётся: нужную позицию выбирает вызывающий по списку из R-03.

## R-07. МКБ-10

```
GET /internal/v1/mkb10?query={text}&limit=20
GET /internal/v1/mkb10?codes=I25.1,Q06
```

Два режима одной ручки: подсказка по строке для поля ввода и перечень по кодам — второй раскрывает наименования сразу по
списку сохранённых ранее кодов. Нужен ровно один из параметров `query` или `codes`: оба вместе — 400 (сервис не угадывает
режим), ни одного — 400 «нужен query либо codes».

- `query` — подсказка среди неархивных кодов. Строка, которая начинается с латинской буквы и цифры (`J4`, `j45.0`),
  ищется как начало кода без учёта регистра; остальное — как часть наименования без учёта регистра. Пределы — в «Общих
  соглашениях»; `limit` — от 1 до 100, по умолчанию 20.
- `codes` — коды разом, включая архивные: старые заявки ссылаются на них, и показать их надо. Перечень — одним параметром
  через запятую (`codes=J45.0,I10`) или повтором параметра (`codes=J45.0&codes=I10`), смешивать нельзя. Регистр
  приводится, пустые элементы и повторы отбрасываются, неизвестные коды просто не попадают в ответ; перечень из одних
  пустых элементов — 400 по полю `codes`.

```json
{
  "items": [
    {"id": "…", "external_id": "…", "code": "I25.1", "name": "…",
     "hierarchy_level": 3, "parent_code": "I25", "is_archive": false}
  ]
}
```

Сортировка по `code`. `hierarchy_level` и `parent_code` могут быть `null`.

Параметров `lpu_id` и `include_children` (показания конкретного ЛПУ) нет: таблицы показаний ЛПУ в потоках 1С нет (В-8).
Переданные, они не действуют: выдача та же, что без них, а не отказ.

«Направление лечения» вместо названия диагноза — не данные справочника: источника в 1С нет. Если направление нужно ЛК
застрахованного, его источник — сервис Заявок.

## R-08. Договор страхования и страхователь

```
GET /internal/v1/insurance-contracts/{id}
GET /internal/v1/insurance-contracts?external_id={uuid}
GET /internal/v1/insurance-contracts?insurer_external_id={uuid}
```

Три способа найти договор:

- по внутреннему `id` — для сервиса Договоров, который хранит наш `id`; откуда взять: `id` ответа по GUID, `contract.id`
  полиса R-05;
- по `external_id` — договор по его GUID в 1С:УСК;
- по `insurer_external_id` — единственный договор страхователя, действующий сегодня по общему правилу (В-13). Это путь
  сервиса Заявок: кадровик входит через B2B-портал, `companyId` из его токена — GUID страхователя в 1С:УСК. `id` ответа
  Заявки хранят как `insurance_contract_id`, `external_id` передают в R-01 и R-04.

```json
{
  "id": "…", "external_id": "…", "number": "26 LM 0000",
  "begin_date": "2026-01-01", "end_date": "2026-12-31",
  "is_archive": false,
  "insurer": {
    "id": "…", "external_id": "…",
    "name": "ООО «Пример»", "full_name": "Общество с ограниченной ответственностью «Пример»",
    "inn": "7700000000", "kpp": "770001001"
  }
}
```

Правила:

- по `id` и `external_id` договор отдаётся и архивный, и закончившийся (`is_archive = true` у архивного) — чтобы старые
  заявки было чем отрисовать; по `insurer_external_id` — только действующий;
- технических полей (дата загрузки, время изменения) нет; даты заключения договора нет — в потоке договоров страхования
  1С (ТЗ-02) её нет (В-8);
- `insurer` — `null`, если страхователя нет в справочнике (ещё не пришёл из 1С или физлицо, которое не хранится). Связь
  со страхователем — по GUID 1С, без внешнего ключа. Это штатный случай, договор отдаётся;
- `end_date`, `insurer.full_name`, `insurer.inn`, `insurer.kpp` могут быть `null`.

По `insurer_external_id`: действующего договора нет (страхователь неизвестен, без договоров, все недействующие) — 404
`INSURANCE_CONTRACT_NOT_FOUND`; действующих два и больше — 409 `AMBIGUOUS_INSURANCE_CONTRACT`, в `details` по объекту
`{"insurance_contract_id": …}` на кандидата, порядок не задан. Договор не угадывается: два одновременно действующих
договора одного страхователя — ошибка данных 1С, а «самый новый» молча привязал бы заявки к не тому договору.
Недействующие договоры в кандидаты не входят.

Ключи `external_id` и `insurer_external_id` взаимоисключающие: оба вместе (в том числе один из них пустой) — 400 по полю
`external_id` с причиной «external_id не передаётся вместе с insurer_external_id»; без ключа — 400 по полю `external_id`
с причиной «нужен external_id либо insurer_external_id»; нечитаемый GUID или пустой параметр — 400 по своему полю.

Ошибки: 400; 404 `INSURANCE_CONTRACT_NOT_FOUND`; 409 `AMBIGUOUS_INSURANCE_CONTRACT` (только по `insurer_external_id`).

## R-09. Страховая программа

```
GET /internal/v1/programs/{id}
```

Программа страхования с перечнем учреждений — для сервиса Договоров (печатная форма договора и сообщение в 1С:УСК).
`{id}` — внутренний `id` программы: `programs[].program.id` в полисе R-05; сервис Заявок передаёт его сервису Договоров
как `program_id`. Ручки программы по GUID 1С нет.

```json
{
  "id": "…", "external_id": "…", "name": "Восстановительное лечение",
  "type_programm": "…",
  "is_archive": false,
  "services": [
    {"lpu_id": "…", "lpu_external_id": "…", "lpu_name": "Санаторий «Пример»",
     "appeal_type_external_id": "…",
     "begin_date": "2026-01-01", "end_date": null,
     "layer_number": 1, "direct_attachment": false,
     "percent_copayment": 0.00, "coverage_type": "R"}
  ]
}
```

- Программа отдаётся и архивная (`is_archive = true`).
- `services` — строки перечня учреждений программы с условиями: `coverage_type` — `R` (рисковая часть) или `D`
  (депозитная), `direct_attachment` — прямое прикрепление, `percent_copayment` — процент сооплаты. `type_programm`,
  `appeal_type_external_id`, `begin_date`, `end_date` могут быть `null`.
- Порядок `services` устойчивый (В-12): перечень идёт в печатную форму, и два чтения одной программы не должны давать
  разный документ. По наименованию учреждения; одинаковые наименования — по GUID учреждения в 1С; строки одного
  учреждения — по слою, дате начала (строка без начала — первой), виду обращения (строка без вида — последней), дате
  окончания (открытая — последней), затем депозитная часть (`D`) раньше рисковой (`R`), без прямого прикрепления раньше,
  меньший процент сооплаты раньше. Наименования сравнивает база — так же, как в каталоге R-01.

Ошибки: 400 — `id` не UUID; 404 `PROGRAM_NOT_FOUND`.

## R-10. Родственники застрахованного

Застрахованные родственники застрахованного, для кабинета застрахованного в сервисе Заявок (В-15).

```
GET /internal/v1/policies/{id}/family
GET /internal/v1/policies/{id}/family?number={number}
```

`{id}` — внутренний `id` полиса застрахованного, как в R-05 (`/internal/v1/policies/{id}`); не UUID — 400 по полю `id`,
полиса нет — 404 `POLICY_NOT_FOUND`.

```json
{
  "items": [
    {
      "id": "…", "external_id": "…", "number": "26LM0000/000002",
      "last_name": "Тестова", "first_name": "Проба", "middle_name": "Тестовна",
      "date_of_birth": "2015-01-01", "gender": "Ж",
      "relationship": "797093be-2c51-11e8-8123-005056b43f21"
    }
  ]
}
```

Правила:

- источник — связи застрахованных из 1С (ТЗ-11), где этот полис — застрахованный (`idInsured`); обратные связи
  (полис — связанный, `otherSide`) и связь полиса с самим собой не отдаются;
- связь действует сегодня (московский день), если её покрывает хотя бы одна запись регистра 1С: начало не позже
  сегодня, окончание пустое (открытая дата 1С) или не раньше сегодня — оба дня включительно, по всем записям, без среза
  последних;
- полис родственника отдаётся, только если он действует сегодня по общему правилу: не в архиве, `begin_date ≤ сегодня`,
  `end_date` пустая или `≥ сегодня`. Архивный, закончившийся и ещё не начавшийся полис родственника не отдаётся;
  поэтому полисы со стёртыми по сроку персональными данными в ответ не попадают;
- полис самого застрахованного не отбирается: родственники отдаются и когда он в архиве, закончился или ещё не начался;
- один элемент на полис родственника: `id` — наш id его полиса (по нему R-05 отдаёт полис целиком); тип связи в поле `relationship` — GUID 1С
  как есть, если у полиса сегодня один действующий тип связи (перекрывающиеся записи одного типа — один тип), и `null`,
  если их несколько. Наименование типа сервис Заявок получает у 1С, сопоставления с кодами заявки в сервисе нет;
- пол — как в 1С (`М`, `Ж`); договора, программ, сроков, e-mail и признаков в элементе нет;
- связь, полиса родственника по которой нет в справочнике, не отдаётся: родственников без полиса в потоке 1С нет, сервис
  Заявок добавляет их сам;
- порядок — по номеру полиса родственника, затем по GUID полиса (строки сравниваются по кодам символов, не по
  алфавиту);
- связей нет — 200 и `{"items": []}`; предела размера нет: состав семьи — единицы записей.

**Поиск по номеру** (`?number=`) — среди тех же родственников: найден — один элемент того же вида, без обёртки
`items`; не найден, в том числе номер чужого полиса или самого застрахованного, — 404 `POLICY_NOT_FOUND`; два
родственника с таким номером (номер уникален только в договоре) — 409 `AMBIGUOUS_POLICY` с `{"policy_id"}` кандидатов в
`details`; пустой `number=` — 400 по полю `number` («обязательный параметр»).

Ответ не кэшируется: в нём персональные данные, и он участвует в решении по заявке. Запросов к базе — постоянное число,
сколько бы родственников ни было.

## Кэширование, индексы и нагрузка

R-01 проходит цепочку «договор → полисы → условия обслуживания → программы → перечень → ЛПУ → договоры ЛПУ». На договоре в
десятки тысяч полисов это дорого, но результат одинаков для всех пользователей договора и меняется только после сообщения
из 1С — поэтому ответы справочника кэшируются в памяти сервиса (В-10).

| Ответ | Ключ | Сбрасывают сообщения 1С |
|---|---|---|
| R-01 | московский день, договор | договоры страхования, полисы, программы, контрагенты, договоры ЛПУ, виды обращения, контактная информация |
| R-02 | московский день, ЛПУ | контрагенты, договоры ЛПУ, контактная информация |
| R-03 без цен | московский день, ЛПУ | контрагенты, договоры ЛПУ, виды обращения, услуги контрагентов |
| R-03 с ценами | московский день, ЛПУ | то же и прейскуранты |
| R-06 | московский день, услуга, период | контрагенты, договоры ЛПУ, виды обращения, услуги контрагентов, прейскуранты |
| R-07 подсказка и перечень кодов | строка поиска и `limit` либо перечень кодов | МКБ-10 |
| R-08 по `id` и по `external_id` | ключ запроса | договоры страхования, контрагенты |
| R-08 по `insurer_external_id` | московский день, GUID страхователя | договоры страхования, контрагенты |
| R-09 | программа | программы, контрагенты |

- Срок жизни записи — 10 минут, не больше 1000 записей на каждый кэш (настройки сервиса).
- Дата в ключе обязательна там, где ответ зависит от «сегодня»: без неё кэш переживёт полночь и отдаст вчерашние договоры
  как действующие.
- Сброс — по потоку: применённое или пропущенное сообщение 1С сразу после фиксации разбора сбрасывает кэши, которые от
  этого потока зависят, на всех экземплярах сервиса. Данные из 1С видны сразу; срок жизни — страховка на случай правки
  базы мимо 1С, а не основной механизм.
- Допустимая устарелость для потребителей — до 10 минут: правка базы мимо 1С и узкое окно, когда чтение совпало с
  фиксацией разбора.
- Отказы (404, 409, 422, 503) не кэшируются. При недоступной базе ответ из кэша отдаётся.
- **Не кэшируются** R-04, R-05, R-05д и R-10: подсказка, карточка и родственники с персональными данными участвуют в
  решениях, нужна свежесть.
  R-04 по самому запросу не кэшировался бы и так — вариантов строки слишком много.
- Справочник видов обращения не кэшируется: он маленький, запрос дешёвый.

**Индексы.** Индексы заданы миграциями сервиса под реальные запросы. Индексы по ссылкам заведены вместе с таблицами
(договор полиса, договор страхователя, договор ЛПУ, услуги договора ЛПУ, строки прайса услуги, перечень программы);
сверх них под запросы REST добавлены:

```sql
CREATE INDEX idx_program_lpu_program ON program_lpu (program_id);
CREATE INDEX idx_lpu_contracts_active ON lpu_contracts (lpu_id, end_date) WHERE is_archive = false;
CREATE INDEX idx_policy_services_program ON policy_services (external_program_id, policy_id) WHERE availability = true;
CREATE INDEX idx_policies_number_trgm ON policies USING gin (lower(number) gin_trgm_ops) WHERE is_archive = false;
CREATE INDEX idx_policies_number ON policies (number);
CREATE INDEX idx_mkb10_code_prefix ON mkb10 (upper(code) text_pattern_ops) WHERE is_archive = false;
CREATE INDEX idx_mkb10_name_trgm ON mkb10 USING gin (lower(name) gin_trgm_ops) WHERE is_archive = false;
```

В частичных индексах нельзя использовать `CURRENT_DATE` — функция не `IMMUTABLE`, PostgreSQL такой индекс не создаст.
Поэтому в условие индекса идут только `is_archive` и `availability`, а дата приходит параметром запроса. Для
`gin_trgm_ops` нужно расширение `pg_trgm`. Обычный индекс по `number` — под R-05 по номеру без договора: сравнение точное, по всем полисам
вместе с архивными, и триграммный индекс поиска R-04 (по `lower(number)`, только неархивные) ему не подходит. Перечень индексов в «Структуре БД» устарел; источник — миграции сервиса.

## Пробы и прогрев

Пробы Kubernetes — на порту API, от базы и брокера не зависят:

- `GET /livez` — 200, как только приложение запущено;
- `GET /readyz` — 200 только после прогрева, до этого 503 со статусом `OUT_OF_SERVICE`.

Прогрев после старта читает собственные ручки по первым записям справочников (договоры страхования, ЛПУ, программы,
полисы), чтобы первый запрос потребителя после развёртывания не собирал всю цепочку на себя. Прогрев ограничен 30 с;
прерванный прогрев (например, база недоступна) готовности не мешает. В теле ответа проб — только поле `status`: `UP`
или, во время прогрева, `OUT_OF_SERVICE`.
