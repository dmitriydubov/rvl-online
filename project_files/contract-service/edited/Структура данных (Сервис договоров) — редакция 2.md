Действующая структура данных сервиса Договоров — по схеме базы сервиса; первая редакция документа — без даты.

Документ описывает структуру данных сервиса Договоров: выпуск договоров КМ и полисов ЛМ, хранение ссылок на печатные формы 1С:УСК, справок 070/у и согласий на обработку персональных данных, фиксацию акцепта оферты и взаимодействие с Ordering Service. Формат сообщений обмена описан в ТЗ «Точки интеграции Заявки — Договоры».

## Схема данных

### Область и границы

В границах документа

- Перечень таблиц сервиса Договоров, состав полей, индексы и связи.
- Перечисления, реализуемые нативными типами PostgreSQL.
- Таблицы интеграции: Outbox, Inbox, карантин входящих сообщений и блокировка ведущего экземпляра.

Вне границ документа

- Оплата как процесс и фискализация — выполняются в Ordering Service.
- Справка 070/у и согласие на обработку персональных данных как документы сервиса Заявок; сервис Договоров хранит их файлы в S3 контура и ведёт реестр в contract_documents.
- Справочники: программы страхования, полисы, договоры страхования, услуги прейскуранта — читаются из Дата-референса.
- Возвраты — на первом этапе выполняются вручную вне системы.
- Контракты обмена — в ТЗ «Точки интеграции Заявки — Договоры».

### Принятые ограничения

| **№** | **Ограничение** |
|---|---|
| 1 | Сервис Договоров — бэкенд без пользовательского интерфейса. С фронтом и БФФ он не взаимодействует. Единственный собеседник внутри контура РВЛ ОНЛАЙН — сервис Заявок. |
| 2 | Выпускаемый документ определяется участником и наличием доплаты: застрахованное лицо без доплаты — ничего не выпускается, застрахованное лицо с доплатой — договор КМ, родственник без доплаты — полис ЛМ по корпоративному договору, родственник с доплатой — договор КМ. Доплата есть при amount_due от 0.01. |
| 3 | Страхователем по договору КМ всегда выступает застрахованное лицо по корпоративному договору. Застрахованным может быть как оно само, так и родственник. |
| 4 | Номер договора КМ присваивается в сервисе Договоров при создании записи. Обмен с 1С:УСК выполняется в один раунд. |
| 5 | Печатные формы договора КМ и полисов формирует 1С:УСК; обратно приходят постоянные ссылки, сервис хранит только их. Справки 070/у участников и согласия родственников на обработку персональных данных сервис хранит в общем файловом хранилище S3 сервисов РВЛ и 1С:УСК; в 1С:УСК вместе с оплаченным договором передаются ссылки только на не удалённые справки 070/у. |
| 6 | Источник персональных данных — сервис Заявок. Они приходят в теле сообщения ДГ-01, а e-mail плательщика — в акцепте (СЭ-03): он хранится в заказе на оплату, только пока счёт не выставлен. Сервис Договоров хранит снимок сторон договора; до акцепта снимок обновляется вслед за задачей на выпуск, после акцепта — не обновляется, поскольку договор должен соответствовать акцептованным данным. |
| 7 | Даты договора равны датам поездки; до акцепта они обновляются вслед за задачей, после акцепта — не меняются. |
| 8 | Акцепт оферты выполняется проставлением отметки в личном кабинете. Факт акцепта фиксируется в базе данных с привязкой к версии договора (entity_version). |
| 9 | Все идентификаторы сущностей — GUID (UUID; записи сервиса получают UUID v7 — упорядоченный для индексов). |
| 10 | Идентификаторы объектов сервиса Заявок (индивидуальная заявка, участник, член семьи) хранятся значением. Внешние ключи между базами данных разных сервисов не устанавливаются — в том числе на справочники Дата-референса. |

### contracts — договор КМ

Одна запись на участника поездки, у которого amount_due больше нуля, среди незавершённых (не ISSUED, ERROR, CANCELLED). Договор выпускается однократно, после прохождения согласований и фиксации сумм.

|---|---|---|---|
| id | UUID | Да | Первичный ключ. Сквозной идентификатор объекта в интеграции |
| number | VARCHAR(50) | Да | Номер договора КМ, уникален. Присваивается в сервисе Договоров при создании записи в формате DKM-ГГГГ-NNNNNN (латиница, год и счёт — по часовому поясу контура) |
| status | contract_status | Да | Статус договора. Перечень значений — в п. 9 |
| individual_request_id | UUID | Да | Идентификатор индивидуальной заявки в сервисе Заявок |
| insured_participant_id | UUID | Да | Идентификатор участника-застрахованного в сервисе Заявок |
| policyholder_participant_id | UUID | Да | Идентификатор участника-страхователя. Всегда застрахованное лицо по корпоративному договору. Может совпадать с insured_participant_id |
| insurance_contract_id | UUID | Да | Идентификатор Дата-референса (insurance_contracts.id). Корпоративный договор страхования |
| insurer_policy_id | UUID | Да | Идентификатор Дата-референса (policies.id). Полис страхователя по корпоративному договору. Передаётся в 1С:УСК для связи |
| program_id | UUID | Нет | Идентификатор Дата-референса (insurance_programs.id). Программа страхования участника из ДГ-01 |
| date_from | DATE | Да | Дата начала действия договора. Равна дате заезда |

| insured_amount | NUMERIC(15,2) | Нет | Страховая сумма — размер страхового покрытия. Источник значения не определён, ОВД-01; сейчас не заполняется |

| issued_policy_id | UUID | Нет | Идентификатор Дата-референса (policies.id). Полис, выпущенный по договору. Заполняется по результату регистрации в 1С:УСК (ДГ-05; найден по external_id полиса), возвращается в сервис Заявок |
| issued_policy_number | VARCHAR(50) | Нет | Номер выпущенного полиса |
| contract_usk_id | UUID | Нет | Идентификатор документа в 1С:УСК. Первоначально не заполняется |
| contract_usk_number | VARCHAR(50) | Нет | Номер документа в 1С:УСК |
| paid_at | TIMESTAMPTZ | Нет | Дата и время поступления оплаты по данным Ordering Service: поле updated события об оплате, а если оплату нашла сверка заказов, — момент события оплаты из истории заказа (нет его — момент сверки). Записывается при переходе договора в PAID и передаётся в 1С:УСК в ДГ-04. При оплате после прекращения работы по договору не записывается: момент оплаты остаётся только в payment_invoices.paid_at |

Страховая сумма и страховая премия — разные величины: премия равна сумме доплаты застрахованного, страховая сумма описывает объём покрытия по программе.

### contract_number_counters — счётчик номеров

Одна строка на год: last_number — последний выданный номер. Номер договора — DKM-&lt;год&gt;-&lt;last_number + 1, шесть цифр&gt;; год — по часовому поясу контура (по умолчанию московскому) на момент создания договора. Номер не переиспользуется: новая запись после ошибки или прекращения получает новый номер.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| year | INT | Да | Год, первичный ключ |
| last_number | INT | Да | Последний выданный номер в году |

### contract_documents — документы

В таблице два семейства записей. Печатные формы 1С:УСК (договор, полис, приложение) — финальные, только ссылкой: файл хранит 1С:УСК. Загружаемые вложения из сервиса Заявок — справки 070/у участников (по индивидуальной заявке и участнику, в том числе принятые до прихода задачи ДГ-01) и согласия родственников на обработку персональных данных (по полису и члену семьи): файл в S3 контура, запись — реестр (ключ объекта, хэш, тип, размер, при мягком удалении — отметка и X-Request-Id). Проектов печатных форм нет.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ |
| contract_id | UUID | Условно | FK contracts.id. Заполняется для печатных форм по договору КМ |
| lm_policy_id | UUID | Условно | FK lm_policies.id. Заполняется для печатных форм по полису ЛМ |
| individual_request_id | UUID | Условно | Индивидуальная заявка в сервисе Заявок (без FK на issuance_requests: справка может быть принята до первой задачи на выпуск). Заполняется для справки 070/у |
| participant_id | UUID | Условно | Участник заявки. Заполняется для справки 070/у |
| policy_id | UUID | Условно | Идентификатор полиса (логическая ссылка на policies.id Дата-референса). Заполняется для согласия на обработку персональных данных |
| family_member_id | UUID | Условно | Член семьи в сервисе Заявок. Заполняется для согласия на обработку персональных данных |
| attachment_id | UUID | Условно | Идентификатор вложения в сервисе Заявок, глобально уникален. Заполняется для справки и согласия; ключ идемпотентности загрузки |
| kind | printed_form_kind | Да | DRAFT — проект, FINAL — финальный документ; сейчас всегда FINAL |
| doc_type | printed_form_type | Да | Тип документа: договор, полис, приложение, справка 070/у, согласие на обработку персональных данных |
| version | INT | Да | Версия документа; сейчас всегда 1 |
| file_key | TEXT | Условно | Ключ объекта в общем файловом хранилище S3: &lt;ИНН&gt;\_&lt;КПП&gt;/&lt;базовый путь&gt;/&lt;uuid&gt;/&lt;attachment_id&gt;.&lt;расширение&gt; (у справок, принятых до 27.10.2026, — без префикса &lt;ИНН&gt;\_&lt;КПП&gt;). Обязателен для справки и согласия. Ссылка в ДГ-04 (только для не удалённых справок 070/у) — /&lt;бакет&gt;/&lt;file_key&gt; |
| file_hash | VARCHAR(64) | Условно | SHA-256 содержимого файла. Обязателен для справки и согласия: по нему повторная загрузка отличается от конфликтующей |
| file_size | BIGINT | Нет | Размер файла в байтах; обязателен для справки и согласия, у формы 1С:УСК — как прислала 1С:УСК |
| content_type | VARCHAR(100) | Условно | MIME-тип файла. Для справки и согласия — image/jpeg, image/png или application/pdf |
| usk_file_url | TEXT | Нет | Постоянная ссылка на документ, полученная из 1С:УСК. Заполняется для печатных форм 1С:УСК |
| deleted_at | TIMESTAMPTZ | Нет | Момент мягкого удаления вложения (заполняется только у справки или согласия вместе с deleted_request_id; у печатных форм 1С:УСК всегда пуст) |
| deleted_request_id | VARCHAR(64) | Нет | Непустой X-Request-Id вызова мягкого удаления вложения; заполнен тогда и только тогда, когда заполнен deleted_at |
| created_at | TIMESTAMPTZ | Да | Дата и время записи |

Ограничения: ровно одно из полей contract_id, lm_policy_id, individual_request_id и policy_id должно быть заполнено (ck_contract_documents_single_owner); у печатных форм 1С:УСК (CONTRACT, POLICY, APPENDIX) поля вложения и deleted_at пусты, у MEDICAL_CERTIFICATE заполнены individual_request_id, participant_id и attachment_id при пустых policy_id и family_member_id, у PD_CONSENT заполнены policy_id, family_member_id и attachment_id при пустых individual_request_id и participant_id (ck_contract_documents_attachment_owner); у вложения обязательны file_key, file_hash, file_size, content_type; deleted_at и непустой deleted_request_id заполняются только вместе (ck_contract_documents_deletion). Индексы: по contract_id; по lm_policy_id; составной по (contract_id, doc_type, kind, version); UQ по attachment_id; по (individual_request_id, participant_id); по (policy_id, family_member_id) (ix_contract_documents_consent).

Ссылки из 1С:УСК постоянные, срок действия не ограничен. Поле expires_at, в отличие от гарантийных писем сервиса Заявок, не требуется.

Имя файла вложения не хранится; объект в S3 лежит под уникальной папкой {uuid}/ внутри базового пути (требование администраторов хранилища), путь начинается с ИНН и КПП организации (настройки), загрузка с другим attachment_id создаёт новый объект. При мягком удалении вложения (СЭ-07) объект физически удаляется из S3 до проставления deleted_at и deleted_request_id в contract_documents; объекты без записи в базе, оставшиеся после прерванной загрузки, чистит политика жизненного цикла бакета.

### contract_acceptances — акцепт оферты

Договор КМ заключается акцептом оферты: застрахованное лицо знакомится с данными договора и проставляет отметку в личном кабинете. Запись об акцепте неизменяема и хранит привязку к версии договора.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| id | UUID | Да | Первичный ключ |

### contract_persons — стороны договора

### payment_orders — заказы на оплату

Оплата выполняется в Ordering Service. Сервис Договоров создаёт там заказ на оплату акцептованного договора КМ: передаёт номер договора, сумму и даты документа, подтверждает документ, а при прекращении договора без счёта (выставление счёта не начато или Ordering Service в счёте отказал) отменяет заказ; заказ отменяется и тогда, когда выставление счёта, начатое до прекращения, так и не дало счёта. Заказ договора с выставленным счётом при прекращении не отменяется — Ordering Service не отменяет заказ после выставления счёта; заказ оплаченного договора — тоже. Фискализация и эквайринг находятся на стороне Ordering Service и в настоящем документе не описываются; возвраты на первом этапе выполняются вручную. Счёт, ссылка на оплату, срок и итог оплаты — в payment_invoices.

Запись одна на договор. Она создаётся в одной транзакции с акцептом (СЭ-03), если оплата включена настройкой сервиса; сам заказ в Ordering Service создаёт фоновый процесс сервиса. Договор, акцептованный при выключенной оплате, записи не получает и после включения. Номер договора, сумма, дата документа и срок жизни документа — снимок на момент акцепта и дальше не меняются. Персональные данные в таблице — только payer_email: e-mail плательщика нужен для счёта и стирается, когда счёт выставлен (в том числе без ответа Ordering Service), договор оплачен или прекращён (в том числе по сроку оплаты). Если Ordering Service отказал в создании заказа или в счёте, адрес хранится, пока договор не прекращён (при отказе в счёте дежурный может стереть его вручную и раньше): он нужен, чтобы вернуть заказ в работу.

### payment_invoices — счёт по заказу

Запись заводится в той же транзакции, в которой записывается полученный идентификатор заказа Ordering Service; одна на заказ и на договор. Если дежурный вернул в работу отклонённый заказ, у которого запись уже была, второй записи нет: прежняя продолжается, подтверждение документа начинается сначала. У заказа, не созданного в Ordering Service, записи нет. Запись ведёт подтверждение документа, выставление счёта (отметка «счёт начат», срок оплаты, идентификатор счёта и ссылка на оплату), итог оплаты и отложенное прекращение договора со счётом. Договор считается договором со счётом, когда счёт в состоянии CHECKOUT, ISSUED или PAYMENT_ERROR. Персональных данных нет, кроме свободного комментария отложенного прекращения (deferred_cancel_comment) — он того же рода, что cancel_comment договора, и хранится, пока прекращение не применено или не снято.

Отложенное прекращение. Причина, комментарий и момент пишутся сюда, когда работу по договору со счётом прекращают (ДГ-02, исключение участника, смена вида документа); статус договора не меняется, а в ДГ-03 и СЭ-01 договор показывается прекращённым. При просрочке оплаты они переносятся в договор (contracts.cancel_reason, cancel_comment, cancelled_at), и договор переходит в CANCELLED; так же — сразу, если Ordering Service отказал в счёте или выставление счёта, начатое до прекращения, так и не дало счёта; в этих двух случаях заказ на оплату уходит в отмену (CANCEL_PENDING). Задача сервиса Заявок с большей версией, в которой участнику снова выпускается договор КМ, отложенное прекращение снимает. Если по такому договору поступила оплата, отложенное прекращение тоже снимается, а договор переходит в ERROR с кодом KM_CONTRACT_PAID_AFTER_CANCELLATION.

## Перечисления (native enum)

Все перечисления реализуются нативными типами PostgreSQL через CREATE TYPE ... AS ENUM.

| **Тип** | **Значения** |

## Таблицы интеграции

Реализуют паттерны Outbox и Inbox по тем же правилам, что приняты в сервисе Заявок. Запись в outbox_messages выполняется в одной транзакции с изменением данных, публикация — отдельным процессом. Входящее сообщение сначала сохраняется в inbox_messages, затем обрабатывается; повторная доставка с тем же message_id отсекается по уникальному индексу.

### leader_lock

Фоновую работу — приём из очередей, разбор журнала входящих, публикацию исходящих, запросы в 1С:УСК и проходы по расписанию — выполняет один экземпляр сервиса, ведущий: тот, кто держит строку этой таблицы. Остальные экземпляры отвечают на синхронные вызовы. Строку ведёт библиотека Spring Integration (JdbcLockRegistry), состав колонок и ключ — как в её схеме для PostgreSQL; транзакции фоновой работы читают строку с блокировкой FOR SHARE, чтобы экземпляр, потерявший роль, не дописал начатое.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| lock_key | CHAR(36) | Да | Ключ блокировки: UUID, полученный из имени роли |
| region | VARCHAR(100) | Да | Группа экземпляров — имя сервиса |
| client_id | CHAR(36) | Нет | Идентификатор экземпляра, который держит роль; новый при каждом запуске |
| created_date | TIMESTAMP | Да | Когда экземпляр взял строку (UTC) |
| expired_after | TIMESTAMP | Да | Срок, после которого строку может забрать другой экземпляр (UTC, по часам экземпляра); ведущий продлевает его раз в секунду, после его гибели роль переходит через срок блокировки (по умолчанию 30 секунд) |

Индексы: первичный ключ leader_lock_pk по (lock_key, region).
