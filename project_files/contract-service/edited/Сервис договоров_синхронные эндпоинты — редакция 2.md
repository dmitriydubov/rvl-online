# Сервис Договоров. Синхронные эндпоинты

Редакция 2 от 22.10.2026, дополнена 26.10.2026: СЭ-01 по договору КМ после оплаты, передачи в 1С:УСК и выпуска; дополнена 09.11.2026: обращение к Ordering Service описано по реализации — заказ на оплату акцептованного договора КМ, подтверждение документа и отмена заказа; акцепт (СЭ-03) к Ordering Service не обращается; дополнена 11.11.2026: по реализации описаны счёт со сроком оплаты и ссылкой на оплату, события Ordering Service об оплате и сверка заказов с Ordering Service; в акцепте (СЭ-03) — e-mail плательщика, в состоянии пакета (СЭ-01) — ссылка и срок оплаты; дополнена 26.11.2026: загрузка справки 070/у (СЭ-04) принимается до прихода задачи ДГ-01 без 404 по заявке и участнику, добавлена синхронная загрузка согласий родственников на обработку персональных данных (СЭ-05), уточнена проверка атрибута filename частей multipart-запроса; дополнена 28.11.2026: добавлены потоковая выдача содержимого вложения (СЭ-06) и двухфазное мягкое удаление вложения (СЭ-07) с защитой справок, переданных в 1С:УСК (409 ATTACHMENT_LOCKED). Действующее описание синхронной части обмена сервиса Договоров; первая редакция документа — без даты. В редакцию перенесены и правки 2026-10-05 к разделу о чтении справочников Дата-референса, сверенные с кодом сервиса.

Документ описывает синхронную часть обмена сервиса Договоров: эндпоинты, которые он предоставляет сервису Заявок, чтение справочников Дата-референса и обращение к Ordering Service. Асинхронные точки ДГ-01…ДГ-07 описаны в ТЗ «Точки интеграции Заявки — Договоры» и здесь не повторяются.

Разделение простое: асинхронно передаются команды, меняющие состояние объекта, вместе со всеми данными для их выполнения. Синхронно выполняются чтение, загрузка, скачивание и удаление вложений (справок и согласий) и действия пользователя, результат которых нужен в момент отрисовки интерфейса.

## Общие положения

### Контур и маршрутизация

Сервис Договоров не имеет внешнего контура. Обращения к нему выполняет только сервис Заявок. Фронтенд и BFF доступа к нему не имеют: всё, что застрахованное лицо видит по договору и оплате, проходит через сервис Заявок, который проксирует вызов и возвращает ответ без изменения смысла.

Эндпоинты размещены под префиксом /internal и на внешнем периметре не публикуются. Ограничение доступа обеспечивается сетевая политика контура; межсервисной аутентификации нет.

### Общие правила

| **Параметр** | **Значение** |
|---|---|
| Базовый путь | https://{contracts-service}/internal/v1 |
| Версионирование | В пути: /v1. Несовместимые изменения выпускаются новой версией, старая поддерживается до перевода потребителя |
| Формат | JSON, UTF-8, имена полей в snake_case. Исключения — загрузка вложений (СЭ-04, СЭ-05: запрос multipart/form-data, ответ JSON), выдача содержимого вложения (СЭ-06: ответ 200 — поток байтов файла, ответ 304 — без тела, ошибки — JSON) и удаление вложения (СЭ-07: ответ 204 — без тела, ошибки — JSON) |
| Даты | ISO 8601 с часовым поясом; моменты в ответах сервис Договоров пишет в UTC с Z, доли секунды — только если они есть, тремя, шестью или девятью знаками (например, 2026-02-13T07:05:00.123456Z); даты без времени — yyyy-mm-dd |
| Суммы | Число с двумя знаками после запятой, валюта RUB |
| Идентификаторы | GUID (UUID; записи сервиса Договоров получают UUID v7, на версию UUID клиент не полагается) |
| Аутентификация | Нет: доступ ограничивает сетевая политика контура |
| Трассировка | Заголовок X-Request-Id передаётся сквозняком и возвращается в ответе и в теле ошибки. Принимается значение из 1–64 знаков A–Z a–z 0–9 . _ -; другое или отсутствующее заменяется новым UUID, оно и возвращается |
| Таймаут вызова | 5 секунд для чтения состояния; для приёма акцепта — больше 5 секунд: договор, занятый обработкой задачи, сервис ждёт до таймаута блокировки базы (по умолчанию 5 с) и отвечает 503; для загрузки, чтения содержимого и удаления вложения (СЭ-04, СЭ-05, СЭ-06, СЭ-07) — больше 20 секунд (общий таймаут вызова хранилища по умолчанию; при удалении справки ожидание блокировки договора ограничено теми же 5 с) |
| Повторы | Допустимы для GET и идемпотентного DELETE вложения (СЭ-07). POST повторяется исключительно с тем же ключом идемпотентности: у загрузки справки и согласия — attachment_id, у акцепта — договор и contract_version. На 503 — повторить тот же запрос позже |

### Коды ответов

| **Код** | **Когда возвращается** |
|---|---|
| 200 OK | Запрос выполнен |
| 204 No Content | Вложение удалено (либо уже отсутствовало или было помечено удалённым ранее) |
| 304 Not Modified | Содержимое вложения не изменилось (совпал условный заголовок If-None-Match в СЭ-06) |
| 400 Bad Request | Нарушен формат запроса: неверный тип, отсутствует обязательное поле |
| 401 Unauthorized | Не используется |
| 403 Forbidden | Не используется |
| 404 Not Found | Объект с переданным идентификатором отсутствует (либо вложение помечено удалённым) |
| 409 Conflict | Состояние объекта не допускает операцию: договор уже акцептован, передана устаревшая версия договора, работа по заявке прекращена, вложение уже принято с другим содержимым, владельцем или видом либо помечено удалённым, медицинская справка заблокирована передачей договора КМ в 1С:УСК |
| 422 Unprocessable Entity | Не используется |
| 500 Internal Server Error | Внутренняя ошибка сервиса |
| 503 Service Unavailable | Сервис временно недоступен либо недоступен внешний контрагент (хранилище файлов); договор занят другой операцией |

### Формат ошибки

Единый для всех эндпоинтов. Текст message предназначен для журнала, а не для показа пользователю: решение о том, что показать застрахованному лицу, принимает сервис Заявок.

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| error.code | string | Да | Машиночитаемый код ошибки из перечня в п. 5 |
| error.message | string | Да | Описание на русском языке |
| error.details | array | Да (может быть пустым) | Перечень нарушений по полям: field, reason . reason — «обязательное поле не передано», «неверный формат», для файла — «тип файла не допускается», «размер файла вне допустимого», «размер файла больше допустимого»; у DOCUMENT_VERSION_MISMATCH — «актуальная версия договора — N» |
| error.request_id | string | Да | Значение X-Request-Id, по которому ошибку можно найти в журнале |

```json
{
  "error": {
    "code": "DOCUMENT_VERSION_MISMATCH",
    "message": "акцептуется не актуальная версия договора КМ",
    "details": [
      { "field": "contract_version", "reason": "актуальная версия договора — 2" }
    ],
    "request_id": "a41f8c02-7d3b-4e19-9a55-2c7e0b6f1d84"
  }
}
```

### СЭ-01. Состояние пакета по заявке

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | GET /internal/v1/requests/{individual_request_id}/package |
| Назначение | Вернуть актуальное состояние договоров, полисов, документов и оплаты по индивидуальной заявке |
| Когда вызывается | Открытие застрахованным лицом раздела документов и оплаты, обновление экрана после действия |
| Идемпотентность | Запрос без побочных эффектов, повторы допустимы |

Сервис Заявок ссылки на документы и на оплату у себя не хранит: они читаются этим вызовом при каждом обращении. В базе данных сервиса Заявок сохраняется только проекция — km_contract_state, km_policy_id, payment_status и другие поля участника, поддерживаемые сообщением ДГ-03.

404 REQUEST_NOT_FOUND — по заявке не было ни задачи на выпуск, ни прекращения. Если прекращение пришло раньше задачи — 200 со status = CANCELLED и пустым items.

Ответ

| **Поле** | **Тип** | **Обяз.** | **Описание** |
|---|---|---|---|
| individual_request_id | guid | Да | Идентификатор индивидуальной заявки |
| status | string | Да | IN_PROGRESS / COMPLETED / ERROR / CANCELLED. Совпадает со значением, публикуемым в ДГ-03 |
| items[] | array | Да | По одному элементу на участника последней задачи, в её порядке, включая тех, кому ничего не выпускается |
| items[].participant_id | guid | Да | Идентификатор участника в сервисе Заявок |
| items[].document_kind | string | Да | KM_CONTRACT / LM_POLICY / NONE; у участника с выпущенным документом — вид выпущенного документа |
| items[].contract_id | guid | Условно | Идентификатор договора КМ. Обязательно при document_kind = KM_CONTRACT |
| items[].contract_number | string | Условно | Номер договора КМ |
| items[].contract_version | int | Условно | Версия договора КМ; растёт при изменении данных до акцепта. Её передают в СЭ-03. Обязательно при document_kind = KM_CONTRACT |
| items[].state | string | Да | Состояние выпуска: NOT_REQUIRED / DRAFTED / ACCEPTED / INVOICE_ISSUED / PAID / ISSUED / ERROR / CANCELLED. Договор КМ: DRAFTED — готов к акцепту, ACCEPTED — акцептован, счёт ещё не выставлен, INVOICE_ISSUED — счёт выставлен (ссылки на оплату может не быть, пока ответ Ordering Service на выставление счёта не записан или если он потерян), PAID — оплачен (в том числе передан в 1С:УСК и ждёт регистрации), ISSUED — зарегистрирован в 1С:УСК, полис выпущен, CANCELLED — работа по договору прекращена, в том числе по сроку оплаты; договор со счётом показывается CANCELLED сразу после прекращения работы, хотя сам ждёт просрочки оплаты (раздел «Обращение к Ordering Service», «Отмена»); ERROR — ошибка выпуска, в том числе оплата, поступившая после прекращения работы по договору. Полис ЛМ: NOT_REQUIRED — в работе (создан или передан в 1С:УСК), ISSUED — выпущен. NONE — всегда NOT_REQUIRED |
| items[].premium_amount | decimal | Условно | Страховая премия. Обязательно при document_kind = KM_CONTRACT |
| items[].policy_number | string | Условно | Номер выпущенного полиса. Обязательно при state = ISSUED |
| items[].acceptance | object | Нет | Сведения об акцепте: accepted_at, contract_version — акцептованная версия договора; остаются и после прекращения договора |
| items[].payment | object | Условно | Оплата договора КМ. У договора, оплата которого засчитана, — status = PAID и amount при любом состоянии: PAID, ISSUED, а также ERROR и CANCELLED после оплаты. Иначе по состоянию: ACCEPTED — PENDING и amount, без ссылки и срока; INVOICE_ISSUED — PENDING, amount, expires_at и payment_url (ссылки нет, пока ответ Ordering Service на выставление счёта не записан или если он потерян). В остальных случаях блока нет: у DRAFTED, у договора, прекращённого без оплаты (в том числе по сроку оплаты и договора со счётом после прекращения работы), у договора в ошибке без оплаты, в том числе когда оплата поступила после прекращения работы по договору — такая оплата договору не засчитывается |
| items[].payment.status | string | Да | PENDING — ждёт оплаты, PAID — оплачен. NOT_REQUIRED, FAILED и EXPIRED не выдаются: в этих случаях блока payment нет |
| items[].payment.amount | decimal | Да | Сумма — страховая премия договора |
| items[].payment.payment_url | string | Условно | Ссылка на страницу оплаты. Есть только при state = INVOICE_ISSUED, когда ответ Ordering Service на выставление счёта получен; ошибка оплаты ссылку не убирает. До счёта и до записи ответа ссылки нет; при потерянном ответе её нет совсем, и получить её повторно сейчас нельзя — ОВС-02 |

### СЭ-02. Выдача содержимого документа

Не реализуется. Проектов печатных форм у сервиса Договоров нет: договор КМ акцептуется по его данным (СЭ-03), а финальные формы договора и полисов формирует 1С:УСК и отдаёт постоянными ссылками (ДГ-05, ДГ-07), которые приходят в ДГ-03 и СЭ-01. Текст первой редакции ниже сохранён для истории и не действует.

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | GET /internal/v1/documents/{document_id}/content |
| Назначение | Вернуть содержимое печатной формы для ознакомления застрахованного лица |
| Когда вызывается | Открытие проекта договора до его размещения в 1С:УСК |
| Ответ | Поток байтов. Content-Type: application/pdf, Content-Disposition: inline, Content-Length, ETag — контрольная сумма файла |
| Идемпотентность | Запрос без побочных эффектов, повторы допустимы |

Документ версии FINAL этим вызовом не выдаётся: после размещения в 1С:УСК он доступен по постоянной ссылке, полученной в ДГ-05 или ДГ-07, и проксировать его через два сервиса незачем. Запрос содержимого финального документа возвращает 409 со ссылкой в теле ошибки.

Сервис Заявок передаёт поток застрахованному лицу без сохранения. Заголовок ETag равен полю file_hash и позволяет убедиться, что пользователь видит ровно ту версию, которая будет акцептована.

| **Код HTTP** | **error.code** | **Когда** |
|---|---|---|
| 404 | DOCUMENT_NOT_FOUND | Документ с переданным идентификатором отсутствует |
| 409 | DOCUMENT_IS_FINAL | Запрошено содержимое финального документа. Постоянная ссылка возвращается в error.details |
| 503 | STORAGE_UNAVAILABLE | Внутреннее хранилище файлов недоступно |

### СЭ-03. Приём акцепта оферты

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | POST /internal/v1/contracts/{contract_id}/acceptance |
| Назначение | Зафиксировать акцепт оферты застрахованным лицом |
| Когда вызывается | Застрахованное лицо проставило отметку в личном кабинете |
| Реакция | Создание записи акцепта, перевод договора в ACCEPTED и, если оплата включена, запись заказа на оплату с e-mail плательщика — в одной транзакции. Сам заказ в Ordering Service создаёт фоновый процесс сервиса после фиксации акцепта, а счёт выставляет другой фоновый процесс, когда Ordering Service подтвердит документ заказа (раздел «Обращение к Ordering Service»); ссылку на оплату сервис Заявок получает в ДГ-03 и видит в СЭ-01. ДГ-03 акцепт не публикует |
| Идемпотентность | По contract_id. Повторный вызов с тем же contract_version возвращает 200 и ранее созданную запись, состояние не меняется, второй заказ не записывается. E-mail из повторного вызова не сохраняется: действует адрес из первого. При включённой оплате e-mail обязателен и в повторном вызове |

Вызов синхронный, поскольку от его результата сразу зависит следующий шаг пользователя: появление кнопки оплаты. Ответ всегда без ссылки на оплату (state = ACCEPTED): акцепт к Ordering Service не обращается и его доступности не ждёт, а ссылка появляется только после выставления счёта. Сервис Заявок получает её в ДГ-03 и видит в СЭ-01.

Проекта договора в PDF нет — печатные формы формирует 1С:УСК после регистрации, поэтому акцептуется версия данных договора (номер, стороны, премия, даты), которую застрахованное лицо видело в СЭ-01. После акцепта данные договора вслед за задачами сервиса Заявок не меняются. Запись акцепта неизменяема; IP-адрес и клиент хранятся только в ней и в журнал сервиса не пишутся. E-mail плательщика в записи акцепта не хранится: он записывается только в заказ на оплату, уходит в Ordering Service при выставлении счёта и после этого стирается (раздел «Обращение к Ordering Service», «Счёт»); в журнал сервиса не пишется и в ответе не возвращается.

Пустая строка, пробелы, кавычки, кириллица и IP-адрес вместо домена (в квадратных скобках и без них) — нарушение. Правило намеренно строгое: адрес, который Ordering Service может отвергнуть, должен отклоняться при акцепте, где его можно исправить, а не при выставлении счёта.

| **Код HTTP** | **error.code** | **Когда** |

| 409 | DOCUMENT_HASH_MISMATCH | Не используется: контрольной суммы файла нет |
| 409 | INVALID_STATE | Состояние договора не допускает акцепт: работа прекращена или договор уже выпущен; договор в ошибке; прекращён и акцептованный ранее договор. Недоступность Ordering Service на ответ акцепта не влияет: акцепт принимается как обычно, а заказ ждёт фонового процесса. 503 SERVICE_UNAVAILABLE означает только занятый договор; акцепт при этом не сохранён, и тот же запрос повторяют позже.

Формат тела, в том числе e-mail, и при включённой оплате наличие e-mail проверяются раньше, чем читается договор: запрос без адреса получает 400 и тогда, когда договора нет, он занят, его состояние не допускает акцепт или акцепт той же версии уже принят.

### СЭ-07. Удаление вложения

Новый раздел. Контракт согласован с разработчиком сервиса Заявок.

| **Параметр** | **Значение** |
|---|---|
| Метод и путь | DELETE /internal/v1/attachments/{attachment_id} |
| Назначение | Удалить объект вложения из хранилища S3 и проставить отметку мягкого удаления (deleted_at и deleted_request_id) в реестре contract_documents |
| Когда вызывается | Застрахованное лицо или сотрудник удаляет ошибочно загруженную справку 070/у до передачи договора КМ в 1С:УСК либо отзывает согласие на обработку персональных данных |
| Ответ | 204 No Content с пустым телом и заголовком X-Request-Id |
| Идемпотентность | По attachment_id: повторный вызов по уже удалённому вложению, неизвестному идентификатору или идентификатору печатной формы 1С:УСК возвращает 204 No Content без обращения к S3 и без перезаписи первичных deleted_at и deleted_request_id |

Удаление выполняется в два обращения к базе с вызовом S3 между ними (без удержания транзакции базы во время сетевого вызова к хранилищу):

1. Короткая транзакция проверяет запись по attachment_id (отсутствующая, печатная или уже удалённая запись сразу завершается ответом 204), а для активной медицинской справки (MEDICAL_CERTIFICATE) берёт пессимистическую блокировку всех договоров КМ пары (individual_request_id, participant_id) в каноническом порядке идентификаторов и проверяет запрет удаления. Удаление справки отклоняется кодом 409 ATTACHMENT_LOCKED (без удаления объекта из S3 и без изменения записи), если хотя бы один договор пары находится в состоянии SUBMITTED или ISSUED либо в журнале исходящих outbox_messages есть запись события KmContractSubmitted по любому договору этой пары (в том числе если после отправки договор перешёл в ERROR или CANCELLED, был возвращён дежурным в PAID или справка была дозагружена после отправки ДГ-04). До фиксации ДГ-04 (до прихода ДГ-01, в состояниях DRAFT_READY, ACCEPTED, INVOICE_ISSUED, PAID без KmContractSubmitted, а также после прекращения заявки ДГ-02 без KmContractSubmitted) удаление справки разрешено. Согласие PD_CONSENT в 1С:УСК не передаётся и 409 ATTACHMENT_LOCKED не вызывает.
2. Вне транзакции объект физически удаляется из S3 (отсутствие ключа в живом бакете идемпотентно). При сбое S3 или отсутствии бакета сервис отвечает 503 STORAGE_UNAVAILABLE, оставляя запись активной в базе (deleted_at IS NULL), чтобы повторный DELETE завершил физическое удаление файла из хранилища.
3. Вторая короткая транзакция повторно проверяет активность записи (а для справки повторно берёт блокировку договоров пары и проверяет отсутствие 409 ATTACHMENT_LOCKED) и атомарно проставляет deleted_at и deleted_request_id (текущий X-Request-Id) только при deleted_at IS NULL. После мягкого удаления СЭ-06 отвечает 404 ATTACHMENT_NOT_FOUND, повторная загрузка с тем же attachment_id в СЭ-04/СЭ-05 — 409 ATTACHMENT_CONFLICT, а в передачу ДГ-04 удалённая справка не включается.

Коды ошибок

| **Код HTTP** | **error.code** | **Когда** |
|---|---|---|
| 400 | VALIDATION_ERROR | Неверный формат GUID параметра attachment_id в пути (field = attachment_id) |
| 409 | ATTACHMENT_LOCKED | Медицинская справка относится к участнику заявки, договор КМ которого передан или передавался в 1С:УСК |
| 503 | SERVICE_UNAVAILABLE | Договор КМ участника занят другой операцией дольше таймаута блокировки базы (по умолчанию 5 с); ни S3, ни реестр не изменены, повторить запрос позже |
| 503 | STORAGE_UNAVAILABLE | Хранилище файлов S3 недоступно или отсутствует бакет; запись остаётся активной, повторить запрос позже |

## Чтение справочников Дата-референса

Сервис Договоров читает справочники синхронно, в момент формирования исходящего сообщения (ДГ-06, ДГ-04) и при поиске выпущенного полиса по ДГ-07 и ДГ-05. Данные нужны на момент формирования сообщения, кэширование на стороне сервиса Договоров не выполняется: справочники ведутся в Дата-референсе и там же изменяются.

| **Вызов** | **Назначение** | **Что берётся** |
|---|---|---|
| GET /internal/v1/programs/{id} | Программа страхования | Наименование, external_id для 1С:УСК, перечень услуг, is_archive |
| GET /internal/v1/policies/{id}/contract-view и /internal/v1/policies/contract-view?external_id={uuid} | Полис без персональных данных | id, external_id, number, begin_date, end_date, is_archive |
| GET /internal/v1/insurance-contracts/{id} | Договор страхования страхователя | Номер, external_id, страхователь (краткое и полное наименование; null, если страхователь — физическое лицо), is_archive |

Идентификаторы external_id подтягиваются из справочников при формировании сообщений ДГ-04 и ДГ-06 и в таблицах сервиса Договоров не дублируются. Недоступность Дата-референса блокирует выпуск: сообщение не формируется, задача остаётся в текущем состоянии и повторяется по общим правилам.

Правила клиента. Даты у Дата-референса — yyyy-mm-dd, открытая дата 1С — null. Таймаут соединения — 2 с, ответа — 7 с: при отказе своей базы Дата-референс отвечает 503 SERVICE_UNAVAILABLE в худшем случае примерно через 5 с, и клиент не обрывает запрос раньше. Ответ 503, таймаут, обрыв соединения и ответ не из контракта повторяются ограниченное число раз (по умолчанию 3 повтора с паузой 1 с), затем — «справочник недоступен». 404 по id программы, договора или полиса и ответ is_archive = true — ошибка выпуска по участнику (PROGRAM_NOT_FOUND, PROGRAM_ARCHIVED, INSURANCE_CONTRACT_NOT_FOUND и т. д.), другой отказ 4xx с кодом — ошибка по участнику с этим кодом. Полис, только что выпущенный в 1С:УСК, может ещё не дойти до Дата-референса — 404 POLICY_NOT_FOUND при поиске по external_id повторяется ограниченно, затем входящее сообщение откладывается по лестнице 1 / 5 / 15 минут. X-Request-Id передаётся сквозняком: при разборе входящего сообщения — его message_id, при подготовке запроса полиса ЛМ — идентификатор записи полиса ЛМ, иначе новый UUID.

## Обращение к Ordering Service

Ordering Service — существующий внутренний сервис управления заказами. Он ничего не знает о страховании: получает документ — номер договора, сумму, даты — и выставляет по нему счёт. Эквайринг и фискализация выполняются в нём; возвраты на первом этапе выполняются вручную. Контракт Ordering Service принадлежит его владельцу и описан в его документации; здесь — вызовы, события и данные, которые использует сервис Договоров. Открытые вопросы к команде Ordering — ОВС-02.

Реализованы: заказ на оплату — создание заказа по акцептованному договору КМ, подтверждение документа и отмена заказа при прекращении договора; счёт со сроком оплаты и ссылкой на оплату; приём событий Ordering Service по заказам, в том числе об оплате; сверка заказов с Ordering Service по расписанию.

Оплата включается настройкой сервиса. Пока она выключена, сервис Договоров к Ordering Service не обращается, его события не читает и заказ при акцепте не записывает, а e-mail в акцепте необязателен; договор, акцептованный при выключенной оплате, заказа не получает и после включения.

| **Вызов** | **Направление** | **Назначение** |
|---|---|---|
| POST /orders | Договоры → Ordering | Создание заказа: клиент (clientId), документ договора — тип contract, идентификатор и номер документа, премия, дата документа, срок жизни документа (ttl), код продукта; канал. В ответе — идентификатор заказа orderId |
| POST /orders/{clientId} | Договоры → Ordering | Поиск заказов клиента по коду продукта и идентификатору документа: перед повтором создания заказа и при отмене заказа, идентификатор которого неизвестен |
| GET /orders/{orderId} | Договоры → Ordering | Чтение состояния заказа: перед повтором отмены (заказ в состоянии CANCELED второй раз не отменяется), после сбоя выставления счёта и при сверке заказов. Берутся статус заказа и история его событий — тип и момент события |
| POST /orders/{orderId}/cancel | Договоры → Ordering | Отмена заказа: канал и причина отмены (по умолчанию notActual) |
| POST /orders/{orderId}/checkout | Договоры → Ordering | Выставление счёта по заказу, готовому к оплате: документ, как при создании заказа, канал, способ оплаты, срок оплаты и e-mail плательщика. В ответе — идентификатор счёта invoiceId и ссылка на оплату paymentUrl |
| Подтверждение документа (fixed) | Договоры → Ordering, RabbitMQ маркетинга | Сообщение в обменник продукта после создания заказа; Ordering переводит документ в готовность к оплате |
| События заказа | Ordering → Договоры, RabbitMQ маркетинга | Сообщения из очереди событий заказов продукта: подтверждение документа (fixed), ожидание оплаты (pendingPayment), оплата (paid), ошибка оплаты (paymentError), просрочка оплаты (paymentOverdue), отмена заказа (canceled); остальные типы пропускаются |

Токен. Каждый вызов несёт токен доступа сервера Keycloak, который сервис Договоров получает по OAuth 2.0 client credentials (клиент и секрет — настройки сервиса). Токен используется, пока не истёк; на ответ 401 или 403 сервис берёт новый. Каждый вызов несёт и заголовок correlationId — один идентификатор на оплату договора, он хранится с заказом и пишется в журнал сервиса.

Заказ. Запись заказа сохраняется в одной транзакции с акцептом (СЭ-03), а сам заказ в Ordering Service создаёт фоновый процесс сервиса (по умолчанию с паузой 10 секунд между проходами): ответ акцепта от Ordering Service не зависит. Заказ один на договор, документ в нём один. Клиент заказа — участник-страхователь договора, застрахованное лицо по корпоративному договору: он платит за всех участников. Идентификатор документа — идентификатор записи заказа в сервисе Договоров, номер документа — номер договора КМ, премия — страховая премия с двумя знаками, дата документа — момент акцепта, срок жизни документа — по умолчанию 23:59:59 накануне даты заезда по московскому времени (часовой пояс и отступ от начала дня заезда — настройки сервиса). Даты уходят с числовым смещением часового пояса и без долей секунды. Коды продукта и канала, причина отмены — настройки сервиса. Акцептованные договоры, заказ по которым не создан дольше порога (по умолчанию 1 час), сервис считает — метрика для оповещения дежурного.

Повтор без второго заказа. Ключа идемпотентности у Ordering Service нет. Поэтому перед запросом на создание сервис отмечает в записи заказа, что запрос отправлялся, и любой следующий запрос — после таймаута, обрыва или на другом экземпляре сервиса — начинается с поиска заказов клиента по идентификатору документа: найденный заказ берётся вместо нового, и только если поиск заказа не нашёл, заказ создаётся. Видит ли поиск только что созданный заказ — ОВС-02.

Подтверждение документа. Когда Ordering Service вернул идентификатор заказа, сервис записывает его в payment_orders.external_order_id и в той же транзакции — сообщение fixed в Outbox. Сообщение публикуется в обменник продукта на брокере RabbitMQ маркетинга с ключом маршрутизации (обменник и ключ — настройки сервиса), с подтверждением брокера и повторами, как остальные исходящие. Тело — в формате Ordering Service, без конверта meta: source — код продукта, eventType = fixed, data.agreementId — идентификатор документа. Брокер маркетинга — третий брокер сервиса Договоров, он подключается только при включённой оплате; обменник и очереди на нём заводит Ordering Service. Кроме публикации подтверждений, сервис читает на нём очередь событий заказов продукта (имя очереди — настройка сервиса), поэтому учётной записи сервиса нужны право публикации в обменник продукта и право чтения этой очереди. Если Ordering Service документ так и не подтвердил, подтверждение повторяет сверка заказов (абзац «Сверка»).

```json
{
  "source": "<код продукта>",
  "eventType": "fixed",
  "data": { "agreementId": "0b7e5a3c-91d4-7f20-8c6e-2d4f1a9b3e57" }
}
```

Счёт. Счёт выставляет фоновый процесс сервиса (по умолчанию с паузой 10 секунд между проходами) по заказу, документ которого Ordering Service подтвердил: пришло событие fixed или сверка застала заказ в состоянии READY_TO_PAYMENT. Перед вызовом отдельная транзакция ставит в записи счёта отметку «счёт начат» и записывает срок оплаты. С этой отметки договор считается договором со счётом — кроме договора, в счёте по которому Ordering Service отказал. Тело вызова: clientId; orderDetails — один документ с теми же значениями, что при создании заказа; eventDetails.channel; payment — paymentType = internetAcquiring, paymentTtl — срок оплаты, email — e-mail плательщика из акцепта. urlToReturn и urlToDecline не передаются. Из ответа со status = success сохраняются invoiceId (латинские буквы, цифры и знаки . _ : -, до 100 знаков) и paymentUrl (адрес http:// или https://, после которого — до 2000 печатных знаков ASCII без пробелов); paymentShortUrl не используется. Ответ без них или не по формату считается сбоем вызова (абзац «Повтор без второго счёта»). Когда ответ записан, договор переходит в INVOICE_ISSUED, e-mail плательщика стирается, а сервису Заявок, если работа по договору не прекращена, уходит ДГ-03 с payment_status = PENDING и ссылкой; ссылку и срок оплаты он видит и в СЭ-01. Ссылка в журнал сервиса не пишется. E-mail плательщика стирается и тогда, когда договор оплачен или прекращён, в том числе по сроку оплаты; если Ordering Service отказал в создании заказа или в счёте, адрес хранится — он нужен, чтобы вернуть заказ в работу (абзац «Отказы»).

Срок оплаты. Срок оплаты — меньшее из «отметка „счёт начат“ плюс трое суток» и срока жизни документа заказа (по умолчанию 23:59:59 накануне даты заезда по московскому времени); срок и минимальный срок оплаты — настройки сервиса. Если к выставлению счёта до срока жизни документа остаётся меньше минимального срока (по умолчанию 1 час) или он уже прошёл, счёт не выставляется: Ordering Service не вызывается, договор прекращается с причиной EXPIRED в момент прохода, заказ отменяется, e-mail плательщика стирается, сервису Заявок уходит ДГ-03 (km_contract_state = CANCELLED, payment_status = NOT_REQUIRED, состояние заявки — по участникам). Если срок жизни документа прошёл раньше, чем ушёл запрос на создание заказа, заказ в Ordering Service не создаётся: запись закрывается в состоянии «срок истёк» (EXPIRED), договор прекращается так же. Заказ, счёт по которому так и не выставлен (документ не подтверждён, Ordering Service отказал в счёте или в создании заказа), после срока жизни документа закрывает сверка заказов по тому же правилу, не обращаясь к Ordering Service. В Ordering Service срок уходит полем paymentTtl с числовым смещением и без долей секунды, а в СЭ-01 отдаётся в UTC с долями, поэтому expires_at может быть позже paymentTtl меньше чем на секунду.

Повтор без второго счёта. Ключа идемпотентности у выставления счёта нет, а выставленный счёт Ordering Service отозвать не даёт, поэтому вслепую вызов не повторяется. После сбоя вызова (временный отказ, таймаут, обрыв соединения, ответ не по формату) сервис в том же проходе читает состояние заказа: READY_TO_PAYMENT — счёта нет, вызов повторяется; PENDING_PAYMENT — счёт выставлен, а ответ потерян; другое состояние — сбой заказа, он ждёт. Заказ, сбой по которому в проходе не разрешился, остаётся с отметкой «счёт начат», и проход счетов его больше не берёт: повторить вызов может только сверка заказов — когда отметка старше порога сверки (по умолчанию 15 минут), а Ordering Service показывает READY_TO_PAYMENT; срок оплаты тогда считается заново.

Потерянный ответ. Если Ordering Service уже ждёт оплаты (PENDING_PAYMENT), а ответа с invoiceId и ссылкой у сервиса нет, счёт записывается выставленным без ссылки: договор переходит в INVOICE_ISSUED, e-mail плательщика стирается, в СЭ-01 — PENDING и срок оплаты без ссылки, ДГ-03 не уходит (PENDING без ссылки контракт ДГ-03 не допускает). Получить ссылку повторно сейчас нельзя: в ответе на чтение состояния заказа её нет (ОВС-02). О потерянном ответе дежурный получает одно оповещение на заказ — при сбое вызова в проходе или от сверки, если ссылки так и нет к порогу сверки. Ошибка оплаты оповещение не отменяет: сверка оповещает и по счёту без ссылки, по которому уже пришла ошибка оплаты, не меняя его состояния. Событие pendingPayment может прийти раньше ответа на выставление счёта: оно только переводит счёт в выставленные, без оповещения, а пришедший следом ответ дописывает ссылку — сервису Заявок уходит ДГ-03 со ссылкой, оповещения о потерянном ответе по этому заказу уже не будет.

События Ordering Service. События по заказам продукта сервис читает из очереди событий заказов на брокере маркетинга; читает её, как и остальные очереди, ведущий экземпляр. Тело — JSON в формате Ordering Service без конверта meta, обработчик выбирается по полю eventType тела. Событие принимается через Inbox: ключ идемпотентности — eventId (GUID берётся как есть, другая строка — UUID, вычисленный из неё), повтор события второй раз не применяется, порядок по версии не применяется. Событие без eventId или с телом не JSON подтверждается брокеру и теряется с записью в журнале сервиса и счётчиком. Применяется событие, только если в нём есть eventType и orderId, в orderDetails[] есть документ продукта Договоров с идентификатором в формате GUID, заказ найден (по orderId, а если заказа с таким orderId нет, — по идентификатору документа), orderId и документ совпадают с заказом, а сумма документа documentPremium — число, равное премии; иначе событие записывается и пропускается с предупреждением в журнале сервиса и счётчиком, договор и заказ не меняются.

- fixed — документ подтверждён, заказ готов к оплате: счёт выставит ближайший проход;
- pendingPayment — счёт, вызов по которому ещё идёт, записывается выставленным (без ссылки, пока ответ не записан): договор INVOICE_ISSUED, e-mail плательщика стирается, оповещения нет; по уже выставленному счёту событие пропускается;
- paid — оплата: договор переходит в PAID, момент оплаты — поле updated события (обязательно: событие без него — нарушение контракта и отклоняется сразу); оплаченный договор уходит в 1С:УСК (ДГ-04 по общим правилам), ДГ-03 оплата не даёт;
- paymentError — ошибка оплаты: договор и ссылка не меняются, ДГ-03 нет, следующее событие paid принимается;
- paymentOverdue — просрочка оплаты: договор прекращается с причиной EXPIRED, момент прекращения — поле updated события (нет его — момент разбора), заказ в Ordering Service не отменяется, сервису Заявок уходит ДГ-03;
- canceled — отмена заказа, которую сервис Договоров не запрашивал: оповещение дежурному, договор не меняется;
- остальные типы (created, changed, draft, show, hide и незнакомые) пропускаются.

Оплата и просрочка договора со счётом, работа по которому прекращена, — абзац «Отмена».

Сверка. Ведущий экземпляр по расписанию (по умолчанию с паузой в минуту между проходами) сверяет с Ordering Service созданные заказы без итога оплаты, запись счёта по которым не менялась дольше порога сверки (по умолчанию 15 минут), а также счета в ошибке оплаты, срок оплаты которых прошёл больше чем на запас (по умолчанию 1 час). Отклонённые, оплаченные и просроченные счета сверка не запрашивает. Состояние заказа берётся вызовом GET /orders/{orderId}:

- NEW — документ не подтверждён: сверка повторяет подтверждение документа (по умолчанию до двух раз), затем один раз оповещает дежурного и дальше только запрашивает состояние;
- READY_TO_PAYMENT — документ подтверждён: счёт выставляется тем же проходом;
- PENDING_PAYMENT — счёт выставлен; если ссылки нет, ответ на выставление счёта считается потерянным (абзац «Потерянный ответ»), а вызов с отметкой «счёт начат» моложе порога сверки ещё считается идущим;
- PAID и PAYMENT_OVERDUE — те же переходы, что по событиям paid и paymentOverdue; момент — из истории событий заказа (последнее событие paid или paymentOverdue), а если его там нет, — момент сверки;
- PAYMENT_ERROR — ошибка оплаты; если ссылки нет — оповещение о потерянном ответе (одно на заказ); если срок оплаты с запасом прошёл, а итога нет, счёт считается просроченным: договор прекращается с причиной EXPIRED, дежурный получает оповещение и сверяет с Ordering Service, не было ли оплаты;
- другой статус или состояние не получено — оповещение дежурному, договор не меняется.

Кроме того, каждый проход сверки закрывает заказы, счёт по которым не выставлен к сроку жизни документа (абзац «Срок оплаты»). Если Ordering Service недоступен, проход сверки останавливается до следующего. Созданные заказы, счёт по которым не выставлен дольше порога (по умолчанию 30 минут), и счета без итога после срока оплаты с запасом сервис считает — метрики для оповещения дежурного.

Отказы. Таймауты по умолчанию: соединение с Ordering Service — 2 с, ответ — 10 с; с сервером токенов — 2 и 5 с. Временный отказ — ответ 5xx, 408, 429, 401 или 403, таймаут, обрыв соединения, ответ не по формату или без обязательного поля, отказ сервера токенов: по умолчанию до 3 попыток подряд, считая первую, с паузой 1 с, затем заказ ждёт следующего прохода фонового процесса (повтор выставления счёта начинается с чтения состояния заказа — абзац «Повтор без второго счёта»); договор не меняется, пока не прошёл срок жизни документа (абзац «Срок оплаты»). Отказ по существу в создании заказа — ответ 4xx, кроме 401, 403, 408 и 429, или ответ 2xx со status = error: заказ отклоняется с кодом ошибки Ordering Service, договор не меняется, сервис Заявок ничего не получает; дежурный устраняет причину и возвращает заказ в работу ручной операцией сервиса. Отказ по существу в выставлении счёта определяется так же и тоже не повторяется: счёт отклоняется с кодом ошибки Ordering Service (если кода нет — «HTTP &lt;код&gt;»), договор остаётся ACCEPTED и договором со счётом не считается, сервис Заявок ничего не получает, дежурный получает оповещение, e-mail плательщика хранится. Дежурный возвращает такой заказ к выставлению счёта ручной операцией сервиса — с прежними номером заказа и correlationId; если отказ из-за адреса, заказ в работу не возвращают, а адрес стирают вручную. Сверка такой заказ не запрашивает; если счёт так и не выставлен к сроку жизни документа, договор прекращается по сроку оплаты (абзац «Срок оплаты»). Исключение — договор, работу по которому прекратили, пока шёл вызов выставления счёта: его прекращение отложено (абзац «Отмена»), и отказ в счёте применяет его сразу, в той же транзакции. Договор CANCELLED с запомненными причиной и моментом, заказ помечается к отмене, e-mail плательщика стирается, дежурный получает оповещение об отказе; нового ДГ-03 нет — договор уже показан прекращённым, а возвращать заказ в работу не нужно. Отказ по существу на поиске заказов и на чтении состояния заказ не отклоняет: он ждёт следующего прохода (при сверке — с оповещением дежурному). Подтверждение документа, которое брокер маркетинга так и не принял (нет обменника, привязки по ключу или права публикации, повторы исчерпаны), так же отклоняет заказ — с кодом FIXED_UNDELIVERED; договор не меняется. Из ответа об ошибке сохраняется только код: в тексте ошибки Ordering Service возвращает значения полей запроса.

Отмена. Если работу по договору прекращают — по ДГ-02, при исключении участника из поездки или смене вида документа, — а договор не со счётом (выставление счёта не начато или Ordering Service в счёте отказал), договор прекращается сразу, а заказ в той же транзакции помечается к отмене и e-mail плательщика стирается. Если запрос на создание заказа ещё не отправлялся, запись закрывается без обращения к Ordering Service. Иначе заказ отменяет отдельный фоновый процесс (по умолчанию с паузой в минуту между проходами): заказ, идентификатор которого неизвестен (ответ на создание потерян), он сначала ищет, а не найденный — закрывает без отмены. Если ответ на создание приходит уже после такого закрытия, заказ снова помечается к отмене и отменяется следующим проходом; документ по нему не подтверждается. Если идентификатор заказа пришёл, когда заказ уже помечен к отмене, документ по нему не подтверждается; подтверждение, записанное до прекращения, отправляется как обычно. Отказ Ordering Service в отмене не повторяется: договор остаётся прекращённым, заказ разбирают с командой Ordering (Ordering отменяет заказ только до выставления счёта).

Договор со счётом сразу не прекращается: выставленный счёт Ordering Service отозвать не даёт. Причина и момент прекращения запоминаются в записи счёта (при исключении участника и смене вида документа — причина OTHER и момент разбора задачи), заказ не отменяется, а наружу договор сразу показывается прекращённым: в ДГ-03 — km_contract_state = CANCELLED и payment_status = NOT_REQUIRED без ссылки, в СЭ-01 — CANCELLED без блока payment. Прекращение применяется, когда Ordering Service сообщит о просрочке оплаты или её признает сверка заказов: договор CANCELLED с запомненными причиной и моментом. Если Ordering Service отказал в счёте или выставление счёта, начатое до прекращения, так и не дало счёта, прекращение применяется сразу, а заказ отменяется. Нового ДГ-03 в этих случаях нет: договор уже показан прекращённым. Пока просрочки нет, задача сервиса Заявок с большей версией, в которой участнику снова выпускается договор КМ, возвращает ему тот же договор и снимает прекращение (ДГ-03 — по правилам ТЗ «Точки интеграции Заявки — Договоры»); оплата после этого принимается как обычная. Если застрахованный оплатил договор, прекращение которого отложено, договор переходит в ERROR с кодом KM_CONTRACT_PAID_AFTER_CANCELLATION: оплата ему не засчитывается, в 1С:УСК он не передаётся, дежурный получает оповещение и возвращает деньги вручную, а следующая задача заводит участнику новую запись. Оплата по договору, уже прекращённому по просрочке, договор не меняет; деньги тоже возвращают вручную.

Оплаченный договор при прекращении работы прекращается сразу; его заказ остаётся оплаченным и в Ordering Service не отменяется, дежурный получает оповещение и возвращает деньги вручную.

Ключ связи — идентификатор документа (payment_orders.id): по нему заказ находится поиском, подтверждается документ и сопоставляется событие Ordering Service, если заказа с orderId события у сервиса нет. Идентификатор заказа Ordering сохраняется в payment_orders.external_order_id, счёт — в payment_invoices.

## Нефункциональные требования

- Время ответа СЭ-01 и СЭ-03 — не более 1 секунды на 95 процентах запросов; к Ordering Service ни один из них не обращается.
- Время ответа СЭ-04, СЭ-05, СЭ-06 и СЭ-07 определяется размером файла (до 5 МБ) и обращением к хранилищу S3.
- Недоступность сервиса Договоров не должна блокировать работу сервиса Заявок: раздел документов отображается с сообщением о временной недоступности, остальные функции заявки сохраняются.
- Журналирование: каждый вызов фиксируется с X-Request-Id, путём и кодом ответа. Тела запросов, содержащие персональные данные, в журнал не записываются; файлы вложений, их имена и ключи объектов S3, e-mail плательщика и ссылка на оплату — тоже.
- Удалено
