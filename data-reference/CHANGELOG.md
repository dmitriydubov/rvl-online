# История изменений data-reference

Здесь записаны заметные изменения сервиса по версиям, новые сверху. Формат — [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
номера версий — по [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html):

- **MAJOR** — ломается контракт REST `/internal/v1`, контракт очередей 1С:УСК или эксплуатация: удалена или переименована
  переменная окружения, появилась обязательная переменная без умолчания, миграция базы без обратной совместимости.
- **MINOR** — новая возможность без поломки, в том числе новая переменная с умолчанием и миграция, которая только добавляет.
- **PATCH** — исправление без новых возможностей.

Рубрики версии: Добавлено, Изменено, Устарело, Удалено, Исправлено, Безопасность и Перенос — что нужно сделать на контуре
при установке версии.

## [Не выпущено]

## [1.0.0-rc.4] - 2026-11-17

### Добавлено

- Полис по номеру без договора — `GET /internal/v1/policies?number=` без `contract_external_id`, для кабинета
  застрахованного, который знает номер полиса, но не договор. Полис ищется среди полисов всех договоров, номер
  сравнивается точно. Один полис — 200, ответ тот же, что с договором; ни одного — 404 `POLICY_NOT_FOUND`; несколько —
  409 `AMBIGUOUS_POLICY`, полис не отдаётся, в `details` у каждого кандидата `policy_id` и `contract_external_id` — GUID
  договора 1С:УСК из полиса. Архивные, закончившиеся и обезличенные полисы находятся так же, как с договором. Пустой
  номер — 400 по `number`; номер вместе с пустым `contract_external_id` — 400 по `contract_external_id`, как прежде.
  Номера полиса нет ни в тексте ошибки, ни в журнале. Ответ не кэшируется. Описание — `docs/openapi.yaml`.

### Изменено

- `GET /internal/v1/policies?number=` без `contract_external_id` больше не отвечает 400 по `contract_external_id`: это
  поиск по номеру без договора (выше). Запрос `/internal/v1/policies` без ключа отвечает 400 по `external_id` с причиной
  «нужен external_id либо number» (было «нужен external_id либо number вместе с contract_external_id»). С договором поиск
  не изменился.

### Перенос

- **Миграции**: `022-policy-number-index` добавляет индекс `idx_policies_number` по `policies (number)`. Индекс строится
  обычным `CREATE INDEX`: пока он строится, запись в `policies` ждёт, чтение не блокируется. Пишут в эту таблицу разбор
  сообщений 1С:УСК и проход стирания персональных данных. Разбор при ожидании дольше `lock_timeout` (5 с) уводит
  сообщение на повтор, порядок потока сохраняется. Проход стирания при том же отказе прерывается с записью ERROR
  «Unexpected error occurred in scheduled task», обезличивание доделывает следующий проход через
  `projectx.import.retention-poll-interval` (1 ч). На большой таблице полисов (`select count(*) from policies`)
  выкатывать в спокойное для 1С:УСК время. Запись ERROR прохода стирания возможна, только если проход совпадёт
  с построением индекса дольше `lock_timeout`.

## [1.0.0-rc.3] - 2026-11-16

### Добавлено

- Приём связей застрахованных из 1С:УСК: чей полис связан с чьим, тип связи и срок. Две новые очереди —
  `ONEC_QUEUE_INSURED_ASSOCIATIONS` (`1c-usk_to_rvl-online_insured-association-changes`, сообщения со строками) и
  `ONEC_QUEUE_INSURED_ASSOCIATIONS_FINAL` (`1c-usk_to_rvl-online_insured-association-changes-final`, финальное сообщение
  со счётчиками); имена — переменные с умолчаниями. Передача применяется целиком после сборки по `cid`, в любом порядке
  очередей; записи, подходящие под отбор передачи, замещаются её строками, пустая передача их удаляет. Счётчики не
  сошлись или часть испорчена — отклоняется вся передача, прежние связи остаются. Из двух передач с пересекающимися
  отборами действует та, финальное сообщение которой принято позже. Связь, пришедшая раньше полиса застрахованного или
  связанного, ждёт его до `projectx.import.parent-wait-timeout`. Хранятся GUID полисов и типа связи, начало и
  окончание; ФИО связанного застрахованного из сообщения не хранится, а тело сообщения стирается через
  `projectx.import.payload-ttl` при любом статусе. Новая таблица `insured_associations` и таблица применённых передач
  `insured_association_finalization`. Новый показатель `onec_insured_association_transfers_stuck` — передачи связей,
  ждущие частей дольше `projectx.import.stuck-transfer-threshold`; проверка зависших передач называет их в журнале.
  Сообщение со строками без массива `recordSet` (поля нет, оно `null` или не массив) отклоняет всю передачу, прежние
  связи остаются; пустой массив — законное сообщение без строк.
- Родственники застрахованного для сервиса Заявок — `GET /internal/v1/policies/{id}/family`, где `{id}` — наш id полиса
  застрахованного. Отдаёт полисы родственников, связь с которыми из 1С:УСК действует сегодня по московскому дню и которые
  сами действуют сегодня (не в архиве, начались и не закончились): номер, ФИО, дату рождения, пол и GUID типа связи
  в поле `relationship` (пустой, если типов связи сегодня несколько). С `number` — один родственник с этим номером; не найден — 404
  `POLICY_NOT_FOUND`, два — 409 `AMBIGUOUS_POLICY`. Родственников нет — пустой список. Ответ не кэшируется. Описание —
  `docs/openapi.yaml`.
- Потребитель очереди 1С:УСК, остановленный из-за того, что очереди нет на брокере (её удалили и заводят заново или
  её не было при получении роли), поднимается сам: ведущий раз в `projectx.onec.ingest.consumer-restart-interval`
  (`30s`) проверяет, вернулась ли очередь, и запускает потребителя без перезапуска пода; сообщения, ждавшие на брокере,
  принимаются. На паузе из-за базы и на неведущем попыток нет, потребители, которые сами переподключаются к брокеру,
  не трогаются, очереди сервис по-прежнему не объявляет. В журнале одна запись ERROR на эпизод отсутствия очереди и
  одна INFO при возврате потребителя. Новый показатель `onec_ingest_queues_without_consumer` — очереди ведущего без
  подтверждённого брокером потребителя (на неведущем и на паузе 0); правило оповещения — в `docs/operations.md`.
  Ответ `onecIngest` в `/actuator/health` не меняется.
- Предел одновременно обрабатываемых запросов к `/internal/v1`: лишние запросы сразу получают 503 `SERVICE_UNAVAILABLE`
  в едином формате с `X-Request-Id`, принятые обслуживаются, пробы `/livez`, `/readyz` и порт актуатора под предел не
  попадают. Новая переменная `API_MAX_CONCURRENT_REQUESTS` (`100`), целое не меньше 1. Метрики `rest_read_rejected_total`
  (отказы по пределу) и `rest_read_in_flight` (запросы в обработке). Защищает процесс от гибели по памяти при перегрузке.
- Ведущий экземпляр не теряет роль, пока его же транзакция приёма или разбора держит блокировку ведущего, и пока
  занят пул приёма и разбора: блокировку продлевает отдельный пул соединений `leader-lock` без ограничения ожидания
  блокировки. Новая переменная `DB_LEADER_POOL_SIZE` (`1`) — соединений в этом пуле; на экземпляр становится на одно
  соединение с базой больше. Проверка таймаутов сеанса при старте сверяет и этот пул.
- Сервис можно запускать несколькими экземплярами: очереди 1С:УСК читает, сырьё разбирает и задачи по расписанию
  выполняет только ведущий, REST отвечает на всех. Ведущего выбирает блокировка в базе (новая таблица `leader_lock`).
  При плавной остановке ведущий отпускает роль сразу, после гибели роль переходит через `LEADER_LOCK_TTL` (30 с).
  Принятое, но неподтверждённое погибшим ведущим сообщение новый ведущий подтверждает как дубль.
- Метрика `onec_leader`: 1 — экземпляр ведущий, 0 — нет.
- Кэш справочников сбрасывается сразу на всех экземплярах: разобрав сообщение 1С:УСК, ведущий оповещает остальные через
  базу (`LISTEN`/`NOTIFY` PostgreSQL). Каждый экземпляр держит для этого одно постоянное соединение с базой вне пулов.
  После обрыва этого соединения экземпляр переподключается и сбрасывает весь кэш. Срок жизни `REFERENCE_CACHE_TTL`
  остаётся страховкой. Новые переменные `REFERENCE_CACHE_RECONNECT_DELAY` (`1s`) и `REFERENCE_CACHE_RECONNECT_MAX_DELAY`
  (`10s`) — паузы между попытками подключения. Метрика `reference_cache_notifications_connected`: 1 — экземпляр слушает
  оповещения, 0 — нет.
- Прогрев после старта: запустившись, экземпляр читает свои ручки REST по первым записям справочников и складывает
  ответы в кэш, и только после этого `/readyz` отвечает 200. Прогрев только читает, длится не дольше `WARMUP_TIMEOUT`
  (`30s`), а отказ базы его лишь прерывает с записью WARN. Сколько записей каждого справочника читать —
  `WARMUP_RECORDS_PER_REFERENCE` (`100`).
- Описание REST `/internal/v1` в формате OpenAPI 3.0.3 — `docs/openapi.yaml`: ручки, параметры, поля ответов и коды
  ошибок; файл импортируется в Postman и открывается в Swagger UI.

### Изменено

- Показатель `onec_price_transfers_stuck` и предупреждение о зависших передачах прайсов считают только передачи прайсов.
- Тестовый стенд: ingress открывает и ручки полисов `/internal/v1/policies…` (к ним обращается BFF сервиса Заявок), и
  МКБ-10 `/internal/v1/mkb10…` (по запросу сервиса Заявок).
  Резервные копии файлов рядом с `values.yaml` (`*.bak` и подобные) в чарт стенда больше не попадают: их исключает
  `.helmignore`.
- `/readyz` отвечает 200 только после прогрева, а не сразу после запуска приложения: под не получает трафик, пока
  горячий код не скомпилирован и кэш пуст. `/livez` по-прежнему отвечает 200 сразу после запуска.
- Момент приёма сообщения 1С:УСК (`received_at` в `inbound_message`, `inbox` и `quarantine`) ставят часы базы, а не
  часы экземпляра. Порядок разбора не зависит от расхождения часов экземпляров, в том числе после смены ведущего. По
  часам базы считаются и сроки от момента приёма: срок хранения тел в сырье и в карантине, порог зависания передач
  прайса, счётчики просроченного и давность ожидания разбора в метриках.
- Компонент здоровья `onecIngest` называет роль экземпляра в детали `role` (`leader` или `standby`). Неведущий
  потребителей не ждёт и отвечает `UP`.
- Метрики снимка из базы (`onec_inbound_messages`, `onec_inbound_pending_oldest_age_seconds`, `onec_price_transfers_stuck`,
  `onec_inbound_backlog_staleness_seconds`, `onec_retention_overdue_*`, `policies_retention_overdue_personal_data`)
  отдаёт только ведущий. Правила оповещения по ним — на `max()` по экземплярам.
- После паузы из-за базы ведущий запускает потребителей всех очередей, а не только остановленных паузой.
- 503 `SERVICE_UNAVAILABLE` теперь приходит не только при отказе базы, но и при перегрузке — сразу, без ожидания
  соединения; правило для вызывающего прежнее: повторить с паузой ограниченное число раз, `message` не разбирать.
- Ответа брокера 1С:УСК на команду канала (открыть канал, объявить или проверить очередь, подписаться, отменить
  подписку) сервис ждёт не дольше 30 с вместо 10 минут; не дождавшись, считает брокер недоступным: проход запуска
  остановленных потребителей откладывается, а потребитель подписывается сам, когда брокер ответит, или ближайшим
  проходом. Поздний ответ брокера на просроченную команду клиент отбрасывает, если ждёт ответа другого типа. Новая
  переменная `RABBITMQ_CHANNEL_RPC_TIMEOUT` (`30s`).
- Строку таймаутов сеанса базы (`lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`) для всех
  пулов собирает сервис из `DB_LOCK_TIMEOUT`, `DB_STATEMENT_TIMEOUT` и `DB_IDLE_IN_TRANSACTION_TIMEOUT`; блок `options`
  ушёл из `application.yml`. Значения по умолчанию прежние. Свойство
  `spring.datasource.hikari.data-source-properties.options`, заданное в окружении, больше не действует: при старте
  пишется WARN.
- Разбор известных проблем эксплуатации вынесен в `docs/troubleshooting.md`: признак, проверка, что делать — для
  старта, готовности, REST, приёма из 1С:УСК, ведущего экземпляра, разбора сырья, кэша и предупреждений при старте.
  В `docs/operations.md`, раздел «Сбои и ручные операции», остались операции, которые меняют данные или роль
  экземпляра. README ссылается на новый документ.
- Тестовый стенд работает двумя репликами с плавной выкаткой: новый под поднимается и прогревается, пока старый
  отвечает, и выкатка проходит без простоя. Перед остановкой под 10 с ждёт, пока его перестанут выбирать ingress и
  сервис, и только потом начинает плавную остановку; окно остановки пода — 60 с вместо 45. Число реплик, стратегия
  выкатки, пауза и окно задаются в `values.yaml` чарта. В `docs/` описаны требования к развёртыванию, правило
  совместимых миграций, расчёт соединений с базой и правила оповещения на нескольких экземплярах.

### Исправлено

- Пакет передачи прайса без массива строк `recordSet` (поля нет, оно `null` или не массив) отклоняет всю передачу без
  повторов с причиной `нет обязательного поля recordSet` или `поле recordSet не является массивом`, прежний прайс
  услуги остаётся. Раньше такой пакет считался пакетом без строк, и передача «1 пакет, 0 строк» очищала прайс услуги.
  Пустой массив `recordSet` — законный пакет без строк.
- Несколько экземпляров, одновременно стартующих на одной пустой базе, иногда не стартовали: один из них падал при
  создании журнала миграций с «duplicate key value violates unique constraint "pg_type_typname_nsp_index"» и стартовал
  только после перезапуска. Теперь миграции накатывает один экземпляр под блокировкой PostgreSQL, остальные ждут его
  (запись INFO «миграции схемы накатывает другой экземпляр») и стартуют с первой попытки. Замок миграций Liquibase,
  оставшийся от экземпляра, погибшего посреди миграций, стартующий экземпляр снимает сам с записью WARN: кто держал
  замок и с какого времени; раньше следующие экземпляры ждали его 5 минут и не стартовали.
- Идентификатор из одних пробелов в пути запроса (`/internal/v1/programs/%20%20` и другие ручки с `{id}`) получал 500
  `INTERNAL_ERROR` с записью ERROR в журнале. Теперь это 400 `VALIDATION_ERROR` по полю `id` с причиной «ожидается UUID»,
  как у любого неверного GUID, без записи ERROR. Параметр запроса из одних пробелов по-прежнему получает 400
  «обязательный параметр».
- REST-чтение, у которого лимит 3 с истёк между обращениями к базе, получало 500 `INTERNAL_ERROR` с записью ERROR в
  журнале вместо 503. Теперь это 503 `SERVICE_UNAVAILABLE` в едином формате и запись WARN, как у остальных временных
  отказов базы, и вызывающий может повторить запрос. Настоящая ошибка в тексте запроса к базе — по-прежнему 500.

### Перенос

- **Переменные окружения** — новые, у всех есть умолчание, задавать не обязательно:
  - `LEADER_LOCK_TTL` (`30s`) — срок блокировки ведущего экземпляра;
  - `DB_LEADER_POOL_SIZE` (`1`) — соединений в пуле блокировки ведущего `leader-lock`;
  - `REFERENCE_CACHE_RECONNECT_DELAY` (`1s`) и `REFERENCE_CACHE_RECONNECT_MAX_DELAY` (`10s`) — паузы переподключения
    слушателя оповещений о сбросе кэша;
  - `WARMUP_TIMEOUT` (`30s`) и `WARMUP_RECORDS_PER_REFERENCE` (`100`) — предел прогрева после старта и число записей
    справочника, которое он читает;
  - `API_MAX_CONCURRENT_REQUESTS` (`100`) — предел одновременных запросов к `/internal/v1` на экземпляр; на нескольких
    репликах общий предел — число реплик, умноженное на значение;
  - `RABBITMQ_CHANNEL_RPC_TIMEOUT` (`30s`) — предел ожидания ответа брокера 1С:УСК на команду канала;
  - `ONEC_QUEUE_INSURED_ASSOCIATIONS` (`1c-usk_to_rvl-online_insured-association-changes`) и
    `ONEC_QUEUE_INSURED_ASSOCIATIONS_FINAL` (`1c-usk_to_rvl-online_insured-association-changes-final`) — очереди
    связей застрахованных: сообщения со строками и финальные сообщения передачи.
- **Миграции**: `020-leader-lock` добавляет таблицу `leader_lock`, `021-insured-associations` — таблицы связей
  застрахованных `insured_associations` и применённых передач связей `insured_association_finalization`.
- **Очереди связей застрахованных**: завести на брокере контура очереди
  `1c-usk_to_rvl-online_insured-association-changes` и `1c-usk_to_rvl-online_insured-association-changes-final`
  (заводит 1С:УСК) до выкатки: без очереди её потребитель не запустится, и `onecIngest` в `/actuator/health` будет
  `DOWN`. Добавить правило оповещения `max(onec_insured_association_transfers_stuck) > 0`.
- **Новые зависимости**: `org.springframework.integration:spring-integration-jdbc` и `spring-integration-core` версии из
  BOM Spring Boot.
- **Зависимость** `org.postgresql:postgresql` теперь нужна при компиляции, а не только при запуске; версия та же, из BOM
  Spring Boot.
- **Синхронизация часов** подов (NTP): по ним считается срок блокировки ведущего; время приёма сообщения ставят часы базы.
- **Соединения с базой**: 17 на экземпляр — пул приёма и разбора (10), пул REST-чтений (`DB_REST_POOL_SIZE`, 5), пул
  блокировки ведущего (`DB_LEADER_POOL_SIZE`, 1) и постоянное соединение слушателя оповещений о сбросе кэша
  (`application_name` = `data-reference-cache-notifications`); на выкатке трёх реплик — до 4 × 17 = 68 плюс одно
  миграций у стартующего пода. `max_connections` базы за вычетом резерва суперпользователя
  (`superuser_reserved_connections`, по умолчанию 3) должно вмещать их вместе с другими клиентами базы.
- **Пробы пода**: проба готовности должна ждать старт приложения вместе с прогревом (до `WARMUP_TIMEOUT` сверх старта).
- **Развёртывание в несколько реплик**: до трёх реплик, выкатка `RollingUpdate` (умолчания Kubernetes или `maxSurge` 1,
  `maxUnavailable` 0), `preStop` с паузой 10 с (`sleep 10`), `terminationGracePeriodSeconds` не меньше паузы плюс 50 с.
  Миграции каждой версии совместимы с предыдущей.
- **Миграции накатывает только сервис**: Liquibase вручную на базе сервиса, пока сервис работает или стартует, не
  запускают — оставшийся замок Liquibase стартующий экземпляр снимает сам.
- **Откат** на предыдущую версию после приёма первых сообщений связей — только по процедуре `docs/operations.md`, «Откат
  на версию без потока связей застрахованных»: предыдущая версия не читает строки сырья нового потока.

## [1.0.0-rc.1] - 2026-10-07

Первая версия с номером: кандидат в выпуск 1.0.0.

### Добавлено

- Приём справочников и полисов из 1С:УСК: 11 очередей RabbitMQ, 10 потоков данных — полисы, договоры страхования (из них
  сохраняются только ДМС), контрагенты-юрлица (ЛПУ и страхователи), МКБ-10, договоры с ЛПУ, страховые программы, виды
  обращения, адреса и регионы ЛПУ, прейскуранты (пакеты строк и финальное сообщение — две очереди), услуги контрагентов.
  Сообщение подтверждается брокеру только после записи в базу; повторная доставка не дублирует запись. Разбор идёт по
  порядку приёма внутри потока, с повторами после временных отказов базы. Сообщение, пришедшее раньше своей родительской
  записи, ждёт её до `ONEC_PARENT_WAIT_TIMEOUT`. Тело, которое база не примет никогда, уходит в карантин. Пока база
  недоступна, приём стоит на паузе и сам возобновляется.
- REST-чтение справочников для сервисов Заявок и Договоров, `GET /internal/v1/…`, ответы в JSON с полями в snake_case:
  - `/lpu?contract_external_id=` — каталог ЛПУ, доступных застрахованным договора страхования;
  - `/lpu/{id}` — карточка ЛПУ с прайсовым договором;
  - `/lpu/{id}/services?need_prices=` — услуги прайсового договора по видам обращения РВЛ, с ценами или без;
  - `/services/{id}/price?date_from=&date_to=` — стоимость услуги за период проживания;
  - `/mkb10?query=&limit=` и `/mkb10?codes=` — подсказка по МКБ-10 и перечень кодов разом;
  - `/policies/search?contract_external_id=&query=&limit=` — подсказка по части ФИО или номера среди действующих полисов договора;
  - `/policies/{id}`, `/policies?external_id=`, `/policies?number=&contract_external_id=` — полис целиком;
  - `/policies/{id}/contract-view`, `/policies/contract-view?external_id=` — полис для сервиса Договоров, без
    персональных данных;
  - `/insurance-contracts/{id}`, `/insurance-contracts?external_id=` — договор страхования со страхователем;
  - `/programs/{id}` — страховая программа с перечнем услуг.

  Ошибки — в едином формате; недоступная или не ответившая вовремя база — 503, потребитель повторяет запрос.
- Кэш справочных ответов в памяти процесса (Spring Cache, Caffeine): срок жизни `REFERENCE_CACHE_TTL`, предел
  `REFERENCE_CACHE_MAXIMUM_SIZE` ответов на кэш. Сообщение 1С сразу сбрасывает зависящие от него ответы. Полисы
  не кэшируются.
- Хранение и стирание персональных данных по сроку: тела сообщений с полисами и договорами страхования и тела в карантине
  стираются через 30 суток после приёма; ФИО, дата рождения и почта застрахованного стираются из полиса через
  `POLICY_PERSONAL_DATA_GRACE` после окончания срока или перевода в архив. Обезличенный полис отдаётся с
  `personal_data_erased: true`.
- Метрики Prometheus и health на порту управления: `/actuator/prometheus`, `/actuator/health` с компонентами `db` и
  `onecIngest`, пробы `/actuator/health/liveness` и `/readiness`; на порту API — короткие пробы `/livez` и `/readyz`.
- Версия сервиса в `/actuator/info` (`build.version`) и в строке старта журнала при запуске из jar или образа.

### Безопасность

- У паролей базы и брокера нет умолчаний: пароль из репозитория не подойдёт ни к одной базе.
- Персональные данные не пишутся в журнал, метрики, health и тексты ошибок; журнал — в формате JSON (ECS).
- Порт управления отделён от порта API: на порту API `/actuator/*` отвечает 404.
- При включённом TLS к брокеру (`RABBITMQ_SSL_ENABLED=true`) сертификат и имя хоста проверяются, пока это не выключено явно.
