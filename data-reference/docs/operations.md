# data-reference: эксплуатация

## О сервисе

**РВЛ ОНЛАЙН** — контур сервисов, через которые застрахованные по ДМС получают восстановительное лечение в
санаториях (ЛПУ): сервис Заявок ведёт заявки на лечение и их согласование, сервис Договоров — договоры, полисы
и личный кабинет застрахованного. Справочники и полисы для них приходят из учётной системы страховщика 1С:УСК.
Аббревиатура «РВЛ» означает ещё и вид деятельности «восстановительное лечение» в 1С:УСК: по нему санатории
отделяются от прочих контрагентов.

**data-reference** принимает из 1С:УСК справочники и полисы через RabbitMQ, хранит их в PostgreSQL и отдаёт
сервисам Заявок и Договоров по REST. Сам он в 1С ничего не пишет и наружу, за пределы контура, не публикуется.

Версия — в `gradle.properties` (`version=`), история изменений — в [CHANGELOG.md](../CHANGELOG.md).

## Стек

Java 21, Spring Boot 4.0.7 (Spring Framework 7.0.8, Spring AMQP 4.0.4, Spring Data JPA 4.0.6), Hibernate ORM 7.2.19,
Liquibase 5.0.3, PostgreSQL 16 (драйвер 42.7.11), RabbitMQ 4.1 (клиент 5.27.1), Jackson 3.1.4, Caffeine 3.2.4,
Micrometer 1.16.6 с реестром Prometheus, встроенный Tomcat 11.0.22, сборка Gradle 8.14.3. Версии библиотек задаёт
BOM Spring Boot.

## REST `/internal/v1`

Только `GET`, ответы в JSON с полями в snake_case. Ручки доступны только сервисам Заявок и Договоров: своей
авторизации у них нет, защищает сетевая политика. Одновременно экземпляр обрабатывает не больше `API_MAX_CONCURRENT_REQUESTS` (100)
запросов ко всем ручкам сразу; лишние сразу получают 503 `SERVICE_UNAVAILABLE`, пробы и порт актуатора под предел не
попадают.

| Метод | Путь | Что отдаёт |
|---|---|---|
| GET | `/internal/v1/lpu?contract_external_id=` | каталог ЛПУ, доступных застрахованным договора страхования |
| GET | `/internal/v1/lpu/{id}` | карточку ЛПУ с прайсовым договором |
| GET | `/internal/v1/lpu/{id}/services?need_prices=` | услуги прайсового договора по видам обращения РВЛ, с ценами или без |
| GET | `/internal/v1/services/{id}/price?date_from=&date_to=` | стоимость услуги за период проживания |
| GET | `/internal/v1/mkb10?query=&limit=` или `?codes=` | подсказку по МКБ-10 или перечень кодов разом |
| GET | `/internal/v1/policies/search?contract_external_id=&query=&limit=` | подсказку по части ФИО или номера среди действующих полисов договора |
| GET | `/internal/v1/policies/{id}`, `/internal/v1/policies?external_id=`, `?number=&contract_external_id=` или `?number=` | полис целиком, с персональными данными; по номеру без договора — среди всех полисов, несколько с таким номером — 409 `AMBIGUOUS_POLICY` с `policy_id` и `contract_external_id` кандидатов |
| GET | `/internal/v1/policies/{id}/family`, `?number=` | полисы родственников застрахованного по связям из 1С:УСК, действующие сегодня; с `number` — один родственник |
| GET | `/internal/v1/policies/{id}/contract-view`, `/internal/v1/policies/contract-view?external_id=` | полис для сервиса Договоров, без персональных данных |
| GET | `/internal/v1/insurance-contracts/{id}`, `/internal/v1/insurance-contracts?external_id=` | договор страхования со страхователем |
| GET | `/internal/v1/insurance-contracts?insurer_external_id=` | единственный действующий сегодня договор страхования страхователя по его GUID в 1С:УСК; нет такого — 404 `INSURANCE_CONTRACT_NOT_FOUND`, несколько — 409 `AMBIGUOUS_INSURANCE_CONTRACT` с `insurance_contract_id` кандидатов |
| GET | `/internal/v1/programs/{id}` | страховую программу с перечнем услуг |

Ручки, параметры, поля ответов и коды ошибок описаны в [openapi.yaml](openapi.yaml) (OpenAPI 3.0.3): файл
импортируется в Postman и открывается в Swagger UI; меняя ручку, меняйте и его. Бизнес-правила ручек — в документе
«ТЗ API Data-reference». Примеры запросов к стенду с
синтетическими данными — [src/test/resources/stand/README.md](../src/test/resources/stand/README.md).

### Как обновлять `openapi.yaml`

Описание правится в том же изменении, что и ручка, параметр, поле ответа, его обязательность или допустимость `null`,
либо код ошибки. Тест `OpenApiContractTest` входит в `./gradlew test`, работает без базы и сети и сверяет файл с кодом:
перечень ручек и методов, параметры пути и запроса (имена, расположение, обязательность, тип и `format`), поля ответов
200 и тела ошибки (имена, тип, `format`, значения `enum`, `required`, `nullable`), таблицу кодов ошибок в
`info.description`, пробы `/livez` и `/readyz`, пределы параметров (`minLength`, `maxLength`, `minimum`, `maximum`,
`maxItems`, числовой `default`) против настроек `projectx.api.*` и каждое «не больше N ночей» в тексте против
`projectx.api.price.max-nights`.
При расхождении он падает списком строк, по строке на расхождение, например:

```text
docs/openapi.yaml разошёлся с кодом (1):
GET /internal/v1/policies, параметр «number»: есть в коде, в описании нет
```

Порядок:

1. Изменить код и запустить `./gradlew test --tests '*OpenApiContractTest'`.
2. Поправить `openapi.yaml` по каждой строке падения:
   - новая ручка — операция в `paths` с параметрами и ответом 200, схема ответа — в `components.schemas`;
   - новое поле записи ответа — свойство схемы в snake_case. Поле, которое пишется всегда (и со значением `null`),
     входит в `required`; компонент с `@Nullable` получает `nullable: true`; поле с `@JsonInclude(NON_NULL)` не входит в
     `required` и `nullable` не получает: при `null` его в ответе нет;
   - параметр запроса — `required: true`, если он обязателен в каждом обработчике пути, который принимает параметры
     запроса. Обработчики-отказы без параметров (оба ключа сразу, ключа нет) обязательность не снимают;
   - новый код ошибки — строка таблицы «Ошибки» в `info.description` с HTTP-статусом и описание ответа у ручек,
     которые его отдают.
   - новый или изменённый предел параметра — ключевое слово схемы параметра и строка в `ParameterLimits.configured`
     (тесты, пакет `controller.openapi`), которая берёт значение из `ReferenceApiProperties` или из константы кода, где
     предел задан. Предел меняют в настройке, а не в описании: тест сверяет описание с умолчанием из `application.yml`
     и `@DefaultValue`. Значение, заданное переменной окружения на контуре, тест не видит.
3. Новый тип исключения со своим кодом или новый `@ExceptionHandler` — случай в `ErrorCatalog` (тесты, пакет
   `controller.openapi`): без него тест падает с сообщением о коде или обработчике без случая.
4. Число ночей тест находит только в записи «не больше N ночей»: предел расчёта стоимости пишут в описании именно так.
5. Тест не сверяет остальные тексты описаний, примеры, заголовки и то, какие коды ошибок отдаёт каждая ручка: их
   проверяют на ревью. Синтаксис OpenAPI тоже не проверяется: после правки файл открывают в Postman или Swagger UI.

## Очереди 1С:УСК

13 очередей, 11 потоков данных: прейскуранты и связи застрахованных приходят двумя очередями каждый. Очереди заводит 1С:УСК, сервис их не создаёт.
Умолчания имён — имена тестового брокера; на контуре их сверяют со списком брокера.

| Переменная | Что приходит |
|---|---|
| `ONEC_QUEUE_POLICIES` | полисы застрахованных с программами и условиями обслуживания (персональные данные) |
| `ONEC_QUEUE_INSURANCE_CONTRACTS` | договоры страхования; сохраняются только ДМС |
| `ONEC_QUEUE_CONTRAGENTS` | контрагенты-юрлица: ЛПУ и страхователи |
| `ONEC_QUEUE_MKB10` | справочник МКБ-10 |
| `ONEC_QUEUE_LPU_CONTRACTS` | договоры с ЛПУ |
| `ONEC_QUEUE_PROGRAMS` | страховые программы и учреждения, доступные по ним |
| `ONEC_QUEUE_APPEAL_TYPES` | виды обращения за медицинской помощью |
| `ONEC_QUEUE_LPU_CONTACTS` | адрес и регион ЛПУ |
| `ONEC_QUEUE_PRICE_LISTS` | прейскуранты ЛПУ, пакетами строк |
| `ONEC_QUEUE_PRICE_LISTS_FINAL` | финальное сообщение передачи прейскуранта со счётчиками пакетов |
| `ONEC_QUEUE_CONTRAGENT_SERVICES` | услуги контрагентов по договорам |
| `ONEC_QUEUE_INSURED_ASSOCIATIONS` | связи застрахованных: чей полис связан с чьим, тип связи и срок; сообщения со строками (в теле — ФИО связанного застрахованного) |
| `ONEC_QUEUE_INSURED_ASSOCIATIONS_FINAL` | финальное сообщение передачи связей застрахованных со счётчиками сообщений и строк |

## Порты

- `8080` — REST `/internal/v1` и пробы `/livez`, `/readyz`. `/livez` отвечает 200, как только приложение запущено;
  `/readyz` — только после прогрева (раздел «Выкатка и сеть»).
- `8081` (`MANAGEMENT_PORT`) — `/actuator/health`, `/actuator/info` (версия сервиса), `/actuator/prometheus`.

## Переменные окружения

Обязательны только пароли. Остальные умолчания ведут на локальный контур из `docker-compose.yml` или заданы под рабочий
режим. Таймауты PostgreSQL пишутся с единицей (`ms`, `s`, `min`): число без неё PostgreSQL читает как миллисекунды.
Таймауты сеанса задаются только переменными `DB_LOCK_TIMEOUT`, `DB_STATEMENT_TIMEOUT` и `DB_IDLE_IN_TRANSACTION_TIMEOUT`:
стартовый параметр драйвера `options` собирает сервис, и свойство `spring.datasource.hikari.data-source-properties.options`,
заданное в окружении, заменяется — при старте об этом пишется WARN.

**База**

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/data_reference?logServerErrorDetail=false` | адрес базы для пула и миграций; параметры драйвера (`sslmode` и подобные) — только здесь; `logServerErrorDetail=false` сохранять |
| `DB_USERNAME` | `data_reference` | пользователь базы; нужны права DDL на схему и CREATE на базу для расширения `pg_trgm` |
| `DB_PASSWORD` | нет, обязательна | пароль базы |
| `DB_CONNECTION_TIMEOUT_MS` | `2000` | ожидание соединения в пуле приёма и разбора, мс |
| `DB_SOCKET_TIMEOUT_SECONDS` | `60` | сетевой тайм-аут драйвера в пуле приёма и разбора, с; больше `DB_STATEMENT_TIMEOUT` |
| `DB_LOCK_TIMEOUT` | `5s` | ожидание одной блокировки |
| `DB_STATEMENT_TIMEOUT` | `30s` | один оператор |
| `DB_IDLE_IN_TRANSACTION_TIMEOUT` | `1min` | открытая транзакция без запросов |
| `DB_REST_POOL_SIZE` | `5` | соединений в пуле REST-чтений; у пула приёма и разбора их 10 |
| `DB_REST_CONNECTION_TIMEOUT_MS` | `2000` | ожидание соединения в пуле REST-чтений, мс, не меньше 250 |
| `DB_REST_SOCKET_TIMEOUT_SECONDS` | `5` | сетевой тайм-аут драйвера в пуле REST-чтений, с; не меньше лимита чтения вместе с ожиданием отмены |
| `DB_REST_CANCEL_SIGNAL_TIMEOUT_SECONDS` | `2` | сколько драйвер ждёт отправки отмены запроса в пуле REST-чтений, с |
| `DB_LEADER_POOL_SIZE` | `1` | соединений в пуле блокировки ведущего `leader-lock`, не меньше 1; соединения держатся открытыми постоянно; у пула нет `lock_timeout`, остальные таймауты сеанса и ожидание соединения — как у пула приёма и разбора |
| `API_READ_TIMEOUT_SECONDS` | `3` | лимит REST-чтения на каждый оператор, с; меньше `DB_LOCK_TIMEOUT` |
| `API_MAX_CONCURRENT_REQUESTS` | `100` | сколько запросов к `/internal/v1` экземпляр обрабатывает одновременно; лишние сразу получают 503 `SERVICE_UNAVAILABLE`; целое не меньше 1, иначе сервис не стартует; больше `DB_REST_POOL_SIZE`; умолчание подобрано замером на 1 CPU / 1 ГБ ([load-testing.md](load-testing.md)) |

**Брокер 1С:УСК**

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `RABBITMQ_HOST` | `localhost` | хост брокера; с TLS он должен быть в сертификате брокера |
| `RABBITMQ_PORT` | `5672` | порт: 5672 без TLS, 5671 с TLS |
| `RABBITMQ_VHOST` | `/` | vhost |
| `RABBITMQ_USERNAME` | `data_reference` | логин брокера; на брокере 1С:УСК — `rvl-online`. Учётной записи нужны право `read` на очереди 1С:УСК и право пассивно объявлять их: потребитель объявляет очередь пассивно перед подпиской, тем же объявлением ведущий проверяет, вернулась ли очередь на брокер; `configure` не нужно — очереди сервис не объявляет |
| `RABBITMQ_PASSWORD` | нет, обязательна | пароль брокера |
| `RABBITMQ_SSL_ENABLED` | `false` | TLS к брокеру |
| `RABBITMQ_SSL_VALIDATE_CERTIFICATE` | `true` | проверка сертификата брокера; на тестовом контуре с самоподписанным сертификатом — `false` |
| `RABBITMQ_SSL_VERIFY_HOSTNAME` | `true` | проверка имени хоста в сертификате; без проверки сертификата не действует |
| `RABBITMQ_LISTENER_AUTO_STARTUP` | `true` | слушатели очередей 1С; `false` — там, где очередей 1С нет |
| `RABBITMQ_CHANNEL_RPC_TIMEOUT` | `30s` | сколько клиент ждёт ответа брокера на команду канала: открыть канал, объявить или проверить очередь, подписаться, отменить подписку. Не дождался — команда считается неудачной: проход запуска остановленных потребителей откладывается, а потребитель подписывается сам, когда брокер ответит (контейнер повторяет запуск каждые 5 с), или ближайшим проходом. Держите от 1 с до 60 с: столько запуск потребителя ждёт его старта. Значение считается в целых миллисекундах: меньше 1 мс превращается в `0` — ждать без предела; отрицательное значение не даёт сервису запуститься |
| `ONEC_QUEUE_*` | имена тестового брокера | имена 13 очередей — раздел «Очереди 1С:УСК» |

## Прочие настройки

У этих настроек нет своей переменной. Любую настройку Spring Boot можно задать переменной окружения: точки заменяются на
`_`, дефисы убираются, буквы прописные (`projectx.import.poll-interval` → `PROJECTX_IMPORT_POLLINTERVAL`); элемент списка
задаётся номером в подчёркиваниях (`my.service[0].other` → `MY_SERVICE_0_OTHER`). Список через запятую в одной
переменной проверен только для `PROJECTX_ONEC_CONTRACT_DMSPRODUCTTYPE`.

| Настройка | Умолчание | Что задаёт |
|---|---|---|
| `projectx.inbound.retry.backoff` | `30s`, `5m`, `30m` | паузы повторов разбора после временного отказа; после последней — `FAILED` |
| `projectx.import.initial-delay` | `30s` | задержка первого прохода разбора, стирания и проверки зависших передач после старта |
| `projectx.import.poll-interval` | `10s` | пауза между проходами разбора |
| `projectx.import.batch-size` | `100` | сообщений за проход разбора |
| `projectx.import.payload-ttl` | `30d` | срок хранения тел полисов, договоров страхования, связей застрахованных, пропущенных сообщений и сообщений, не дождавшихся родителя |
| `projectx.import.quarantine-ttl` | `30d` | срок хранения тел в карантине |
| `projectx.import.retention-poll-interval` | `1h` | пауза между проходами стирания по сроку |
| `projectx.import.retention-batch-size` | `500` | строк за пачку стирания |
| `projectx.import.stuck-transfer-threshold` | `1h` | с какого возраста передача прайса или связей застрахованных считается зависшей |
| `projectx.import.stuck-transfer-poll-interval` | `15m` | пауза между проверками зависших передач |

## Выкатка и сеть

- Сервис работает несколькими репликами, до трёх, с плавной выкаткой `RollingUpdate`: новый под поднимается и
  прогревается, пока старые отвечают, и старый останавливается, только когда новый готов. На время выкатки работают до
  четырёх экземпляров двух версий, поэтому миграции каждой версии совместимы с предыдущей ([design.md](design.md),
  «Выкатка в несколько реплик»). Фоновую работу — очереди 1С:УСК, разбор сырья и задачи по расписанию — выполняет
  ведущий экземпляр, REST отвечает на всех. Ведущего выбирает строка таблицы `leader_lock`. При плавной остановке ведущий отпускает роль, и другой экземпляр берёт
  её за секунду-две; если в момент остановки транзакция приёма или разбора ведущего ещё держала строку блокировки,
  строка остаётся, и роль переходит через `LEADER_LOCK_TTL`, как после гибели. Если ведущий погиб, роль переходит
  через `LEADER_LOCK_TTL` (30 с). Сообщение, которое погибший
  ведущий не успел подтвердить, брокер возвращает в очередь, а новый ведущий подтверждает его как дубль.
- **Откат на версию без потока связей застрахованных.** Предыдущая версия не знает поток `INSURED_ASSOCIATIONS` и вид
  родителя `POLICY` в строках сырья: на таких строках у неё отказывают выборка разбора, снимок метрик и проверка срока
  ожидания, и разбор встаёт для всех потоков. Порядок отката:
  1. Остановить все поды новой версии (масштабировать до нуля или откатить и дождаться, пока их не останется): пока
     ведущий новой версии жив, он читает очереди связей и записывает новые строки.
  2. Одной транзакцией удалить сырьё потока, его отметки в `inbox` и таблицу применённых передач. Без удаления из
     `inbox` повторно присланные 1С:УСК сообщения после возврата на новую версию были бы приняты как дубли и потеряны:

     ```sql
     begin;
     delete from inbox where message_id in (select message_id from inbound_message
                                             where stream = 'INSURED_ASSOCIATIONS');
     delete from insured_association_finalization;
     delete from inbound_message where stream = 'INSURED_ASSOCIATIONS';
     commit;
     ```

  3. Поднять предыдущую версию. Связи в `insured_associations` остаются, предыдущая версия их не читает.

  Теряются принятые, но не применённые части передач связей (`NEW`, `BUFFERED`, `AWAITING_PARENT`) и история порядка
  передач. Поэтому после повторной выкатки новой версии 1С:УСК просят заново выгрузить связи застрахованных.
- Кэш ответов живёт в памяти каждого экземпляра. Ведущий, разобрав сообщение 1С:УСК, оповещает все экземпляры через
  базу (`LISTEN`/`NOTIFY` PostgreSQL), и они за доли секунды сбрасывают кэши этого справочника. Экземпляр, у которого
  обрывалось соединение слушателя, после переподключения сбрасывает весь кэш. Срок жизни `REFERENCE_CACHE_TTL` (10 мин)
  остаётся страховкой, например от правки базы мимо 1С:УСК.
- Часы подов синхронизированы (NTP): по ним считается срок блокировки ведущего, то есть когда роль перейдёт после
  гибели ведущего. Момент приёма сообщения и сроки от него ставят часы базы, на порядок разбора часы подов не влияют.
- **Прогрев после старта.** Запустившись, экземпляр сначала прогревается: читает свои же ручки REST на `localhost` (порт API, `server.port`)
  по первым `WARMUP_RECORDS_PER_REFERENCE` (100) записям договоров страхования, ЛПУ, программ и полисов и складывает
  ответы в кэш. Пока идёт прогрев, `/livez` отвечает 200, а `/readyz` — 503 `OUT_OF_SERVICE`, и трафик на под не идёт.
  Прогрев длится не дольше `WARMUP_TIMEOUT` (30 с), затем `/readyz` отвечает 200. Предел отсчитывается до чтения ключей;
  при отказе базы само это чтение может занять до 5 с (ожидание соединения 2 с и лимит чтения 3 с). Отказ
  базы или истёкший предел прогрев только останавливает, с записью WARN, и экземпляр всё равно становится готовым:
  готовность от базы не зависит. Прогрев только читает и идёт на каждом экземпляре.
- Пробы пода. На тестовом стенде проба готовности — `/readyz`, первая проверка через 60 с, затем каждые 10 с, порог 6
  неудач; проба живости — `/livez`, через 120 с, каждые 30 с, порог 3. Неудачная проба готовности под не перезапускает,
  а только не пускает на него трафик; перезапускает проба живости, а `/livez` во время прогрева отвечает 200. Старт
  приложения вместе с прогревом (до `WARMUP_TIMEOUT` сверх старта) должен укладываться в окно проб готовности
  стенда — 60 с плюс 6 проверок по 10 с; иначе выкатка дольше ждёт готовности нового пода.
- **Требования к развёртыванию** (так настроен тестовый стенд; значения контура сверяются с ними):
  - реплик — не больше трёх; две — чтобы REST отвечал и при остановке одного пода;
  - выкатка `RollingUpdate` с умолчаниями Kubernetes (`maxSurge` и `maxUnavailable` по 25 %: на двух-трёх репликах это
    один лишний под и ни одного недоступного) или явно `maxSurge` 1, `maxUnavailable` 0, как на стенде; `Recreate`
    гасит все поды до запуска новых, и сервис не отвечает до готовности нового — около минуты;
  - `preStop` с паузой 10 с (`sleep 10`; в образе команда есть): без неё в первые секунды остановки запросы ещё
    приходят на под, который их уже не принимает, и получают отказ соединения;
  - `terminationGracePeriodSeconds` — не меньше паузы `preStop` плюс 50 с: на стенде 60 с. Плавная остановка — это
    остановка потребителей и слушателя (до 5 с каждая), отпускание роли ведущего и доработка начатых запросов (до
    `spring.lifecycle.timeout-per-shutdown-phase`, 30 с). Не уложившись, Kubernetes убивает процесс, и роль ведущего
    переходит через `LEADER_LOCK_TTL`, а не сразу;
  - проба готовности — `/readyz`: трафик на новый под идёт только после прогрева;
  - если в кластере больше одного узла — поды разносятся по узлам мягко: `topologySpreadConstraints` по
    `kubernetes.io/hostname` с `whenUnsatisfiable: ScheduleAnyway` или `podAntiAffinity` с
    `preferredDuringSchedulingIgnoredDuringExecution`. Мягко — значит, планировщик предпочитает узел без пода сервиса,
    но при потере узла ставит замену на оставшийся; жёсткое правило оставило бы её без места. Вместе с этим —
    PodDisruptionBudget с `minAvailable: 1`: при выводе узла на обслуживание экземпляры вытесняются по одному, и один
    всегда отвечает. На кластере из одного узла бюджет не ставится: вывод такого узла не закончился бы никогда, второй
    под некуда поставить.
- Соединений к базе на экземпляр: 10 у пула приёма и разбора (умолчание HikariCP) плюс `DB_REST_POOL_SIZE` (5) плюс
  `DB_LEADER_POOL_SIZE` (1) у пула блокировки ведущего плюс одно постоянное соединение слушателя оповещений о сбросе
  кэша (вне пулов) — 17; на время старта ещё одно — миграций, оно закрывается после них. На время выкатки трёх реплик
  работают до четырёх экземпляров — до 4 × 17 = 68 соединений плюс одно миграций у стартующего пода (при `maxSurge` 1
  новые поды стартуют по одному). `max_connections` базы за вычетом `superuser_reserved_connections` (по умолчанию 3) и
  `reserved_connections` (по умолчанию 0) должно вмещать эти 69 соединений плюс соединения других клиентов той же базы
  и того же сервера PostgreSQL: администраторов, мониторинга, соседних сервисов. Умолчание PostgreSQL `max_connections`
  — 100.
- **Миграции накатывает только сервис.** Экземпляры, стартующие одновременно, накатывают миграции по очереди: соединение
  миграций держит блокировку PostgreSQL, остальные ждут её с записью INFO «миграции схемы накатывает другой экземпляр».
  Замок Liquibase (`databasechangeloglock`), оставшийся от экземпляра, погибшего посреди миграций, снимает сам экземпляр,
  взявший блокировку, с записью WARN ([troubleshooting.md](troubleshooting.md)). Поэтому Liquibase вручную на базе
  сервиса, пока сервис работает или стартует, не запускают: его замок снимет стартующий экземпляр. Предела ожидания
  блокировки у сервиса нет: на стенде под, ждущий её дольше окна пробы живости, Kubernetes перезапускает примерно
  через 3 минуты (`L_INIT_DELAY` 120 с плюс 3 проверки по 30 с).
- Порт 8080 открывают сервисам Заявок и Договоров, порт актуатора — только мониторингу и Kubernetes. Своей авторизации у
  ручек нет, защита — сетевая политика.
- ФИО и номер полиса едут в строке запроса (`/internal/v1/policies/search?query=`, `/internal/v1/policies?number=`): в
  ingress и mesh строку запроса у `/internal/v1/policies*` маскируют, в журнал доступа Tomcat не включают `%r` и `%q`.
- База создаётся с локалью, в которой у кириллицы есть регистр: провайдер `libc` с `ru_RU.UTF-8` или `en_US.UTF-8`
  либо провайдер ICU, но не `C` или `POSIX` провайдера `libc`. Сервис сравнивает названия видов обращения и ищет по
  МКБ-10 и полисам без учёта регистра средствами PostgreSQL, а в `C` и `POSIX` регистр есть только у латиницы. Проверка
  на базе сервиса — `select lower('РВЛ и СКЛ') = 'рвл и скл';`, ответ `true`.
- Миграции Liquibase идут при старте под пользователем приложения: ему нужны права DDL на схему и CREATE на базу для
  расширения `pg_trgm`, либо расширение заранее ставит администратор базы.

## Метрики и когда тревожиться

Метрики — `/actuator/prometheus` на порту актуатора. Пороги ниже — предложение, на контуре их настраивают.

| Метрика | Что показывает | Когда тревожиться |
|---|---|---|
| `onec_ingest_deliveries_total{stream,queue,outcome}` | доставки из очередей по исходу: `stored`, `duplicate`, `quarantined`, `unidentified`, `returned`, `storage_outage` | любой рост `unidentified` (сообщение без пригодного `message-id` потеряно) или `quarantined` (тело в карантине) |
| `onec_leader` | 1 — экземпляр ведущий: читает очереди 1С:УСК и выполняет задачи по расписанию; 0 — нет | `sum(onec_leader)` не равна 1 дольше минуты: ведущего нет или их больше одного |
| `onec_ingest_paused` | 1 — приём на паузе: база не принимает записи; показатель есть у каждого экземпляра | `max(onec_ingest_paused)` держится 1: база недоступна |
| `onec_ingest_pauses_total` | сколько раз приём вставал на паузу | частый рост: база работает с перебоями |
| `onec_ingest_queues_without_consumer` | очереди 1С:УСК, которые ведущий должен читать, но у которых нет подтверждённого брокером потребителя: окно запуска, очередь, пропавшая на брокере, или брокер недоступен; на неведущем, при выключенных слушателях и на паузе из-за базы — 0 | `max(onec_ingest_queues_without_consumer) > 0` дольше 2 минут (`for: 2m`): окно запуска после получения роли или снятия паузы столько не длится, а очередь, которой нет на брокере, ведущий ищет каждые `consumer-restart-interval` (30 с) и поднимает её потребителя сам — тревога значит, что 1С:УСК не завела очередь заново или имя в `ONEC_QUEUE_*` неверно ([troubleshooting.md](troubleshooting.md), «Очередь без потребителя») |
| `onec_inbound_messages{stream,status}` | строки сырья в `NEW`, `RETRY`, `BUFFERED`, `AWAITING_PARENT`, `FAILED` | рост `max(onec_inbound_messages{status="FAILED"})` |
| `onec_inbound_pending_oldest_age_seconds{stream}` | сколько ждёт разбора самое давнее сообщение потока (`NEW` или `RETRY`) | `max by (stream)` растёт и не падает: разбор потока стоит |
| `onec_inbound_transitions_total{stream,status}` | переходы статусов при разборе | — |
| `onec_inbound_parent_wait_expired_total{stream}` | сообщения, отклонённые потому, что родитель не пришёл за срок | `increase(onec_inbound_parent_wait_expired_total[1h]) > 0` |
| `onec_price_transfers_stuck` | передачи прайса, ждущие своих частей дольше часа | `max(onec_price_transfers_stuck) > 0` |
| `onec_insured_association_transfers_stuck` | передачи связей застрахованных, ждущие своих частей дольше часа | `max(onec_insured_association_transfers_stuck) > 0` ([troubleshooting.md](troubleshooting.md), «Передача связей застрахованных не собралась») |
| `onec_inbound_backlog_staleness_seconds` | давность снимка, по которому считаются `onec_inbound_messages` и возраст ожидания | `max(onec_inbound_backlog_staleness_seconds)` намного больше 30 с: снимок не обновляется, значения выше устарели |
| `onec_retention_overdue_payloads`, `onec_retention_overdue_quarantine_bodies` | тела с персональными данными и тела карантина старше срока хранения, ещё не стёртые | `max(…) > 0` дольше двух проходов стирания (2 ч при `retention-poll-interval` 1 ч) |
| `policies_retention_overdue_personal_data` | полисы, чьи ФИО, дата рождения и почта должны быть стёрты, но ещё нет | `max(policies_retention_overdue_personal_data) > 0` дольше двух проходов стирания (2 ч) |
| `hikaricp_*{pool}` | пулы соединений: `application` (приём и разбор), `rest-read` (REST-чтения) и `leader-lock` (блокировка ведущего; `hikaricp_connections_timeout_total{pool="leader-lock"}` растёт при недоступной базе, а ещё на остановке экземпляра, если в этот момент его транзакция приёма или разбора ещё держала строку блокировки) | `increase(hikaricp_connections_timeout_total{pool="application"}[5m]) > 0`; `hikaricp_connections_pending{pool="rest-read"} > 0` дольше минуты — REST-чтений больше, чем успевает пул: следующий шаг нагрузки даёт 503 ([load-testing.md](load-testing.md)) |
| `http_server_requests_seconds_count{status,uri}` | запросы REST по статусу и шаблону пути | доля `status="503"` среди `uri=~"/internal/v1/.*"` по всем экземплярам вместе (`sum` числителя и знаменателя) выше 5 % за 10 минут |
| `rest_read_rejected_total` | запросы к `/internal/v1`, отклонённые сразу по пределу одновременно обрабатываемых (`API_MAX_CONCURRENT_REQUESTS`) | `increase(rest_read_rejected_total[5m]) > 0`: экземпляр перегружен — нагрузка выше предела, нужна ещё реплика или больше CPU; вместе с `hikaricp_connections_pending{pool="rest-read"}` — база не успевает |
| `rest_read_in_flight` | запросы к `/internal/v1` в обработке сейчас | держится у предела дольше минуты: следующий шаг нагрузки даст отказы |
| `cache_gets_total`, `cache_puts_total`, `cache_evictions_total`, `cache_size` с меткой `cache` | кэш ответов | — |
| `reference_cache_notifications_connected` | 1 — экземпляр слушает оповещения о сбросе кэша; 0 — соединения слушателя нет | хотя бы у одного экземпляра 0 дольше минуты — `min(reference_cache_notifications_connected) == 0` или правило по каждому экземпляру, не `sum()`: такой экземпляр не получает сбросов и отдаёт ответы, которые могут отставать до `REFERENCE_CACHE_TTL` |

Метрики снимка из базы (`onec_inbound_messages`, `onec_inbound_pending_oldest_age_seconds`, `onec_price_transfers_stuck`,
`onec_insured_association_transfers_stuck`, `onec_inbound_backlog_staleness_seconds`, `onec_retention_overdue_*`,
`policies_retention_overdue_personal_data`) отдаёт только ведущий; у остальных экземпляров этих рядов нет. Правила оповещения по ним строятся на `max()` по экземплярам,
а не на `sum()`: с `sum()` значение удвоилось бы, если ряды отдают два экземпляра, например в секунды смены ведущего.
Пока роль переходит, рядов может не быть ни у кого: правило с `for:` (держится N минут) это окно пропускает. Счётчики
(`*_total`) у каждого экземпляра свои, а после перезапуска пода начинаются с нуля: `increase()` и `rate()` считаются по
каждому ряду, а затем складываются через `sum()`.

Проход стирания запускается через `retention-poll-interval` после конца предыдущего, а метрики просроченного считают
строки старше срока без запаса. Поэтому между проходами значение больше нуля — норма, тревожно, когда оно не падает.

Среди компонентов `/actuator/health` — `db`, `rabbit` (соединение с брокером) и `onecIngest`. `onecIngest` в `DOWN` с
деталями `sqlstate`, `failure`, `since`, `queues` — приём на паузе из-за базы; с деталью `queuesWithoutConsumer` вне
паузы — у этих очередей нет потребителя: окно запуска, потерянная на брокере очередь или потребитель, не поднявшийся
после паузы; остановленного потребителя ведущий поднимает сам, как только очередь снова есть на брокере (раз в
`consumer-restart-interval`), то же число очередей отдаёт показатель `onec_ingest_queues_without_consumer`. При выключенных слушателях (`RABBITMQ_LISTENER_AUTO_STARTUP=false`) `onecIngest` очередей не ждёт и
отвечает `UP`. Деталь `role` называет роль экземпляра: `leader` или `standby`. Неведущий потребителей не ждёт и
отвечает `UP`, а пока его приём стоит на паузе из-за базы, отвечает `DOWN` с деталями паузы, как и ведущий.

## Сбои и ручные операции

Признаки сбоев, как их проверить и что делать — в [troubleshooting.md](troubleshooting.md). Здесь — операции, которые
меняют данные или роль экземпляра; их делают только по разбору оттуда.

- **Передать роль ведущего.** Строку `leader_lock` вручную не удаляют. Без неё транзакции приёма и разбора ведущего
  отказывают: он возвращает сообщение в очередь, отдаёт роль и участвует в выборе заново, а роль может достаться другому
  экземпляру. Чтобы передать роль, под ведущего перезапускают: при плавной остановке он отпускает роль сам.
- **Освободить блокировку миграций пропавшего пода.** Если узел с подом пропал посреди миграций (сеть, выключение), его
  сеанс в базе может жить, пока PostgreSQL не заметит обрыв соединения, и блокировка миграций держится: новые поды
  ждут её (INFO «миграции схемы накатывает другой экземпляр») и перезапускаются пробой живости. Сеанс, который держит
  блокировку, и его адрес находит запрос ниже; если пода с этим адресом нет (`kubectl get pods -o wide`), сеанс
  завершают. Его транзакция откатывается вместе с недоделанным changeSet'ом, блокировка снимается, а замок Liquibase,
  если он остался, снимет следующий экземпляр сам.

  ```sql
  select a.pid, a.client_addr, a.backend_start, a.state_change
    from pg_locks l join pg_stat_activity a on a.pid = l.pid
   where l.locktype = 'advisory' and l.granted and l.objsubid = 1
     and ((l.classid::bigint << 32) | l.objid::bigint) = 7311094201825640017;
  select pg_terminate_backend(<pid>);
  ```

  Завершить можно сеанс своего пользователя базы; чужой — с правами `pg_signal_backend`. Каждый changeSet сервиса
  выполняется в своей транзакции: прерванный при следующем старте выполняется заново.
- **Ручной возврат в `NEW`** (`FAILED` и `SKIPPED`). Строка встаёт в поток по старому моменту приёма (`received_at`,
  его ставят часы базы) и затрёт всё, что пришло после неё. `received_at` вручную не меняют. Поэтому:
  - возвращают последнее сообщение по объекту или весь хвост потока, начиная с него: тем же запросом по каждому
    `message_id` хвоста, кроме строк в `AWAITING_PARENT`, в одной транзакции;
  - только пока тело не стёрто по сроку хранения, иначе разбор отклонит его с причиной «тело сообщения стёрто по сроку
    хранения»;
  - сообщение, не дождавшееся родителя, возвращают, когда родитель уже пришёл: после возврата ожидание начинается
    заново, на полный срок;
  - сообщение в `AWAITING_PARENT` возвращать не нужно: его разберут, когда придёт родитель.

  ```sql
  update inbound_message
     set status = 'NEW', next_retry_at = null, last_error = null, processed_at = null
   where message_id = '<message-id>';
  -- передача прайса или связей застрахованных целиком
  update inbound_message
     set status = 'NEW', next_retry_at = null, last_error = null, processed_at = null
   where correlation_id = '<cid>';
  ```

  Счётчик попыток `attempt` при возврате не сбрасывается: сообщение, уже исчерпавшее повторы, при следующем временном
  сбое базы сразу получит `FAILED` («повторы исчерпаны на попытке …»).
- **Родитель, который не придёт нашими потоками.** Его признают не нашим строкой в `foreign_reference`; вид записи
  `kind` — тот же, что в `awaited_parent_kind` ожидающих сообщений (`CONTRAGENT`, `LPU_CONTRACT`, `CONTRAGENT_SERVICE`;
  третий запрос README). Ближайший проход разбора пропустит его детей, а не будет ждать. Полис (`POLICY`) не нашим не
  признают: полисы приходят без отбора, и строка с `kind = 'POLICY'` ожидание связи не снимает — она ждёт полис до
  срока:

  ```sql
  insert into foreign_reference (external_id, kind, recorded_at)
  values ('<awaited_parent_id>', '<awaited_parent_kind>', now());
  ```

- **Закрыть зависшую передачу связей застрахованных.** Передача связей, которой не хватает части, сама не закрывается:
  1С:УСК присылает выгрузку заново новой передачей с новым `cid`, а старая остаётся в `BUFFERED` и держит
  `onec_insured_association_transfers_stuck` больше нуля. Когда новая передача тех же застрахованных применена
  ([troubleshooting.md](troubleshooting.md), «Передача связей застрахованных не собралась»), старую закрывают пропуском;
  связи она не меняет, а её часть, пришедшая позже, будет пропущена:

  ```sql
  update inbound_message
     set status = 'SKIPPED', last_error = 'передача закрыта вручную: не собралась', processed_at = now()
   where stream = 'INSURED_ASSOCIATIONS' and correlation_id = '<cid>' and status = 'BUFFERED';
  ```

Почему процедуры такие — в [design.md](design.md), разделы «Разбор сырья, повторы и ручная переобработка», «Прайсы» и
«Связи застрахованных».

## Сборка и локальный запуск

Нужны JDK 21 и Docker: тесты поднимают PostgreSQL и RabbitMQ в контейнерах.

```shell
./gradlew build          # сборка и тесты
./gradlew bootJar        # только jar: build/libs/data-reference-<версия>.jar
```

Вне рабочего контура сборке нужны публичные репозитории: `./gradlew -PpublicRepositories=true …` или переменная
`ORG_GRADLE_PROJECT_publicRepositories=true`. По умолчанию сборка берёт зависимости только из Nexus контура.

Концы строк в git задаёт `.gitattributes` модуля: LF у текстовых файлов, CRLF у `*.bat`. Без него git на Windows с
`core.autocrlf=true` кладёт в рабочую копию CRLF, и `gradlew` и скрипты стенда падают в Linux-контейнере на «\r».
Кодировку, концы строк и отступы для редактора задаёт `.editorconfig` модуля, правила кода — [code-style.md](code-style.md).

Локально база и брокер поднимаются из `docker-compose.yml`. В локальном брокере нет очередей 1С, поэтому слушатели
выключаются; пароли — локального контура:

```shell
docker compose up -d
DB_PASSWORD=data_reference RABBITMQ_PASSWORD=data_reference RABBITMQ_LISTENER_AUTO_STARTUP=false \
LOGGING_STRUCTURED_FORMAT_CONSOLE= ./gradlew bootRun
curl http://localhost:8081/actuator/info
```

Пустая `LOGGING_STRUCTURED_FORMAT_CONSOLE` переключает журнал с JSON на обычный текст. Сервис в контейнере —
`docker compose --profile app up -d --build`. Образ и локальный контур описаны ниже.

Переменные окружения и настройки — разделы выше; почему значения такие — в [design.md](design.md).

### Образ

Образ собирается из `Dockerfile` модуля (нужен BuildKit). Откуда взять jar, задаёт аргумент `JAR_SOURCE`:

- `build` — собрать внутри образа, так собирает CI. Нужна сеть до Nexus и дистрибутива Gradle. Вне контура задайте
  `PUBLIC_REPOSITORIES=true`, чтобы зависимости брались из Maven Central.
- `host` — взять собранный на машине, когда у сборки нет сети:
  `./gradlew bootJar && docker build --build-arg JAR_SOURCE=host .`

В сети без выхода наружу базовые образы и Gradle берутся из зеркала Nexus (compose читает эти аргументы из `.env`,
шаблон — `.env.example`):

```shell
docker build --build-arg JDK_IMAGE=<зеркало>/eclipse-temurin:21.0.12.1_1-jdk \
             --build-arg JRE_IMAGE=<зеркало>/eclipse-temurin:21.0.12.1_1-jre \
             --build-arg GRADLE_DISTRIBUTION_URL=<зеркало>/gradle-8.14.3-bin.zip .
```

Сертификаты корпоративного центра сертификации кладутся в `certs/`: без них JVM не доверяет Nexus при сборке и брокеру
1С:УСК при работе. В слои образа они не попадают. Тесты при сборке образа не запускаются: им нужен Docker, их
прогоняет CI до сборки образа.

### Локальный контур и стенд (`docker-compose.yml`)

```shell
docker compose up -d                  # база и брокер
docker compose --profile app up -d    # и сам сервис из Dockerfile
```

Пароли локального контура известны всем, поэтому порты по умолчанию открыты только на 127.0.0.1. Чтобы к сервису и
базе ходили с других машин (например, тестировщик из Postman), задайте в `.env` `SERVICE_BIND_ADDRESS=0.0.0.0` и/или
`POSTGRES_BIND_ADDRESS=0.0.0.0`, смените пароль базы и откройте порты в брандмауэре. Брокер и актуатор остаются на
127.0.0.1. Переменные сервиса и аргументы сборки берутся из `.env` (шаблон `.env.example`), без него действуют умолчания
`application.yml` и `Dockerfile`.

Локальный брокер — не брокер 1С:УСК: очередей 1С в нём нет, поэтому слушатели 1С выключены. Чтобы проверить приём,
задайте `RABBITMQ_LISTENER_AUTO_STARTUP=true` в `.env` и заведите очереди в панели брокера (`http://localhost:15672`).

Стенд для разработчиков сервиса Договоров (профиль `stand`) — база, сервис и закладка синтетических данных 1С:
контрагентов, договоров страхования, программ и полисов. Брокер стенду не нужен. Файлы и примеры запросов —
[src/test/resources/stand/](../src/test/resources/stand/README.md).

```shell
./gradlew clean bootJar               # только при JAR_SOURCE=host
docker compose up --build stand-seed
```

- Запускайте именно `stand-seed`, а не `--profile stand`: профиль целиком поднял бы и брокер.
- Стенд готов, когда закладка напечатала «сырьё 1С заложено» и пример 09 из README стенда отвечает 200: health
  отвечает UP раньше, чем данные разобраны. Статус SKIPPED у строки страхователя в `inbound_message` ожидаем:
  страхователь — не санаторий.
- Сервис — `http://localhost:8080`; профили `app` и `stand` вместе не поднимать, порт у них один. Клиенту из другого
  контейнера нужна сеть `data-reference_default` (адрес `http://data-reference-stand:8080`) или `network_mode: host`.
- Сброс — `docker compose --profile stand down -v`. Он удаляет и базу, общую с профилем `app`, и данные брокера; только
  базу удалит `docker volume rm data-reference_postgres-data` после `down` без `-v`.
- Если Docker Hub отвечает 429 (Too Many Requests): в `.env` задайте `JAR_SOURCE=host` и
  `JRE_IMAGE=mirror.gcr.io/library/eclipse-temurin:21.0.12.1_1-jre`, а образ базы возьмите из зеркала:
  `docker pull mirror.gcr.io/library/postgres:16.10-alpine && docker tag mirror.gcr.io/library/postgres:16.10-alpine postgres:16.10-alpine`.
  В рабочем контуре все образы берутся из Nexus.

### Тестовый стенд в k3s (`devops/test/`)

Скрипт `devops/test/deploy.sh <тег>` собирает образ из `Dockerfile` модуля и выкатывает Helm-чарт `devops/test/helm` в
namespace `rvl-test`. Docker на машине стенда нет: `nerdctl` собирает образ прямо в containerd k3s, сокет и namespace
заданы в `/etc/nerdctl/nerdctl.toml`.

- На машину стенда копируется весь каталог модуля, а не только jar: jar собирается внутри образа (`JAR_SOURCE=build`).
  Чарт `devops/test/helm` при этом заменяется версией из модуля: значения, нужные только стенду, сначала переносятся в
  чарт модуля, иначе копия их затрёт.
- В `certs/` кладётся сертификат корпоративного центра (`.crt`, `.cer` или `.pem`): без него Gradle внутри образа не
  доверяет Nexus.
- Базовые образы — те же, что в `Dockerfile`, из реестра `nexus.sogaz.ru/library`; дистрибутив Gradle — тот же, что в
  `gradle/wrapper/gradle-wrapper.properties`, из зеркала Nexus; зависимости — из Nexus (`PUBLIC_REPOSITORIES=false`).
  Реестр и зеркало меняются переменными `IMAGE_REGISTRY` и `GRADLE_MIRROR`, отдельный образ или архив — `JDK_IMAGE`,
  `JRE_IMAGE`, `GRADLE_DISTRIBUTION_URL`. Через `sudo` переменная проходит только записью после него
  (`sudo IMAGE_REGISTRY=… ./devops/test/deploy.sh v3`) и только если это разрешает sudoers. Зеркало обязано отдать тот
  же архив Gradle: обёртка сверяет его контрольную сумму.
- Пароли базы и брокера — в Secret `data-reference-secret`, его создают один раз вручную; без него скрипт подсказывает
  команду и останавливается.
- Тег каждый раз новый: с прежним тегом под не пересоздаётся, и скрипт откажется собирать.
- Реплик две, выкатка плавная: `REPLICA` (2), `STRATEGY` (`RollingUpdate`; `Recreate` — все поды гасятся до запуска
  новых), `MAX_SURGE` (1), `MAX_UNAVAILABLE` (0), пауза перед остановкой `PRE_STOP_DELAY` (10 с) и
  `TERMINATION_GRACE_PERIOD` (60 с; не меньше паузы плюс 50 с) в `values.yaml` чарта. Поды обновляются по одному, каждый
  не раньше первой проверки готовности (`R_INIT_DELAY`, 60 с), поэтому выкатка двух реплик идёт несколько минут; скрипт
  ждёт её конца (`kubectl rollout status`) 10 минут ([troubleshooting.md](troubleshooting.md), «Под не становится
  готовым»).
- Куча JVM на стенде — 60 % лимита памяти пода: `jvm.options` чарта (`-XX:MaxRAMPercentage=60.0
  -XX:+ExitOnOutOfMemoryError`) уходит в под переменной `JDK_JAVA_OPTIONS` через ConfigMap и перекрывает умолчание
  образа (75 %). При 75 % и лимите 1 ГБ перегрузка REST доводила память до лимита, и ядро убивало процесс; при 60 % сервис
  отвечал 503 и сразу восстанавливался ([load-testing.md](load-testing.md)).
- Ingress стенда (`ingress.resources` в `values.yaml`) публикует снаружи `/internal/v1/lpu…`,
  `/internal/v1/insurance-contracts…`, `/internal/v1/policies…` и `/internal/v1/mkb10…`: к ручкам полисов через ingress
  обращается BFF сервиса Заявок, МКБ-10 опубликован по запросу сервиса Заявок. Своей авторизации у ручек нет, а журнал
  доступа ingress-nginx пишет строку запроса целиком, поэтому строки поиска полисов с ФИО на стенде в нём остаются. Сервис Заявок обращается к сервису внутри кластера, по адресу
  `http://data-reference:8080`, ingress ему не нужен.
- Резервные копии файлов (`*.bak`, `*.orig`, `*.swp`, `*~` и подобные), оставленные редактором рядом с `values.yaml`,
  Helm в чарт не берёт: их исключает `.helmignore` чарта.
- До сборки скрипт проверяет то, что иначе уронило бы её через несколько минут: исходники модуля и
  `certs/import-ca.sh`, сертификат в `certs/`, исполняемый `gradlew`, переводы строк LF в `gradlew` и `import-ca.sh`,
  доступ `helm` к кластеру.
- Образы старых тегов и кэш сборки сами не удаляются: место освобождают `sudo nerdctl rmi data-reference:<тег>` и
  `sudo nerdctl builder prune` (спрашивает подтверждение и удаляет только висячий кэш; `--all` удаляет весь
  неиспользуемый, вместе с кэшем зависимостей Gradle, и следующая сборка скачает их заново).
- Каталог BuildKit на стенде перенесён на `/data`: строка `root = "/data/buildkit"` в `/etc/buildkit/buildkitd.toml`
  (по умолчанию `/var/lib/buildkit`). Раздел `/var` там около 5 ГБ, а одной сборке нужно 1–1,5 ГБ под дистрибутив
  Gradle, зависимости и слои. Строка `root` стоит в начале файла, до первой секции `[…]`: в TOML ключ после заголовка
  секции относится к этой секции. После правки — `sudo systemctl restart buildkit`. Готовые образы по-прежнему хранит
  containerd k3s на `/var` (`/var/lib/rancher/k3s/agent/containerd`), поэтому образы старых тегов всё равно удаляются.

```shell
sudo ./devops/test/deploy.sh v2
```

Настройки сервиса на стенде — ConfigMap чарта (`devops/test/helm/values.yaml`). Аргументы сборки задаёт скрипт; в
ConfigMap они не нужны: его читает только под.
