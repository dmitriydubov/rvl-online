# contract-service — эксплуатация

Сборка, запуск и настройки сервиса Договоров, метрики и ручные операции. Коротко о сервисе — в [README](../README.md),
признаки известных проблем и что делать — в [troubleshooting.md](troubleshooting.md), почему он устроен так — в
[design.md](design.md).

## Стек и версии

Java 21, Spring Boot 4.0.7 (Spring Framework 7.0.8, Spring Data JPA 4.0.6, Spring AMQP 4.0.4), Hibernate ORM 7.2.19,
Liquibase 5.0.3, PostgreSQL 16 (драйвер 42.7.11, пул HikariCP 7.0.2), RabbitMQ 4.1 (клиент 5.27.1), Jackson 3.1.4,
клиент S3 MinIO Java SDK 8.6.0,
Micrometer 1.16.6 с реестром Prometheus, встроенный Tomcat 11.0.22, сборка Gradle 8.14.3. Версии библиотек задаёт BOM
Spring Boot. Версия сервиса — в `gradle.properties` (`version=`), история изменений — в [CHANGELOG.md](../CHANGELOG.md).

## Порты

- `8080` — внутренний API для сервиса Заявок (`/internal/v1/…`: загрузка справки 070/у по участнику заявки, состояние
  пакета документов по заявке, акцепт оферты договора КМ) и пробы `/livez`, `/readyz`.
- `8081` (`MANAGEMENT_PORT`) — `/actuator/health`, `/actuator/info` (версия сервиса), `/actuator/prometheus`.
- Локальный контур (`docker-compose.yml`) публикует порты со сдвигом, чтобы рядом поднимался локальный контур сервиса
  справочных данных (у него база `5432`, брокер `5672`/`15672`, сервис `8080`, актуатор `8081`): база `5433`;
  межсервисный брокер `5674`, его панель `15674`; брокер 1С:УСК `5675`, его панель `15675`; брокер маркетинга `5676`,
  его панель `15676`; сервис в контейнере
  (профиль `app`) — `8082`, его актуатор — `8083`. Внутри сети compose порты штатные.

Ведущий экземпляр (см. [design.md](design.md), «Ведущий экземпляр»): фоновую работу делает один экземпляр, роль держит
строка в таблице `leader_lock` базы сервиса; группа блокировки и сердцебиение (1 с) заданы в `application.yml`
(`projectx.leadership`):

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `LEADER_LOCK_TTL` | `30s` | срок строки блокировки ведущего: столько после гибели ведущего роль ждёт, прежде чем перейти к другому экземпляру; строго больше сердцебиения (1 с) |
| `DB_LEADER_POOL_SIZE` | `1` | соединения отдельного пула `leader-lock`, которым экземпляр берёт и продлевает строку блокировки: настройки пула и сеанса копируются с основного (адрес, учётные данные, драйвер, схема, стартовый SQL, изоляция, сроки пула, параметры драйвера), отличия — `lock_timeout` выключен (`0`) и `application_name` сеанса `contract-service-leader-lock` (так соединения роли видны в `pg_stat_activity`); продлению хватает одного соединения. Каждый экземпляр держит столько соединений к базе сверх основного пула, они открыты постоянно |

держится только при согласованных часах.

Хранилище S3 контура — справки 070/у (см. [design.md](design.md), «Справки 070/у и хранилище»). Бакет создаётся
заранее, сервис его не создаёт; на бакете нужна политика жизненного цикла, которая убирает объекты без записи в реестре
(сироты после отказа базы) и не удаляет справки раньше, чем их прочитает 1С:УСК. Учётной записи сервиса нужны права
записывать объекты, читать их метаданные и проверять наличие бакета: перед передачей договора КМ сервис спрашивает
метаданные каждой справки, а на ответ «объекта нет» — есть ли бакет. 1С:УСК нужен доступ на чтение того же бакета.

| Переменная | Умолчание | Что задаёт |
|---|---|---|
| `S3_ENDPOINT` | — | адрес S3 со схемой и портом, без слэша на конце, например `https://s3.contour:9000` |
| `S3_REGION` | `us-east-1` | регион S3; без него клиент спрашивал бы регион бакета отдельным запросом |
| `S3_BUCKET` | — | бакет справок |
| `S3_INN` | `0000000000` | ИНН организации — 10 цифр, начало ключа объекта; умолчание — заглушка, на контуре задаётся настоящий ИНН |
| `S3_KPP` | `000000000` | КПП организации — 9 цифр, идёт в ключ объекта после ИНН; умолчание — заглушка, на контуре задаётся настоящий КПП |

Сертификат внутреннего УЦ для S3 задаётся набором SSL Spring Boot, например:
`SPRING_SSL_BUNDLE_PEM_STORAGE_TRUSTSTORE_CERTIFICATE=file:/etc/contract-service/s3-ca.pem` и `S3_SSL_BUNDLE=storage`.

(`projectx.attachments.content-types`).

Имена очередей заданы в `application.yml` значениями из документа «Точки интеграций сервис Договоров и Заявок» и
переопределяются переменными `INTERNAL_QUEUE_TASK_CHANGES`, `INTERNAL_QUEUE_STATUS_CHANGES`,
`ONEC_QUEUE_KM_CONTRACT_SUBMISSIONS`, `ONEC_QUEUE_KM_CONTRACT_REGISTRATIONS`, `ONEC_QUEUE_LM_POLICY_REQUESTS`,
`ONEC_QUEUE_LM_POLICY_ISSUES`; на новом контуре их сверяют со списком очередей брокера. Два свойства с одним именем
очереди или пустое имя не дают сервису запуститься.

Оплата договоров КМ через сервис управления заказами (Ordering). Выключатель `PAYMENT_ENABLED` обязателен и
умолчания не имеет: без него сервис не стартует. При `false` заказы на оплату не создаются, сервис стартует без
настроек ниже, при старте пишет в журнал WARN «оплата выключена…», метрика `contracts_payment_disabled` равна `1`. При
`true` обязательны адреса Ordering и сервера токенов, код продукта и канал, учётные данные клиента сервера токенов и
подключение к брокеру маркетинга — без них сервис не стартует. Договоры, акцептованные при выключенной оплате, заказа не
получают и после включения: оплату включают до того, как застрахованные начнут принимать оферты договоров КМ.

Как идёт оплата. Акцепт оферты приносит адрес электронной почты плательщика и заводит заказ на оплату. Проход ведущего
создаёт заказ в Ordering и подтверждает документ; когда Ordering сообщает, что документ подтверждён, следующий проход
выставляет счёт со сроком оплаты и отдаёт ссылку на оплату сервису Заявок. Об оплате, ошибке оплаты и просрочке сервис
узнаёт из событий Ordering в очереди продукта на брокере маркетинга, а если событие не пришло — из сверки заказов по
расписанию. Оплаченный договор уходит в 1С:УСК, просроченный прекращается с причиной «истёк срок оплаты». Если работу
по договору прекратили, когда счёт по нему уже начат или выставлен и ещё ждёт оплаты (в том числе после ошибки оплаты),
прекращение откладывается: просрочка, отказ Ordering в счёте или повтор брошенного вызова выставления счёта прекращают
договор с отложенной причиной, а оплата, пришедшая раньше, переводит его в ошибку. Деньги за такую оплату, как и за
оплату после просрочки, возвращает дежурный («Возврат денег за оплату после прекращения договора»). Оплаченный договор
и договор с отклонённым счётом прекращаются сразу. Адрес плательщика хранится только до счёта: он стирается, когда
счёт выставлен, договор оплачен или прекращён.

Порядок включения оплаты:

1. Проверить доступ к брокеру маркетинга с учётными данными сервиса: соединение, виртуальный хост, право публикации
   в обменник продукта и право чтения очереди событий заказов продукта. Пока к брокеру маркетинга нет соединения или
   учётные данные неверны, подтверждения документов ждут в журнале исходящих, а события оплаты — в очереди; ответы
   сервису Заявок и передачи в 1С:УСК уходят как обычно ([troubleshooting.md](troubleshooting.md), «Брокер недоступен»).
2. Проверить, что клиент сервера токенов получает токен и Ordering принимает его, а продукт и канал заведены в Ordering.
3. Задать `PAYMENT_ENABLED=true` и настройки ниже, перезапустить экземпляры; убедиться, что `marketingBroker` и `inbox`
   в `UP` (у очереди событий заказов есть потребитель), а `contracts_payment_disabled` равна `0`.

Выключать оплату (`PAYMENT_ENABLED=false`) нельзя, пока есть заказы в работе и счета без итога: при выключенной оплате
сервис не читает очередь событий, не сверяет заказы и не отменяет их. Оплата по уже выставленному счёту осталась бы
незамеченной — договор не ушёл бы в 1С:УСК, а деньги пришлось бы искать вручную. Перед выключением запрос ниже должен
вернуть пустой результат; строки в нём — заказы, которые ещё ждут создания, счёта, оплаты, просрочки или отмены:

```sql
select o.state as order_state, i.state as invoice_state, count(*)
  from payment_orders o
  left join payment_invoices i on i.payment_order_id = o.id
 where o.state in ('AWAITING_CREATION', 'CANCEL_PENDING')
    or (o.state = 'CREATED' and i.state not in ('PAID', 'OVERDUE'))
 group by o.state, i.state;
```

| Переменная | Умолчание | Что задаёт |

| `ORDERING_READ_TIMEOUT` | `10s` | таймаут ответа Ordering на каждый вызов |

| `ORDERING_CHANNEL` | — | код канала в Ordering (`eventDetails.channel` при создании, `channel` при отмене) |

| `PAYMENT_ORDER_CREATION_INTERVAL` | `10s` | пауза между проходами создания заказов |

| `PAYMENT_ORDER_BATCH_SIZE` | `100` | сколько заказов берёт один проход |

| `PAYMENT_ORDER_AWAITING_THRESHOLD` | `1h` | сколько договор КМ может ждать заказа на оплату, прежде чем попасть в сводку |

| `PAYMENT_MIN_TERM` | `1h` | наименьший срок оплаты: если до границы накануне заезда осталось меньше, счёт не выставляется, договор прекращается с причиной «истёк срок оплаты» |
| `PAYMENT_INVOICE_AWAITING_THRESHOLD` | `30m` | сколько договор с созданным заказом может ждать счёта, прежде чем попасть в сводку `contracts_km_contracts_without_invoice_overdue` |
| `PAYMENT_RECONCILIATION_INTERVAL` | `1m` | пауза между проходами сверки заказов с Ordering |
| `PAYMENT_RECONCILIATION_THRESHOLD` | `15m` | сколько заказ без итога оплаты может не меняться, прежде чем сверка запросит его состояние у Ordering; повторный запрос по тому же заказу — не раньше чем через столько же. Через столько же сверка считает брошенным начатый вызов выставления счёта и может его повторить, поэтому значение должно быть заметно больше времени одного выставления счёта со всеми попытками: в каждой из `ORDERING_ATTEMPTS` попыток возможны запрос токена (`ORDERING_TOKEN_CONNECT_TIMEOUT` + `ORDERING_TOKEN_READ_TIMEOUT`), запрос состояния заказа и сам вызов (по `ORDERING_CONNECT_TIMEOUT` + `ORDERING_READ_TIMEOUT` на каждый), между попытками — `ORDERING_RETRY_DELAY`; при умолчаниях это около полутора минут |
| `PAYMENT_OVERDUE_GRACE` | `1h` | запас после срока оплаты: столько сервис ждёт события об оплате или просрочке, прежде чем счёт попадёт в сводку `contracts_km_invoices_without_outcome_overdue`, а счёт с ошибкой оплаты сверка закроет как просроченный |
| `PAYMENT_DOCUMENT_FIX_REPEATS` | `2` | сколько раз сверка повторяет подтверждение документа, пока Ordering держит заказ неподтверждённым; затем одно оповещение на заказ |
| `PAYMENT_SUMMARY_INTERVAL` | `1m` | как часто пересчитываются сводки счетов |

Брокер маркетинга — третий брокер, только при включённой оплате: туда сервис публикует подтверждение документа заказа в
обменник продукта и оттуда читает события заказов из очереди продукта. Подключение настраивается как у двух других брокеров переменными `RABBITMQ_MARKETING_HOST`,
`RABBITMQ_MARKETING_PORT` (умолчание `5672`), `RABBITMQ_MARKETING_VHOST`, `RABBITMQ_MARKETING_USERNAME`,
`RABBITMQ_MARKETING_PASSWORD`, `RABBITMQ_MARKETING_SSL_ENABLED`, `RABBITMQ_MARKETING_SSL_VALIDATE_CERTIFICATE`,
`RABBITMQ_MARKETING_SSL_VERIFY_HOSTNAME`; хост, логин и пароль умолчаний не имеют. Обменник и ключ маршрутизации
подтверждения документов — `MARKETING_DOCUMENT_FIXES_EXCHANGE` (`<продукт>.exchange`) и
`MARKETING_DOCUMENT_FIXES_ROUTING_KEY` (`<продукт>-contract-fixed`), без умолчаний. Очередь событий заказов продукта —
`MARKETING_ORDER_EVENTS_QUEUE` (`order.event.<продукт>.topic`), тоже без умолчания; читать ли её, задаёт
`RABBITMQ_MARKETING_LISTENER_AUTO_STARTUP`, как у двух других брокеров. Учётной записи сервиса на брокере маркетинга нужны
право публикации (`write`) в обменник продукта и право чтения (`read`) очереди событий заказов; объявлять обменник и
очереди сервис не будет — их заводит Ordering. Обработчик события выбирается по полю `eventType` тела, ключ
маршрутизации доставки сервис не читает.

Таймауты сеанса пишутся с единицами PostgreSQL (`ms`, `s`, `min`): число без единицы PostgreSQL читает как
миллисекунды. Почему настройки такие — в [design.md](design.md), переменные с описанием — в шаблоне `.env.example`.

## Сборка и локальный запуск

Нужны JDK 21 и Docker: тесты поднимают PostgreSQL, RabbitMQ и хранилище S3 (MinIO) в контейнерах. Образ MinIO задаёт
`TEST_MINIO_IMAGE` (по умолчанию `chainguard/minio`, закреплённый по хешу); в контуре — образ MinIO из корпоративного
реестра, префикс реестра — как у остальных образов, `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`. Без Docker тесты берут базу из
`TEST_POSTGRES_URL` и брокер из `TEST_RABBITMQ_URL` (`amqp://логин:пароль@хост:порт/vhost`, отдельный тестовый брокер,
не рабочий); без Docker и без адресов они падают, а не пропускаются. Тестам хранилища S3 Docker нужен всегда. Тест
брокера маркетинга (`MarketingBrokerIT`) работает в обоих режимах: с контейнером он заводит брокеру маркетинга отдельный
виртуальный хост, а с `TEST_RABBITMQ_URL` берёт тот же адрес и виртуальный хост из URL и отделяется именами обменника и
очередей — учётной записи из URL нужны права на объявление обменника и очередей.

```shell
./gradlew build          # сборка и тесты
./gradlew bootJar        # только jar: build/libs/contract-service-<версия>.jar
```

Вне рабочего контура сборке нужны публичные репозитории: `./gradlew -PpublicRepositories=true …` или переменная
`ORG_GRADLE_PROJECT_publicRepositories=true`. По умолчанию сборка берёт зависимости только из Nexus контура.

Концы строк в git задаёт `.gitattributes` модуля: LF у текстовых файлов, CRLF у `*.bat`. Без него git на Windows с
`core.autocrlf=true` кладёт в рабочую копию CRLF, и `gradlew` и `certs/import-ca.sh` падают в Linux-контейнере на «\r».
Кодировку, концы строк и отступы для редактора задаёт `.editorconfig` модуля, правила кода —
[code-style.md](code-style.md).

Локально база и брокеры (межсервисный, 1С:УСК и маркетинга) поднимаются из `docker-compose.yml`, пароли — локального контура:

```shell
docker compose up -d
DB_PASSWORD=contract_service RABBITMQ_INTERNAL_PASSWORD=contract_service RABBITMQ_ONEC_PASSWORD=contract_service \
  REFERENCE_URL=http://localhost:8080/internal/v1 S3_ENDPOINT=http://localhost:9000 S3_BUCKET=contracts \
  S3_ACCESS_KEY=local S3_SECRET_KEY=local-secret PAYMENT_ENABLED=false LOGGING_STRUCTURED_FORMAT_CONSOLE= ./gradlew bootRun
curl http://localhost:8081/actuator/health
```

Пустая `LOGGING_STRUCTURED_FORMAT_CONSOLE` переключает журнал с JSON на обычный текст. `PAYMENT_ENABLED` обязателен:
без него сервис не стартует; с `true` нужны и настройки оплаты из таблицы выше. Очередей соседей в локальных
брокерах нет: их заводят вручную в панелях брокеров, а пока их нет, слушателей выключают
(`RABBITMQ_INTERNAL_LISTENER_AUTO_STARTUP=false`, `RABBITMQ_ONEC_LISTENER_AUTO_STARTUP=false`; профиль `app` делает это
сам). Справочники сервис ждёт от локального контура сервиса справочных данных (`docker compose --profile stand up -d` в
его каталоге, адрес `REFERENCE_URL=http://localhost:8080/internal/v1`); без него старт проходит, а чтение справочника
заканчивается ошибкой «справочник недоступен». Сервис в контейнере — `docker compose --profile app up -d
--build`: API на `8082`, актуатор на `8083`, а до справочников контейнер ходит по сети локального контура
data-reference (`data-reference_default`, адрес `http://data-reference-stand:8080/internal/v1`), поэтому стенд
data-reference должен быть поднят раньше: на машине он слушает только 127.0.0.1, и из контейнера туда не попасть.
Другой адрес задаётся `REFERENCE_URL` в `.env`. Хранилища S3 в локальном контуре нет: настройки S3 обязательны для
старта, но к хранилищу сервис обращается только при загрузке справки, и без S3 загрузка отвечает 503
`STORAGE_UNAVAILABLE`. Профиль `app` задаёт S3 локальные значения (адрес `http://s3.local:9000`, бакет `contracts`);
своё хранилище подключается переменными `S3_*` в `.env`. Оплату профиль `app` по умолчанию выключает
(`PAYMENT_ENABLED=false`). Пароли локального контура известны всем, поэтому порты по умолчанию открыты только на
127.0.0.1; открыть API и базу для других машин можно переменными
`SERVICE_BIND_ADDRESS` и `POSTGRES_BIND_ADDRESS` в `.env` (шаблон `.env.example`), брокеры и актуатор остаются
на 127.0.0.1.

### Образ

Образ собирается из `Dockerfile` модуля (нужен BuildKit). Откуда взять jar, задаёт аргумент `JAR_SOURCE`:

- `build` — собрать внутри образа, так собирает CI. Нужна сеть до Nexus и дистрибутива Gradle. Вне контура задайте
  `PUBLIC_REPOSITORIES=true`, чтобы зависимости брались из Maven Central.
- `host` — взять собранный на машине, когда у сборки нет сети:
  `./gradlew bootJar && docker build --build-arg JAR_SOURCE=host .`

В сети без выхода наружу базовые образы и Gradle берутся из зеркала Nexus (аргументы `JDK_IMAGE`, `JRE_IMAGE`,
`GRADLE_DISTRIBUTION_URL`). Сертификаты корпоративного центра сертификации кладутся в `certs/`: без них JVM не
доверяет Nexus при сборке. В слои образа они не попадают. Тесты при сборке образа не запускаются: им нужен Docker,
их прогоняет CI до сборки образа.

### Тестовый стенд в k3s (`devops/test/`)

Скрипт `devops/test/deploy.sh <тег>` собирает образ из `Dockerfile` модуля и выкатывает Helm-чарт `devops/test/helm` в
namespace `rvl-test`, одной репликой. Docker на машине стенда нет: `nerdctl` собирает образ прямо в containerd k3s.

```shell
sudo ./devops/test/deploy.sh v1
```

**Перед первой выкаткой** нужны три вещи:

1. Значения базы в `devops/test/helm/values.yaml`: `postgres.host`, `postgres.port`, `postgres.database`,
   `postgres.username` (из них собираются `DB_URL` и `DB_USERNAME`). Пока они пусты, чарт не рисуется и называет первое
   пустое значение (`postgres.host is empty: …`); скрипт проверяет это до сборки образа.
2. Secret `contract-service-secret`, его создают один раз вручную. Шаблона Secret в чарте нет: всё, что рисует чарт,
   Helm хранит в истории релизов, а пароли и ключи там быть не должны. Без Secret скрипт печатает команду и
   останавливается:

   ```shell
   kubectl -n rvl-test create secret generic contract-service-secret \
     --from-literal=DB_PASSWORD='...' \
     --from-literal=RABBITMQ_INTERNAL_PASSWORD='...' \
     --from-literal=RABBITMQ_ONEC_PASSWORD='...' \
     --from-literal=S3_ACCESS_KEY='...' --from-literal=S3_SECRET_KEY='...'
   ```

   `RABBITMQ_INTERNAL_PASSWORD` — любая непустая строка, пока межсервисного брокера нет (ниже). Смена Secret под сам не
   перезапускает: `kubectl -n rvl-test rollout restart deploy/contract-service`. Смена значений в ConfigMap
   перезапускает его сама (аннотация `checksum/config`).
3. В `certs/` кладутся сертификат корпоративного центра (`.crt`, `.cer` или `.pem`: без него Gradle внутри образа не
   доверяет Nexus) и сертификат центра сертификации брокера 1С:УСК. Сервис доверяет брокерам по хранилищу JVM, а не по
   набору SSL Spring (`BrokerConnectionFactories`; переменных `SPRING_RABBITMQ_SSL_BUNDLE` и тома с сертификатом, как у
   сервиса справочных данных, здесь нет), и `certs/import-ca.sh` добавляет файлы из `certs/` в хранилище образа при
   сборке. Тот же сертификат уже лежит на стенде в ConfigMap `rabbitmq-ca` (ключ `ca.pem`), который создан для сервиса
   справочных данных:

   ```shell
   kubectl -n rvl-test get configmap rabbitmq-ca -o jsonpath='{.data.ca\.pem}' > certs/onec-broker-ca.pem
   ```

   Без него соединение с брокером 1С:УСК не устанавливается (`onecBroker` в `DOWN`).

На машину стенда копируется весь каталог модуля, а не только jar: jar собирается внутри образа (`JAR_SOURCE=build`).
Базовые образы и дистрибутив Gradle скрипт берёт из реестра и зеркала Nexus (`IMAGE_REGISTRY`, `GRADLE_MIRROR`; отдельный
образ или архив — `JDK_IMAGE`, `JRE_IMAGE`, `GRADLE_DISTRIBUTION_URL`), зависимости — из Nexus
(`PUBLIC_REPOSITORIES=false`). Тег каждый раз новый: с прежним тегом под не пересоздаётся, и скрипт откажется собирать.
До сборки скрипт проверяет исходники и `certs/import-ca.sh`, сертификат в `certs/`, исполняемый `gradlew`, переводы строк
LF, доступ `helm` к кластеру, наличие Secret и то, что чарт рисуется.

**Значения стенда** (`values.yaml`; чарт превращает их в переменные окружения из раздела «Переменные окружения» и три стандартных — `SERVER_PORT`, `LOGGING_LEVEL_ROOT` Spring Boot и `JDK_JAVA_OPTIONS` JVM):

| Что | Значение на стенде |
|---|---|
| Реплик | `REPLICA` 1, `STRATEGY` `RollingUpdate`, `MAX_SURGE` 1, `MAX_UNAVAILABLE` 0 |
| Пробы | готовность `/readyz`, живость `/livez`, оба на порту 8080; от брокеров, базы и роли ведущего они не зависят |
| Остановка | `PRE_STOP_DELAY` 10 с, `TERMINATION_GRACE_PERIOD` 60 с: пауза, остановка сервиса (30 с, `spring.lifecycle.timeout-per-shutdown-phase`) и запас |
| Метрики | аннотации Prometheus на порт 8081, `/actuator/prometheus` |
| Брокер 1С:УСК | `s00-0000-rt14.sogaz.ru:5671`, virtual host `/`, пользователь `rvl-online`, TLS, проверка сертификата и имени хоста включены |
| Справочный сервис | `REFERENCE_URL=http://data-reference:8080/internal/v1`: внутри кластера, тот же namespace; базовый путь `/internal/v1` обязателен, без него запросы справочника уходят на несуществующие адреса |
| S3 | `S3_ENDPOINT=http://s00-0000-s301:9000` (без TLS), `S3_BUCKET=00-0000-edo-bucket`, `S3_REGION=us-east-1`; `S3_INN` и `S3_KPP` не заданы, ключ объекта собирается с заглушками из `application.yml` |
| Оплата | `PAYMENT_ENABLED=false` (ровно `false`); Ordering и брокер маркетинга не настраиваются |
| JVM | `-XX:MaxRAMPercentage=60.0 -XX:+ExitOnOutOfMemoryError` через `JDK_JAVA_OPTIONS`, память пода 512 МиБ — 1 ГиБ, процессор 100 мс — 1 ядро; каждая одновременная загрузка справки держит в памяти до 10 МБ, для нагрузочной проверки загрузок лимит памяти поднимают |

**Выкатка без простоя.** Новый под поднимается рядом со старым (`MAX_SURGE` 1), старый гасится, когда новый прошёл
проверку готовности (`MAX_UNAVAILABLE` 0), и на время выкатки работают два экземпляра. Синхронные вызовы отвечает каждый
из них. Фоновую работу ведёт один ведущий (строка `leader_lock`): новый экземпляр остаётся неведущим, пока старый не
отпустит роль. При плавной остановке старый отпускает её сам после паузы `PRE_STOP_DELAY`, и новый берёт роль за
одно-два сердцебиения; если старый убит без остановки, роль переходит через `LEADER_LOCK_TTL` (30 с). Готовность нового
пода от роли не зависит, поэтому до остановки старого он готовым становится сразу. Скрипт ждёт конца выкатки
(`kubectl rollout status`) 10 минут: первая проверка готовности наступает через `R_INIT_DELAY` (60 с).

**Что на стенде не работает.**

- Межсервисного брокера (между сервисами Договоров и Заявок) пока нет. Слушатель выключен
  (`RABBITMQ_INTERNAL_LISTENER_AUTO_STARTUP=false`), а хост, порт, пользователь и пароль нужны сервису непустыми для
  старта (`BrokerConnectionProperties`): хост, порт и пользователь берутся из умолчаний `application.yml`
  (`localhost`, `5674`, `contract_service`), пароль — заглушка из Secret. Соединения никто не слушает, и компонент
  здоровья `internalBroker` в `DOWN`, а `/actuator/health` отвечает 503; пробы `/readyz` и `/livez` от этого не
  зависят.
- Задачи на выпуск от сервиса Заявок на стенд не приходят, поэтому на корректный запрос ручки по заявке отвечают
  404 `REQUEST_NOT_FOUND` по любой заявке, а акцепт оферты — 404 `CONTRACT_NOT_FOUND`: договоров на стенде нет. Проверить работу этих ручек на стенде можно,
  только когда появится брокер и задачи.
- Оплата выключена: заказы и счета не создаются, брокер маркетинга и Ordering не используются
  (`marketingBroker` в `/actuator/health` нет).
- Справки пишутся в S3 без TLS и с заглушками ИНН и КПП в ключе объекта; их на стенде не меняют, пока не задан
  настоящий ИНН и КПП организации.

**Ingress** публикует снаружи `https://s00-0000-rvl8.sogaz.ru/contract-service/internal/v1/requests…` и
`…/internal/v1/contracts…` (класс `nginx`, TLS-секрет `hr-activity-tls`, тот же хост, что у сервиса справочных данных,
путь у каждого сервиса свой). Предел тела запроса `ingress.proxyBodySize` — 10 МБ, как предел запроса сервиса
(`spring.servlet.multipart.max-request-size`): значение по умолчанию у ingress-nginx, 1 МБ, справку не пропустило бы.
Своей авторизации у ручек нет, поэтому снаружи их вызовет любой, у кого есть доступ к ingress стенда; сервис Заявок
обращается к сервису внутри кластера по адресу `http://contract-service:8080`, ingress ему не нужен.

Образы старых тегов и кэш сборки сами не удаляются: `sudo nerdctl rmi contract-service:<тег>` и
`sudo nerdctl builder prune`.

делать, когда сработало оповещение, — в [troubleshooting.md](troubleshooting.md).

| `contracts_payment_term_expired_total` | договор КМ прекращён с причиной «истёк срок оплаты» ещё до счёта: граница накануне заезда прошла до создания заказа или до выставления счёта либо до неё осталось меньше `PAYMENT_MIN_TERM` | рост без срочности: выяснить, почему счёт не успел |

Договор, оплаченный после прекращения, сюда не попадает — он уже учтён в `contracts_km_contracts_paid_after_cancellation_total` | любой рост |

Что делать по счётчикам и сводкам оплаты — [troubleshooting.md](troubleshooting.md), «Оплата через Ordering».

Сводки ожидания ответа 1С:УСК (`contracts_*_awaiting_*`) отдаёт только ведущий экземпляр, у неведущего этих рядов нет:
при нескольких экземплярах правила строятся по `max()` по экземплярам, а не по сумме.

Пулы соединений базы — метрики `hikaricp_*` с меткой `pool="application"` (основной) и `pool="leader-lock"` (блокировка
ведущего, `DB_LEADER_POOL_SIZE` соединений). Подключения брокеров — метрики `rabbitmq_*` с меткой `name="internalBroker"`
или `name="onecBroker"`, при включённой оплате — ещё `name="marketingBroker"`.

Состояние базы и брокеров — компоненты `/actuator/health`: `db`, брокеры — `internalBroker` и `onecBroker`, при включённой оплате — ещё `marketingBroker`; приём из
очередей — компонент `inbox` с деталью `role` (`leader` / `standby`). У ведущего `UP` — у каждой очереди из настроек,
которую он читает (при включённой оплате — и у очереди событий заказов), есть потребитель, подписку которого подтвердил
брокер; `DOWN` (ответ 503) с деталью `queuesWithoutConsumer`
(имена очередей по алфавиту) — у очереди нет потребителя; `DOWN` с деталями `sqlstate`, `failure` (тип отказа), `since`,
`queues` (остановленные очереди) — приём на паузе из-за недоступной базы, перечня очередей без потребителя в это время
нет. Неведущий потребителей не ждёт и отвечает `UP`. Оповещение — `inbox` в `DOWN` с `queuesWithoutConsumer` дольше
минуты: у этого состояния нет метрики, правило строится на ответе `/actuator/health`. Пробы `/livez` и `/readyz` от
компонента не зависят: недоступную базу или очередь на брокере перезапуск экземпляра не починит.

## Сбои и ручные операции

Признаки сбоев, как их проверить и что делать — в [troubleshooting.md](troubleshooting.md). Здесь — операции, которые
меняют данные или роль экземпляра; их делают только по разбору оттуда.

### Ведущий экземпляр

Строку `leader_lock` вручную не удаляют: просроченную забирает живой экземпляр сам. Чтобы передать роль, под ведущего
перезапускают: при плавной остановке он отпускает роль сам, и она переходит к другому экземпляру за одно-два
сердцебиения. Кто ведущий — [troubleshooting.md](troubleshooting.md), «Ведущий экземпляр».

**Проверка перехода роли на стенде** (при установке версии с несколькими экземплярами):

1. Увидеть ведущего: `contracts_leader` равна `1` ровно у одного экземпляра, у него же `/actuator/health` отдаёт в
   компоненте `inbox` деталь `role: leader` (у остальных `standby`), запрос из [troubleshooting.md](troubleshooting.md),
   «Ведущий экземпляр», показывает его `client_id`.
2. Опубликовать в очередь задач сервиса Заявок несколько тестовых задач и плавно остановить под ведущего (SIGTERM, как при
   обновлении). Ожидание: строка `leader_lock` переходит к другому экземпляру за одно-два сердцебиения (секунды), у него
   `contracts_leader` становится `1`, компонент `inbox` — `UP` без `queuesWithoutConsumer`, накопившиеся задачи попадают в
   `inbox_messages` по одному разу (одна строка на `message_id`).
3. Повторить с гибелью: убить под ведущего без остановки (SIGKILL или удаление пода с нулевым сроком ожидания). Ожидание:
   строка `leader_lock` просрочивается, и роль переходит через `LEADER_LOCK_TTL` (по умолчанию 30 с) после последнего
   продления; задачи, опубликованные в это время, ждут в очереди и принимаются новым ведущим по одному разу. Роль не
   переходит дольше двух `LEADER_LOCK_TTL` — сверить часы подов (раздел «Переменные окружения») и доступность базы с каждого
   экземпляра.

### Возврат отклонённого входящего сообщения в разбор

Сообщение журнала входящих, отклонённое окончательно (`FAILED`), сервис сам больше не разбирает. Когда причина
устранена — полис дошёл до справочного сервиса, база или справочник снова доступны, — дежурный возвращает сообщение
одним запросом по его `message_id` (найти отклонённые — [troubleshooting.md](troubleshooting.md), «Входящее отклонено
окончательно»):

```sql
update inbox_messages
   set status = 'NEW', attempts = 0, error_message = null, next_attempt_at = null
 where message_id = '<message-id>'
   and status = 'FAILED'
   and payload is not null;
```

Ближайший проход разбора берёт его как только что принятое: с первой попытки и с полной лестницей
`INBOX_RETRY_BACKOFF`. Запрос возвращает только отклонённые сообщения с телом: обработанное, пропущенное или ждущее
разбора сообщение он не трогает, а сообщение со стёртым по сроку телом разобрать уже нечем — `update` сообщит
`0` строк. Задачу сервиса Заявок возвращать имеет смысл, только если по заявке не обработана задача с большей версией:
иначе разбор пропустит её как устаревшую. Возврат счётчик `contracts_inbox_failed_total` не уменьшает; новый
окончательный отказ после возврата посчитается снова. Тело стирается по сроку от приёма при любом статусе: сообщение,
возвращённое незадолго до конца `INBOX_PAYLOAD_RETENTION`, может потерять тело посреди лестницы повторов и будет
отклонено с причиной «тело сообщения стёрто по сроку хранения».

### Возврат договора КМ, не переданного в 1С:УСК, в оплаченные

Договор КМ переходит в ERROR с кодом `KM_CONTRACT_SUBMISSION_UNDELIVERED`, когда журнал исходящих окончательно отклонил
его передачу (нет очереди у 1С:УСК, исчерпана лестница повторов, стёрто тело), с кодом
`KM_CONTRACT_SUBMISSION_PREPARATION_FAILED`, когда передачу не удалось подготовить (внутренняя ошибка, нет файла справки в
хранилище), и с кодом справочника, когда запись справочника не найдена или в архиве: `PROGRAM_NOT_FOUND`,
`PROGRAM_ARCHIVED`, `INSURANCE_CONTRACT_NOT_FOUND`, `INSURANCE_CONTRACT_ARCHIVED`, `POLICY_NOT_FOUND`, `POLICY_ARCHIVED`. Новой записи по такому договору задача сервиса Заявок не заводит: деньги по нему уже заплачены. Это правило
действует для любого оплаченного договора в ERROR, какой бы ни был код ошибки. Изменения из следующих задач к нему не
применяются — в журнале сервиса WARN «договор КМ оплачен, изменения из задачи версии N не применены», договор остаётся в
ошибке с прежним кодом. Если задача исключила участника из поездки или у него исчезла доплата, договор прекращается
(CANCELLED, причина OTHER), и вернуть его этой процедурой нельзя: деньги за него возвращают («Возврат денег за оплату
после прекращения договора» ниже). Когда причина устранена — очередь у брокера 1С:УСК
восстановлена, объект справки на месте, дефект данных исправлен ([troubleshooting.md](troubleshooting.md), «Обмен с
1С:УСК»), — дежурный возвращает договор в оплаченные одним запросом по его идентификатору. При коде справочника дежурный
сначала убеждается у сервиса справочных данных, что запись — программа, договор страхования или полис страхователя из
задачи — есть и не в архиве: запрос этого не проверяет, и договор с прежней записью вернётся в ERROR на ближайшем проходе.

При коде `KM_CONTRACT_SUBMISSION_UNDELIVERED` дежурный сначала сверяется с 1С:УСК. Отклонённая окончательно передача
могла дойти: сервис не всегда знает, что брокер получил сообщение («Возврат денег за оплату после прекращения договора»
ниже). Ответ 1С:УСК сервис относит к договору по его идентификатору, а не по `message_id` передачи: ответ, пришедший,
пока договор в ERROR, не применяется (сообщение обработано, в журнале — WARN «… результат регистрации получен по
договору КМ в статусе ERROR, запись не изменена»), а после возврата ближайший проход пишет новую передачу того же
договора с новым `message_id`, и сервис применит первый ответ, пришедший после неё, по какой бы из передач он ни был.
Поэтому дежурный спрашивает 1С:УСК по `message_id` каждой отклонённой передачи договора (журнал исходящих:
`aggregate_type` `CONTRACT`, `aggregate_id` — идентификатор договора, статус `FAILED`; после прежних возвратов таких
строк несколько), получала ли она этот договор и не ждёт ли такая передача разбора в её очереди. Получала или передача
ждёт — договор не возвращают, а разбирают вместе с 1С:УСК; не получала — возвращают запросом ниже.

```sql
update contracts
   set status = 'PAID', error_code = null, error_message = null, entity_version = entity_version + 1,
       updated_at = now()
 where id = '<contract-id>'
   and status = 'ERROR'
   and paid_at is not null
   and error_code in ('KM_CONTRACT_SUBMISSION_UNDELIVERED', 'KM_CONTRACT_SUBMISSION_PREPARATION_FAILED',
                      'PROGRAM_NOT_FOUND', 'PROGRAM_ARCHIVED', 'INSURANCE_CONTRACT_NOT_FOUND',
                      'INSURANCE_CONTRACT_ARCHIVED', 'POLICY_NOT_FOUND', 'POLICY_ARCHIVED');
```

Ближайший проход подготовки передач берёт договор как оплаченный и пишет новую передачу с новым `message_id` и
новой версией договора; отклонённая запись журнала исходящих остаётся в истории. Запрос трогает только оплаченный
договор (с моментом оплаты) в ERROR с одним из перечисленных кодов: договор, который 1С:УСК отклонила ответом (код
ошибки 1С:УСК), договор без программы в задаче (`PROGRAM_REQUIRED` — он не оплачен), договор, оплаченный после
прекращения (`KM_CONTRACT_PAID_AFTER_CANCELLATION` — по нему возвращают деньги, см. ниже), и договор в любом другом
состоянии он не меняет — `update` сообщит `0` строк. Сервис Заявок о возврате не узнаёт (оплаченный и переданный договор
наружу не публикуются) и получит следующий снимок по заявке, когда 1С:УСК ответит. Не устранённая причина вернёт договор
в ERROR на ближайшем проходе.

Повторная задача сервиса Заявок новой записи по оплаченному договору в ERROR не заводит, поэтому второго договора
участника рядом с ним нет. Исключение — договоры, по которым новая запись была открыта прежней версией сервиса: тогда
запрос упадёт на уникальном индексе `uq_contracts_active_insured_participant`, а не вернёт `0` строк, и договор не
возвращают, а разбирают вместе с владельцем данных.

Полис ЛМ в ERROR (`LM_POLICY_REQUEST_UNDELIVERED`, `LM_POLICY_REQUEST_PREPARATION_FAILED`) дежурный не возвращает: после
устранения причины новый запрос уходит по новой записи, которую создаёт следующая задача сервиса Заявок с большей
версией.

### Возврат отклонённого заказа на оплату в работу

Заказ на оплату договора КМ отклоняется, когда Ordering отказал в создании по существу (в `rejection_code` — код ошибки
Ordering или `HTTP <код>`, если ответ без тела) или когда подтверждение документа не доставлено на брокер маркетинга
(`FIXED_UNDELIVERED`). Договор при этом остаётся акцептованным, сервис Заявок ничего не получает, сервис сам заказ в
работу не возвращает; если заказ не вернуть до границы накануне заезда, сверка закроет его и прекратит договор с
причиной «истёк срок оплаты». Когда причина устранена — Ordering завёл наш продукт и канал, у брокера маркетинга есть
обменник и права публикации ([troubleshooting.md](troubleshooting.md), «Оплата через Ordering»), — дежурный возвращает
заказ одним запросом по идентификатору договора:

```sql
update payment_orders
   set state = 'AWAITING_CREATION', rejection_code = null, external_order_id = null, updated_at = now()
 where contract_id = '<contract-id>'
   and state = 'REJECTED'
   and contract_id in (select id from contracts where status = 'ACCEPTED');
```

Ближайший проход создания берёт заказ заново с прежними `correlationId` и идентификатором документа. Запрос на создание
уже отправлялся, поэтому проход сначала ищет заказ клиента по идентификатору документа: заказ, созданный до отказа
подтверждения, находится, и подтверждение документа уходит заново; иначе заказ создаётся. Запрос трогает только
отклонённый заказ акцептованного договора — заказ в любом другом состоянии и заказ договора, который уже прекращён или
ушёл дальше акцепта, он не меняет, `update` сообщит `0` строк. Не устранённая причина снова
отклонит заказ на ближайшем проходе. Счётчик `contracts_payment_orders_rejected_total` возврат не уменьшает.

Заказ в состоянии «отмена отклонена» (`CANCEL_REJECTED`) этой процедурой не возвращают: договор уже прекращён, а заказ
отменяют в Ordering вместе с его командой. Заказ, по которому Ordering отказал в счёте, остаётся созданным (`CREATED`),
отклонён у него счёт — этот запрос его не трогает, для него процедура ниже.

### Возврат заказа с отклонённым счётом в работу

Ordering может отказать в выставлении счёта по существу: заказ создан и документ подтверждён, но вызов выставления счёта
отклонён. Запись счёта (`payment_invoices`) переходит в `REJECTED` с кодом отказа в `rejection_code` (код ошибки Ordering
или `HTTP <код>`), растёт `contracts_payment_orders_rejected_total`, в журнале — ERROR «Ordering отклонил выставление
счёта, код …». Договор остаётся акцептованным, сервис Заявок ничего не получает, адрес плательщика хранится, сервис сам
счёт больше не выставляет. Если работу по договору прекратят, он прекратится сразу, как договор без счёта; если до
границы накануне заезда ничего не изменится, сверка закроет заказ и прекратит договор с причиной «истёк срок оплаты».

Иначе бывает, когда работу по договору прекратили, пока шёл вызов выставления счёта: прекращение тогда было отложено, и
отказ в счёте применяет его сразу. Договор прекращён (`CANCELLED`) с той причиной, с которой его прекращали, заказ уходит
к отмене (`CANCEL_PENDING`), адрес плательщика стёрт; в журнале рядом с ERROR об отказе — INFO «счёт отклонён, отложенное
прекращение договора применено». Возвращать такой заказ в работу не нужно, запрос ниже его не возьмёт (`0` строк).

Когда причина отказа устранена на стороне Ordering, дежурный возвращает заказ в работу одним запросом по идентификатору
договора:

```sql
update payment_invoices
   set state = 'READY', rejection_code = null, checkout_started_at = null, payment_deadline = null,
       updated_at = now()
 where contract_id = '<contract-id>'
   and state = 'REJECTED'
   and contract_id in (select id from contracts where status = 'ACCEPTED')
   and payment_order_id in (select id from payment_orders where state = 'CREATED' and payer_email is not null);
```

Ближайший проход выставления счетов повторяет вызов с прежними номером заказа и `correlationId` и с адресом из заказа;
срок оплаты считается от нового момента. Запрос трогает только отклонённый счёт созданного заказа акцептованного
договора, у которого сохранён адрес плательщика: заказ без адреса, счёт в любом другом состоянии и заказ прекращённого
договора он не меняет — `update` сообщит `0` строк. Не устранённая причина снова отклонит счёт на ближайшем проходе.

### Стирание адреса плательщика у заказа с отклонённым счётом

Причину отказа в счёте сервис не различает: текст ошибки Ordering он не хранит и не разбирает. Если дежурный вместе с
командой Ordering выяснил, что счёт отклонён из-за адреса электронной почты плательщика, заказ в работу не возвращают —
с тем же адресом отказ повторится. Адрес — персональные данные, и хранить его дальше незачем; дежурный стирает его одним
запросом по идентификатору договора:

```sql
update payment_orders
   set payer_email = null, updated_at = now()
 where contract_id = '<contract-id>'
   and state = 'CREATED'
   and id in (select payment_order_id from payment_invoices where state = 'REJECTED');
```

Состояние заказа, счёта и договора запрос не меняет. Заказ без адреса процедура возврата в работу не берёт, счёт по нему
не выставляется; договор ждёт прекращения работы по заявке или границы накануне заезда. Застрахованному оформляют новый
договор новой задачей сервиса Заявок после прекращения этого.

### Возврат денег за оплату после прекращения договора

Оплата может прийти по договору, работа по которому уже прекращена: застрахованный успел оплатить выставленный счёт
после прекращения работы по заявке, исключения участника или смены вида документа. Сервис отменить выставленный счёт не
может, поэтому прекращение такого договора он откладывает до просрочки (о ней сообщает событие Ordering или её
признаёт сверка), а наружу сразу показывает договор
прекращённым. Если вместо просрочки приходит оплата, договор переходит в ERROR с кодом
`KM_CONTRACT_PAID_AFTER_CANCELLATION`, растёт `contracts_km_contracts_paid_after_cancellation_total`, в журнале — ERROR
«оплата поступила после прекращения работы по договору». Тот же счётчик растёт, когда оплата пришла уже после
просрочки — по событию или признанной сверкой: с ERROR «оплата поступила по договору, прекращённому по просрочке», если
причина прекращения договора (`contracts.cancel_reason`) — `EXPIRED`, и с ERROR «оплата поступила по договору, который
не ждёт оплаты, статус CANCELLED», если просрочка применила отложенное прекращение с другой причиной. Такой договор в
1С:УСК не уходит, оплаченным не считается, следующая задача сервиса Заявок заводит участнику новую запись.

Что делает дежурный:

1. По записи журнала с ERROR берёт идентификатор договора (`contractId`) и находит заказ и счёт запросом только на
   чтение:

   ```sql
   select o.external_order_id, i.invoice_id, i.paid_at, c.number, c.premium_amount, c.status, c.error_code
     from contracts c
     join payment_orders o on o.contract_id = c.id
     join payment_invoices i on i.payment_order_id = o.id
    where c.id = '<contract-id>';
   ```

2. Передаёт команде Ordering номер заказа, идентификатор счёта, момент оплаты и сумму для возврата денег плательщику.
   Возврат выполняется на стороне Ordering и платёжной системы; сервис в возврате не участвует и события о нём не ждёт.
3. В базе сервиса ничего не меняет: договор остаётся в ERROR или прекращённым, запись счёта хранит момент оплаты.
   Процедура возврата договора в оплаченные такой договор не берёт.

Счётчик `contracts_km_contracts_paid_cancelled_total` и запись INFO «работа по оплаченному договору прекращена: заказ
не отменяется, деньги возвращают» означают обратный порядок: договор сначала оплачен, потом прекращён. Заказ в Ordering
при этом не отменяется, деньги возвращают тем же порядком, но за договор, который к прекращению уже передан в 1С:УСК, —
только после того, как 1С:УСК подтвердит, что договор у неё не зарегистрирован или его регистрация отменена: прекращение
передачу не отзывает, и 1С:УСК может зарегистрировать договор и выпустить по нему полис. Передавался ли договор,
показывает журнал исходящих — запрос только на чтение:

```sql
select message_id, status, attempts, error_message, created_at, published_at
  from outbox_messages
 where aggregate_type = 'CONTRACT' and aggregate_id = '<contract-id>'
 order by created_at;
```

Строк нет — договор в 1С:УСК не передавался, деньги возвращают обычным порядком. Есть строка в любом статусе — деньги
возвращают только после подтверждения 1С:УСК; вопрос к ней — по `message_id` передачи. `PUBLISHED` — передача ушла,
`NEW` — ещё уйдёт: прекращение её не отменяет. `FAILED` — передача отклонена окончательно, но и она могла дойти: сервис
не всегда знает, что брокер получил сообщение (брокер промолчал, ожидание подтверждения прервала остановка сервиса или
ведущий сменился между отправкой и записью исхода), а `attempts` и `error_message` показывают только записанные
попытки.

### Закрытие заказа к отмене, которого нет в Ordering

Заказ «к отмене» без номера заказа Ordering (`external_order_id` пуст) проход отмены закрывает сам, только когда поиск
Ordering ответил, что заказа нет. Если Ordering раз за разом отклоняет поиск ([troubleshooting.md](troubleshooting.md),
«Заказ «к отмене» без номера не закрывается»), запись остаётся «к отмене». Дежурный закрывает её только после сверки с
командой Ordering: по идентификатору документа (идентификатор записи `payment_orders.id`) и клиенту (`client_id`) заказа
у них нет. Один запрос по идентификатору договора:

```sql
update payment_orders
   set state = 'CANCELLED', updated_at = now()
 where contract_id = '<contract-id>'
   and state = 'CANCEL_PENDING'
   and external_order_id is null;
```

Запрос трогает только запись «к отмене» без номера заказа: запись, у которой номер уже есть, проход отмены отменит сам,
`update` сообщит `0` строк.

Если заказ у Ordering всё же есть, запись не закрывают и вручную у Ordering заказ не отменяют. Команда Ordering называет
номер заказа, и дежурный записывает его вместе с отметкой «отмена отправлялась» одним запросом с тем же условием:

```sql
update payment_orders
   set external_order_id = '<order-id>', cancel_requested = true, updated_at = now()
 where contract_id = '<contract-id>'
   and state = 'CANCEL_PENDING'
   and external_order_id is null;
```

Ближайший проход отмены по записи с номером и отметкой сначала запрашивает состояние заказа: `CANCELED` — закрывает
запись без второй отмены, любое другое — отменяет заказ с каналом и причиной из настроек. Без отметки проход послал бы
отмену сразу, и отказ Ordering по уже отменённому заказу увёл бы запись в «отмена отклонена» (`CANCEL_REJECTED`) с
ERROR и ростом `contracts_payment_order_cancel_rejected_total`.
